### The shipped Docker path could not be exercised — BLOCKER

`docker compose up --build -d --wait` fails at image pull. The sandbox's egress policy
answers `403` to `CONNECT production.cloudfront.docker.com:443` (Docker Hub's blob CDN) and
blocks `pkg-containers.githubusercontent.com` (GHCR's blob host) too, so no image layer can
be fetched by either the build path or `docker-compose.pull.yml`. Registry manifest hosts
(`registry-1.docker.io`, `ghcr.io`) are reachable; only the blob CDNs are denied.

```
Image postgres:18-alpine Pulling
Image redis:8-alpine Pulling
failed to copy: httpReadSeeker: failed open: failed to do request:
Get "https://production.cloudfront.docker.com/registry-v2/..." : Forbidden
```

This is an environment restriction, not an asobeast defect, so no product issue was filed
for it. Per the rules of engagement I fell back to the same stack run natively and continued
with everything still reachable, recording the deviation:

- PostgreSQL **16.13** instead of the composed **18-alpine**
- Redis **7.0.15** instead of the composed **8-alpine**
- `AUTH_COOKIE_SECURE=false` and `NODE_ENV=development` on the API, because the run is over
  plain HTTP on a loopback host rather than the image's production defaults

Everything below therefore validates the application, not the packaging. See §5.

### Store endpoints are unreachable — BLOCKER

`itunes.apple.com`, `apps.apple.com` and `play.google.com` are all denied by the same egress
policy. Live import, rank checks, review sync, competitor discovery, category charts and the
daily pipeline cannot produce real data here. This blocked every store-dependent happy path
(§5), but it did let me test the failure handling directly, which passed (TC-APP-010/011,
TC-UI-013).

### Test data

Live import is blocked, so the dataset was written directly with `qa/seed-qa.ts` and is
deliberately hostile: 5 apps (including one whose title carries Polish diacritics, emoji,
Arabic, Chinese and a 180 character run), 216 keywords (200 for pagination plus unicode, RTL,
emoji, a 100 character boundary keyword, and `<script>alert(1)</script>` and
`'; DROP TABLE "Keyword"; --` inserted below the API's validation), 167 rankings covering a
60 day trend with gaps, a flat line, a single point and an all-null series, 5 reviews
(unicode, RTL, XSS, a 9 000 character body, null author and null date), change events, SERP
entries and category ranks with a null day. Creating this by hand is itself a deviation from
the documented flow and is called out as a coverage gap in §5.

### Cases I invalidated and re-ran

Two results from the first interaction pass were wrong and are not counted as findings:

- **"No loading state on a slow network."** I throttled only client-side `/api/backend/*`
  calls, but the pages are server-rendered, so the data was already in the HTML and no
  loading state was needed. The test proved nothing. Replaced by TC-UI-013, which stops the
  API outright; that passed.
- **"Sidebar shows 0 tracked."** This came from the same run, where I forced every
  `/api/backend/*` call to 500, so the apps query legitimately had no data. With the backend
  healthy the switcher shows the correct app. Not a defect. Worth noting only that while the
  backend is down the sidebar asserts "0 tracked" rather than an unknown state; too minor to
  file.

One case is **BLOCKED** rather than failed: adding a keyword through the UI (TC-UI-004 in the
interaction script). My automation could not locate the real submit control inside the add
dialog, and the database confirmed no keyword was created, so the double-click check was not
actually exercised through the browser. The equivalent race was proven at the API with eight
concurrent requests (TC-KW-014, PASS).

## 4. Failures grouped by area, most severe first

Every failure found in this pass is **P3**. Nothing rated P0, P1 or P2 was found.

**Web presentation**
1. #49 — React hydration error on five routes in a production build. Reproducible 5/5 per
   route, absent under `next dev`, final DOM converges. Cost is console noise and a discarded
   server render, not broken output.
2. #50 — A store icon that fails to load renders overflowing alt text over the app name.
   Reachable whenever an icon URL stops resolving or the store CDN is unreachable.
3. #52 — The difficulty cell multiplies by 10 without the clamp the API's own
   `toDifficulty100` applies. Not reachable through the scoring path, which clamps to 0-10 on
   write; a duplicated-rule robustness defect surfaced by deliberately out-of-domain data.

**API contract**
4. #51 — `/apps/:id/actions` answers 200 for an unknown or foreign app id where all 13
   sibling routes answer 404. Verified not to be a data leak.

**Auth hardening**
5. #53 — Registration accepts ten spaces as a password.

## 5. Coverage gaps

1. **The Docker packaging is untested.** The self-hosted Compose path is the product, and the
   sandbox's egress policy blocks Docker Hub and GHCR blob CDNs, so no image could be pulled
   or built. Compose file syntax validates (`docker compose config` is clean) and nothing else
   about the packaging was exercised: image build, healthchecks, `depends_on` ordering,
   memory limits, the internal `backend` network, volume persistence, the tunnel and pull
   overlays, and the production-mode guards the image turns on (`NODE_ENV=production`,
   `AUTH_COOKIE_SECURE=true`, `TRUST_PROXY`). This needs a re-run on a host with registry
   access before shipping.
2. **PostgreSQL 16 and Redis 7 instead of 18 and 8.** Migrations applied cleanly and every
   query worked, but no PostgreSQL 18 or Redis 8 specific behaviour was covered.
3. **Every store-dependent happy path.** Import, refresh and metadata diffing, rank checks to
   depth 200, keyword suggestions and the spider, competitor discovery, review sync, category
   charts, market availability probes, the daily pipeline, scoring jobs, the store canary and
   proxy pool. All of it needs reachable store endpoints. Only the failure paths were tested,
   and they behaved well. The 7 failed queue jobs visible in `/health` during the run are
   these blocked store calls, which is the correct outcome given the network.
4. **Data was seeded, not created through the product.** Because import is blocked, apps,
   snapshots, rankings, reviews and competitors were written straight to the database, so
   real store payload shapes, parser behaviour and the create flows themselves are unverified.
5. **Outbound integrations.** SMTP email alerts, webhook delivery and signature verification
   (registration and SSRF rejection were tested; no delivery was attempted), OpenAI-backed AI
   audit and metadata drafts (needs `OPENAI_API_KEY`), Stripe billing and its webhook, and
   Sentry reporting.
6. **Multi-user and role behaviour.** Two workspaces were used for isolation, but the invite
   flow, member removal, non-owner roles and any owner-only screen were not exercised;
   registration closes after the owner, so a second user has to be created out of band.
7. **Email-dependent flows.** Password reset, email verification and invite acceptance all
   need a delivered token and no SMTP was configured.
8. **The MCP server**, `/admin/queues`, `/metrics`, `/docs`, the support and capacity admin
   surfaces, CSV export, and tablet breakpoints between 375 px and 1440 px.
9. **Two browser tabs editing the same record** and refresh mid-multi-step-flow, which need a
   working create path in the UI.

## 6. Risk assessment

The application logic is in good shape: input validation is strict and whitelist-based
throughout, tenant isolation held on every one of 17 cross-workspace probes, SSRF is blocked
at both app import and webhook registration including cloud metadata, stored XSS renders
escaped, a fast double click produced no duplicate under eight concurrent writes, data and
sessions survive a full restart, and the project's own 1969 tests pass. Every defect found
is P3, and three of the five are cosmetic or defensive rather than user-visible breakage.

The reason I would not ship this build on the strength of this pass is coverage, not quality:
the Docker packaging that *is* the self-hosted product was never started, and every
store-dependent feature — the entire reason the tool exists — could only be tested for how it
fails, not for whether it works. Those gaps are environmental and say nothing bad about the
code.

My recommendation is to re-run this same pass on a host with registry and store access before
release, and treat the five open issues as cleanup that need not block it.
