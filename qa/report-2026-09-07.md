## 3. New findings in detail

### #57 — keyword field merges concurrent saves (P2, intermittent)

The one genuine new defect. `PUT /apps/:id/keyword-field` replaces the whole field correctly
when saves are sequential, but when two saves land together the stored field sometimes keeps
the keywords from both.

```
sequential:  PUT alpha,bravo,charlie  -> ['alpha','bravo','charlie']
             PUT delta,echo,foxtrot   -> ['delta','echo','foxtrot']          correct

concurrent:  PUT alpha,bravo,charlie + PUT delta,echo,foxtrot
             -> ['alpha','bravo','charlie','delta','echo','foxtrot']         wrong
```

Reproducibility 3/9 from a clean state. The user impact is that this is the one field
submitted verbatim to the App Store, and the merged result can blow its budget: two
concurrent saves of nine keywords each produced `charactersUsed: 197` against
`charactersLimit: 100`. Both callers get a 200 and nothing signals a conflict.

Hypothesis recorded in the issue, not fixed: `setKeywordField`
(`apps/api/src/keywords/keywords.service.ts:312`) reads the current field outside the
transaction that writes it, so two interleaved readers each compute a stale-set that misses
the other's keywords.

## 5. Coverage gaps

Reduced from the first pass but still real:

1. **Docker packaging, still entirely untested.** Same blocker, same reason. Image build,
   healthchecks, `depends_on` ordering, memory limits, the internal network, volume
   persistence, the tunnel and pull overlays and the production-mode guards
   (`NODE_ENV=production`, `AUTH_COOKIE_SECURE=true`, `TRUST_PROXY`) have never been
   exercised.
2. **PostgreSQL 16 / Redis 7 rather than the composed 18 / 8.**
3. **Every store-dependent happy path.** Import, refresh, metadata diffing, rank checks,
   keyword suggestions and the spider, competitor discovery, review sync, category charts and
   market availability. Only failure behaviour is covered, and it behaves well.
4. **Data is still seeded rather than imported**, so real store payload shapes and the parsers
   remain unverified.
5. **Not exercised this pass:** `ChangePasswordDto` (the third place the weak password rule
   likely lives), password reset and email verification token flows, Stripe billing and its
   webhook, OpenAI-backed audit and metadata drafts, the MCP server's 21 tools, `/admin/queues`,
   `/metrics`, `/docs`, and CSV export from pages other than keywords.
6. **A two-tab UI edit** of the same record, because no page reachable in this build exposed a
   Save control that two tabs could contend on. The API-level equivalent did run.

## 6. Risk assessment

Two passes over this commit have produced one P2 and four P3 issues, and the second pass
went considerably deeper than the first: a real second user, role and admin-surface checks,
cascade integrity, the Action Center lifecycle, and both alert delivery paths verified end to
end including an independently recomputed webhook HMAC. Nearly all of it passed, and several
things that are easy to get wrong are right here — admin surfaces hide their own existence
rather than returning a tell-tale 403, deleting an app leaves zero orphaned rows, ten
concurrent keyword adds produce one row, and the CSV export is safe to open in a spreadsheet.

The one new defect, #57, is worth fixing before it bites someone: it is silent, it lands on
the single field that goes verbatim to Apple, and it can push that field past the store limit
without telling either user.

I would still not ship on the strength of these two passes, and still for coverage reasons
rather than quality. The Docker packaging that *is* the self-hosted product has never been
started in either pass, and the store-facing features that justify the tool can still only be
tested for how they fail. Re-run on a host with registry and store access before release.
