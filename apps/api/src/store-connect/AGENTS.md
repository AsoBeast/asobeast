# Store console rules

### Domain rule 23: A console key is sealed, owner only, and the funnel is read from the store's own report

Connecting a store console is optional and off until `STORE_CONNECT_ENCRYPTION_KEY` is set (`SECRET_BOX` is `null`, `GET /store-connections` answers `available: false`, every change but a disconnect answers `409`, the schedule is removed and nothing reaches Apple; a stored key that no longer decrypts answers `409` with `CREDENTIAL_UNREADABLE` and marks the connection rejected). One connection per workspace and store, through `GET /store-connections` and `PUT`, `POST …/verify`, `POST …/sync` and `DELETE /store-connections/{store}`; every change is `@SessionOnly()` with `OwnerGuard`, so no `asob_` token, write scope included, can replace or remove a key, and a member reads the state. `PUT` verifies the key with Apple before anything is stored (`422` refused, `502` unreachable, `400` for a key that is not a P-256 PKCS8 PEM, which `normalizePrivateKey` rebuilds when a password field joined its lines), replaces any earlier key and its report requests, and queues a sync. The credential is sealed as one JSON string by `SecretBox` (AES-256-GCM, `v1.<key id>.<iv>.<tag>.<body>`) with the context `store-connection:<workspaceId>:<store>`, so a ciphertext copied into another workspace never opens; `STORE_CONNECT_ENCRYPTION_KEY_PREVIOUS` opens an older one and `StoreConnectionService.openAppStore` and `openPlay` reseal it. The issuer ID, key ID and public key fingerprint are kept in clear; the sealed value is never answered, exported (`SECRET_FIELDS`) or logged (PEM blocks and signed tokens are scrubbed). Report access is learned, never asked: a `201` creating a report request records `admin`, a `403` records `readOnly` with the sentence that an Admin key is needed once, and an existing request is adopted by listing first. The sync runs in its own `store-connect` queue at concurrency 1, outside the store request budget and the proxy pool, one deduplicated job per workspace and store, fanned out by `CRON_STORE_REPORTS` to the workspaces `ActiveWorkspaces.forDailyRun` names and queued by connect, verify and sync. It matches each primary App Store app to the key's apps by store id (an app the key cannot see is `unmatched`), lists each visible app's remote requests on every run so an ongoing request Apple stopped or dropped is placed again, requests the one time snapshot and the ongoing Discovery and Engagement report, downloads at most `MAX_INSTANCES_PER_RUN` (200) daily instances per attempt newer than each request's `lastProcessingDate` in ascending processing date order, keeps the gzip in `StoreReportInstance.raw` for `RETENTION_STORE_REPORTS_DAYS`, and pivots the rows by header name into `StoreFunnelDay` (app, date, territory, source type, page type) with an upsert that never lets an older processing date overwrite a newer one; `lastProcessingDate` only advances. An Apple error for one app, or a report that cannot be downloaded or read, stops only that app or that request for the run; an attempt of the job that is not its last then keeps the earlier `lastError` and fails with `PartialSyncRetryError`, so BullMQ tries the failures again, and only the last attempt leaves `PARTIAL_SYNC` (or `PLAY_PARTIAL_SYNC`) in `lastError` (`retriesFailures`, never after a rate limit; a key that may not request reports records `ADMIN_KEY_NEEDED` and a Play file over the ceiling, counted as `skipped`, records `PLAY_PARTIAL_SYNC` at once); a segment whose size differs stops that request for the run, a checksum mismatch is only logged, a `429` ends the run normally, a `401` or `403` from the App Store Connect API after the request phase marks the connection `rejected` with the reason (`refusalOf`: the missing agreement code `FORBIDDEN.REQUIRED_AGREEMENTS_MISSING_OR_EXPIRED` names the agreement, anything else the refused key) and fails the job as unrecoverable, while a refused segment download is a plain error and never rejects the key, and a `5xx` is retried once. A territory is resolved to a storefront through `countryOfTerritory` or kept with a `null` country, which every market filter leaves out and "all markets" counts. `GET /apps/{id}/funnel` answers `connected: false` and empty series for a competitor, an app without an ongoing `requested` request of an active connection, or with the feature off, even when rows survive a disconnect; otherwise a zero filled daily series and the 7, 14 and 28 day windows of complete days against the period before. A day is complete once it is three days old and no later than the newest stored day of the app (`reportedThrough`), derived at read time and never stored, so a sync that falls behind never turns missing days into zeros. Conversion is Get taps divided by unique impressions on the App Store, as Apple reports them; a dimension a store does not report is `null`, never estimated. When the key may read it, the sync also downloads the detailed report into `StoreFunnelPageDay` (one row per date, territory and page title, `no page` dropped) with its own `detailedReportId` and `detailedLastProcessingDate`; any error on the detailed report but a rate limit, while listing or applying it, only skips that lane for the run and never rejects the key or holds back the standard report, and the funnel answers the optional `pages` of the last 28 complete days, default page first. `GET /apps/{id}/changes/impact` merges an optional `funnel` block into every window only while the app's store connection reports it (`measureChangeFunnel`): the same number of complete days before the change and from the day of the change on, `measured` when every day after is final, `pending` while Apple finishes them, `unmeasured` when the console reports nothing for the whole period before; without a connection the field is absent, so the response stays as it was. Both conversion rules read 21 or 14 calendar days of the home market ending at `completeThrough` and hold an existing action as `withheld` instead of resolving or confirming it while the console stops reporting the app (`ActionFunnel.reporting`), a day of the window is missing, page views move past `CONVERSION_PAGE_VIEW_TOLERANCE`, or a page or the default page has under `CPP_MIN_UNIQUE_IMPRESSIONS`. Google Play connects a service account instead (`PUT /store-connections/GOOGLE_PLAY` with `serviceAccountJson` and a `pubsite_prod` `bucket`, picked by `StoreConnectionBodyPipe`; a body whose `store` differs from the path is `400`): the JSON must hold an RSA PEM key (`400` otherwise), verification lists `stats/store_performance/` once with a `devstorage.read_only` token (`401`, `403` and `404` answer `422`, the last naming the bucket), the sealed credential is `{ clientEmail, privateKeyId, privateKey, bucket }`, `issuerId` stores the email and `keyId` the private key id, and `reportAccess` is `admin` at once because Google has no request step. Google Play also connects through the owner's own Google account when `GOOGLE_PLAY_OAUTH_CLIENT_ID`, `GOOGLE_PLAY_OAUTH_CLIENT_SECRET` and `WEB_PUBLIC_URL` are set (otherwise `GOOGLE_OAUTH_CLIENT` is `null`, `GET /store-connections` answers `googleSignIn: false` and both sign in routes answer `409`; a stored Google account connection is never rejected for it, because the configuration of the instance is not the credential, so verify answers `409` and the sync fails and retries): `POST /store-connections/GOOGLE_PLAY/sign-in` with the `bucket` answers the Google consent address (offline access, `prompt=consent`, PKCE S256, scopes `openid email devstorage.read_only`) carrying a state that `SecretBox` seals with the context `play-sign-in:<workspaceId>:<userId>` around the bucket, the PKCE verifier and a ten minute expiry (`sign-in-state.ts`); Google returns to the web page `PLAY_SIGN_IN_PATH` (`/integrations/google-play`), which posts the code and the state once to `POST …/sign-in/complete`. That route opens the state for the same owner and workspace only (`400` otherwise), redeems the code (`400` when Google refuses it), refuses an answer whose granted scopes leave out storage with `422`, lists the bucket with the refresh token exactly as a key is checked, and stores `{ email, refreshToken, bucket }` sealed like any credential, with `credential = 'googleAccount'`, `issuerId` the email and `keyId` the Google subject; both routes are `@SessionOnly()` with `OwnerGuard`. `GcsApi` takes a `GoogleGrant` (the service account's JWT bearer assertion or the refresh token grant, built by `GcsApiFactory`) and the account it reads as, and `playRefusal` (`play/play-refusal.ts`) is the one wording of a Play refusal for connect, verify and sync: a token answer is a refusal only for the OAuth codes `invalid_grant`, `invalid_client`, `unauthorized_client` and `redirect_uri_mismatch` (any other `4xx` stays a retryable `GcsError`, a `429` a rate limit), and a refused token names the deleted key or the revoked sign in, or the instance's OAuth client when Google answers `invalid_client`, `unauthorized_client` or `redirect_uri_mismatch` (`CLIENT_REFUSED`, also `409` on `…/sign-in/complete`), a `403` names the account and the Account permissions tab, and only a `404` names the bucket, because Cloud Storage answers `404` for a bucket that does not exist even to an account without access. `PlayReportSync` lists each primary Play app's files under its package prefix (at most `MAX_LISTED_OBJECTS`, `unmatched` when the bucket holds none), checks the bucket once per run (a refusal or a missing bucket rejects the connection), marks an app `forbidden` when Google refuses its listing or a file, skips a file that vanished or cannot be read (`PLAY_PARTIAL_SYNC`) without holding back the rest, skips a file listed above `PLAY_REPORT_MAX_BYTES` and stops reading one past it, keeps search terms storable (`MAX_TERM_CHARS`, no NUL, no lone surrogate) and counts within int4, and downloads the current and the previous month's country and traffic source files only when the object's `generation` changed, recorded as a `MONTHLY` `StoreReportInstance` whose `remoteId` is the object name and generation. The country file writes `StoreFunnelDay` rows with `sourceType = 'all'` and the country code as territory, the traffic source file rows with `territory = 'all'` and `country = null` (`funnelScope`): a market reads the first set and "all markets" the second, so the two breakdowns are never summed; visitors land in `pageViews` and acquisitions in `gets`, Play conversion is acquisitions divided by visitors and `impressions` stay `null`. A newer generation replaces the month's rows of its breakdown in the same transaction, so a row Google dropped does not linger. The traffic file also replaces the month's `StoreFunnelSearchTerm` rows (tenant owned, RLS, unique on app, month and raw term), and `GET /apps/{id}/keywords` gives a Play keyword of a reporting Play connection the optional `playAcquisitions` of the newest complete month, or the month in progress when it is the only one, whose `normalized` term equals `normalizeText` of the keyword, summing the spellings of that month; an App Store keyword carries no field.
