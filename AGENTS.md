# AGENTS.md — asobeast

## What this project is

**asobeast** is an open source, self hosted ASO (App Store Optimization) toolkit for indie developers and small teams. It imports an app from a store URL, stores metadata snapshots, extracts and tracks keywords, checks keyword rankings daily, scores keywords (traffic, difficulty, opportunity) and shows everything through a Next.js frontend talking to a NestJS API. All store requests run on the machine that hosts the app. Multi-country: an app is a **single tracking entity** with a home storefront (`app.country`, from the URL or `DEFAULT_COUNTRY`); keyword tracking carries its own country, so one app tracks keywords across many storefronts, filtered per market on the keyword monitor. **Both stores are live: Apple App Store and Google Play.** All scraping stays behind the `StoreProvider` interface (provider isolation unchanged), so a parser breakage is contained to one module.

**Everything described above is implemented and merged on `main`.** What constrains change is the compatibility promise: the HTTP contract, the `@asobeast/shared` contract types and the MCP tool surface are stable for the whole `1.x` line — read the release policy below before starting any change.

## Tech stack

- **Monorepo:** pnpm workspaces + Turborepo, Node.js 24.9+ (the images build on `node:24-alpine`; Jest runs the API suites with `--experimental-vm-modules` so it can `require()` the ESM-only NestJS 12 packages, which needs 24.9), TypeScript strict everywhere
- **apps/api:** NestJS (latest stable), Prisma + PostgreSQL 18, BullMQ + Redis 8, Jest + Supertest
- **apps/web:** Next.js (latest stable, App Router, Tailwind), consumes the API over HTTP; Vitest + Playwright
- **apps/mcp:** stdio MCP server built with tsup, tested with Vitest. Both MCP surfaces run `@modelcontextprotocol/server@2.3.0` and serve protocol `2026-07-28` alongside the 2025 revisions from one factory
- **packages/shared:** `@asobeast/shared`, compiled with tsup (cjs + esm + dts), tested with Vitest
- **packages/typescript-config:** `@asobeast/typescript-config`, base tsconfigs
- Scraping: `@perttu/app-store-scraper` (App Store) and `@mradex77/google-play-scraper` (Google Play), both isolated behind the `StoreProvider` interface.
- Screenshot text: `tesseract.js` 7 (WASM) with bundled `@tesseract.js-data/*` integer models and `sharp` for preprocessing, behind the `OcrEngine` interface. Never a CDN, never OpenAI.
- Docker + docker compose for dev services and self hosting

## Commands (run from the repo root)

```bash
pnpm install
pnpm dev                        # turbo run dev: shared (tsup watch) + api + web
pnpm --filter api dev           # just the API
pnpm --filter web dev           # just the frontend
pnpm build                      # turbo run build (respects the dependency graph)
pnpm lint && pnpm test          # turbo run lint / test across all packages; lint never writes
pnpm --filter api lint:fix      # the only lint that rewrites files
pnpm --filter api test:e2e      # supertest e2e, providers mocked, separate REDIS_DB
pnpm --filter api test:isolation # two-workspace tenancy isolation suite, blocking in CI
pnpm --filter web test:e2e      # playwright against the typed mock api on port 4100
pnpm --filter api db:migrate    # prisma migrate dev (script inside apps/api)
pnpm --filter api db:studio
pnpm format:check               # prettier; the pre-commit hook formats staged files
docker compose -f docker-compose.dev.yml up -d
```

The browser suite needs its browsers once: `pnpm --filter web exec playwright install chromium webkit`.

A fresh checkout needs its `.env` files before any of that runs:

```bash
pnpm env:dev                    # writes .env, apps/api/.env and apps/web/.env from the examples
```

It copies each `.env.example` and generates the secrets they leave empty, so the
files are working development configuration rather than a template. Existing
files are kept, so a re-run never overwrites real credentials.

## Cloud sessions (Claude Code on the web)

A cloud session is a Claude Code session running on an Anthropic-managed VM
instead of a laptop: you describe a task from claude.ai/code or the mobile app,
it works in the sandbox, and it opens a pull request. Two committed files make
this repository work there.

- `scripts/cloud/setup.sh` provisions the VM. Paste it into the **Setup script**
  field of the cloud environment at claude.ai/code. It runs once per
  environment, installs Node 24 over the image's Node 22 so cloud runs agree
  with CI and both Dockerfiles, and pre-pulls the two Compose images. The result
  is snapshotted and reused, so later sessions skip it.
- `scripts/cloud/session-start.sh` prepares the checkout. The SessionStart hook
  in `.claude/settings.json` runs it on every session and resume: it starts
  `dockerd`, brings up `docker-compose.dev.yml`, runs `pnpm env:dev`, installs
  dependencies, generates the Prisma client and applies migrations. It exits
  immediately unless `CLAUDE_CODE_REMOTE=true`, so a local session is untouched.

Postgres and Redis come from `docker-compose.dev.yml`, not from the sandbox's own
PostgreSQL 16 and Redis 7, because this repository targets 18 and 8. The images
bind 5433 and 6380, which is what `apps/api/.env.example` already points at.

What runs in a cloud session, and what does not:

| Suite                                          | Cloud         | Note                                                                                                                                                                                          |
| ---------------------------------------------- | ------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm lint`, `pnpm test`, `pnpm build`         | yes           | no services needed beyond the Prisma client                                                                                                                                                   |
| `pnpm --filter api test:e2e`, `test:isolation` | yes           | the Compose services cover both                                                                                                                                                               |
| `docker compose` stacks and the drills         | yes           | `dockerd` runs inside the sandbox                                                                                                                                                             |
| `pnpm --filter web test:e2e`                   | no by default | Playwright downloads Chromium from `cdn.playwright.dev`, which is not on the default network allowlist. Add it under **Custom** network access, keeping the default list, to enable the suite |

Set the environment's network access to **Trusted**. That allowlist already
covers npm, GitHub, Docker Hub, ghcr.io and nodejs.org, which is everything the
setup script and the install need. Never put a real secret in the environment's
**Environment variables** box: anyone using the environment can read it, and
`pnpm env:dev` generates the development secrets in the session anyway.

Two limits worth knowing before relying on this. The VM is roughly 4 vCPU, 16 GB
RAM and 30 GB disk, so the load benchmarks are not a cloud workload. And routine
GitHub triggers fire on pull request and release events only, not on issues, so
"fix issue #12" is a message you send to a session, not something an issue opens
by itself.

## Git conventions (strict)

- Conventional commits: `type(scope): subject`. Types: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `build`, `ci`, `perf`, `revert`.
- Scopes: `repo` (workspace level), `api`, `web`, `mcp`, `shared`, `docker`, `ci`, `docs` (the Mintlify site in `/docs`), dependency scopes `deps`, `deps-dev`, plus API domain scopes `db`, `providers`, `apps`, `keywords`, `rankings`, `scoring`, `competitors`, `analytics`, `jobs`, `audit`, `metadata`, `changes`, `alerts`, `auth`, `actions` (domain scopes always mean code inside `apps/api`; `actions` means `apps/api/src/actions/`).
- Subject: imperative, lowercase, no trailing period, max 72 chars. One logical change = one commit; use the body only for what a reviewer cannot infer from the diff.
- Before every commit: `pnpm lint && pnpm test` green (plus `pnpm build` when configs or dependencies changed).
- Before a pull request is ready, in this order: after everything is done, run the code review skills from `agent-skills` and make sure everything is correct, every edge case is handled, there are no errors or bugs and the code quality is very good; after all changes, run `/open-code-review:review` to review the pull request against `main`; then have a Sonnet 5.5 subagent run manual QA of the plan's functionality and all its edge cases, through `agent-browser` where it can, because it spends far fewer tokens; a fix made in any pass reruns both code reviews, so the last review covers the final diff. Before each release: the same full code review over everything since the last tag, plus regression testing with manual QA through `dogfood` and `playwright-cli`. `CONTRIBUTING.md` holds the details.
- Never commit `.env` files, `node_modules`, `dist`, `.next`, `.turbo`.
- The `pre-commit` hook formats staged files with lint-staged, and the `commit-msg` hook enforces the type, scope and subject rules with commitlint. Use `--no-verify` only in an emergency and explain it in the pull request.

### Roadmap and release policy

- `1.0.0` is the first release of this repository. The `1.x` line takes normal feature work under semantic versioning: a `feat` bumps the minor, a `fix` bumps the patch.
- **The compatibility promise is what constrains `1.x` now.** The HTTP contract, the `@asobeast/shared` contract types and the MCP tool surface stay compatible for the whole line; breaking any of them requires `2.0.0`. Additive change is fine — a new endpoint, a new optional field, a new tool. Removing or renaming anything on those three surfaces, or narrowing what a request accepts or a response guarantees, is not. Environment variables, the database schema and internal modules are outside the promise; schema changes always ship as forward Prisma migrations.
- The upgrade and backup drills read their baseline from `UPGRADE_FROM_TAG`, currently `v1.0.0`, so every drill applies each migration added since the first release. CI resolves the baseline first and skips the drill steps when it is the commit under test rather than running a vacuous pass.
- Every `fix` must include a regression test written from the reported symptom, observed failing for that reason before the fix, and passing afterward with the rest of the suite. Use a unit spec for logic, API e2e for a contract or guard, and Playwright for a user-visible flow.
- Release Please owns tags, versions and `CHANGELOG.md`. Never cut a release by hand while the pipeline is healthy. When a manual release is unavoidable, bump the six manifests together (`package.json`, `apps/{api,web,mcp}/package.json`, `packages/{shared,mcp-tools}/package.json`), match `.release-please-manifest.json` to them and push the matching `v` tag — `.github/scripts/verify-release-state.sh` fails the Release workflow when the manifest names a version origin has no tag for. See `docs/operations/release-recovery.mdx`.

## Coding conventions

- TypeScript `strict: true` in all packages, extending `@asobeast/typescript-config`. No `any` except where untyped scraper payloads enter the provider layer, mapped to typed structures immediately.
- The repository forbids every comment: no line comments, block comments, JSDoc or TODOs, in source and tests alike. `.coderabbit.yaml` carries the same instruction, so CodeRabbit flags a comment on every pull request. Make the implementation explain itself through names, types and extracted functions; a why that fits nowhere else goes in the documentation site or the pull request description.
- Every controller input is a DTO validated with `class-validator`; global `ValidationPipe` with `whitelist: true`.
- The `path` of an error envelope is the request path without its query string (`pathWithoutQuery`, `apps/api/src/common/request-path.ts`), and Nest's unknown route message is cut the same way (`withoutQueryEcho`), because a client that puts a credential in a URL must not get it back in a response body. Anything that builds an `ApiErrorEnvelope` for a request calls `pathWithoutQuery`; the web proxy's own envelope already uses `nextUrl.pathname`.
- Text reaches a service only through `@Param`, `@Query` or `@Body` arguments, where the global `StorableTextPipe` runs ahead of the `ValidationPipe` and refuses a NUL character (`404` in a path id, `400` elsewhere) because PostgreSQL text cannot store it, and an unpaired surrogate (`400`) because the Prisma query protocol cannot carry it. It also refuses a body or query nested more than `MAX_NESTING_DEPTH` (64) levels with `400`, passwords included, because the `ValidationPipe` after it recurses and would otherwise throw a `RangeError` as a `500`. A field that is only hashed, never stored (a password, a one time token), carries `@HashedOnly()` and is skipped; `@IsPassword()` applies it. The mark lives on the DTO class and survives `extends`, but a class built with `PartialType`, `PickType` or `OmitType` does not inherit it and must apply `@HashedOnly()` again; until it does the field is scanned, which refuses a NUL rather than storing one. A controller never reads `req.params`, `req.query` or `req.body` itself; `McpController` is the one exception, because its tool arguments are dispatched in process to `GET` routes that carry the same pipe. Do not map the database error in `AllExceptionsFilter` instead: server sourced text must stay a visible `500`.
- Controllers thin, services own logic, scoring functions pure and unit tested.
- All scraping goes through the `StoreProvider` interface in `apps/api/src/store-providers/`. No other module may import a scraper library. This isolation contains parser breakage and lets a future cloud version swap in proxies or a data API.
- Store raw scraper payloads in `raw` Json columns; parsers change, raw data allows reprocessing.
- Every email is a React Email template rendered with `renderEmail` inside `EmailLayout` (`apps/api/src/mail/`). Never build email HTML by string concatenation. A template is a pure component whose props carry everything it shows, including the web origin; colours come from `email-theme.ts`.
- A migration never assumes `_prisma_migrations` exists. `prisma migrate dev` replays every migration into a shadow database that has no such table, so a migration that reads it guards the read with `to_regclass('_prisma_migrations')` inside PL/pgSQL. `apps/api/test/migration-replay.e2e-spec.ts` replays the whole history that way. A released migration is edited only to make it replayable, and the edit ships with a forward migration that rewrites the stored checksum from the released value to the edited one, as `20261008092139_record_plain_play_whats_new_checksum` does. `migrate dev` stops at a changed checksum before it applies anything, so a database that holds the released checksum runs `pnpm --filter api db:deploy` once first.
- All dates UTC; daily granularity uses Postgres `date` (`@db.Date`); "today" is the UTC date.
- `installs` is `BigInt` (kept for future Google Play); JSON serialization patched in `apps/api/src/main.ts`.

## Documentation site

The public documentation lives in `/docs` and is published at `docs.asobeast.com` by Mintlify. It is not a pnpm workspace member and has no build step in this repository, so the Mintlify CLI is never a dependency and is always invoked through `pnpm dlx`.

- Preview with `pnpm docs:dev`. Check with `pnpm docs:check`, which runs `mint validate`, `mint broken-links` and `mint a11y`. Lint prose with `pnpm docs:prose`, which runs Vale.
- Every page needs a `title` and a `description`. Headings use sentence case. Prose uses no dash punctuation, meaning no em dash, no en dash and no spaced hyphen standing in for a comma or colon. Hyphenated compound modifiers are correct and stay. `docs/styles/asobeast/Dashes.yml` enforces this in CI.
- `docs/configuration/reference.mdx` is the single source of truth for environment variables on the site. A change to `apps/api/.env.example` or `apps/web/.env.example` updates it in the same commit.
- `docs/api-reference/openapi.json` is captured from the running API with `pnpm docs:openapi`. A change to a controller, a DTO or a response shape re-runs it. Its `info.version` is the release version, so Release Please bumps it with every other versioned file and no recapture is needed for a release. `pnpm check:release-versions` reads the JSON files registered in `release-please-config.json` and every workspace manifest, and fails a registered file that has drifted off the version or a manifest that states it without being registered.
- A fact lives on exactly one page. The concept pages under `docs/concepts/` own the domain rules and every other page links to them; the screenshot caption rules live in `docs/guides/screenshot-captions.mdx` and `docs/concepts/stores.mdx`.
- Prettier does not format `docs/**/*.mdx`. Use `pnpm docs:format`, which runs Mintlify's canonical formatter.
- Use the `docs` commit scope for the site and `repo` for repository-level documentation such as `README.md` and `CONTRIBUTING.md`.
- **`README.md` follows the same dash rule as the site and is linted for it in CI** (`pnpm check:readme-prose`, and a step in `.github/workflows/docs.yml`). It is also deliberately short: it introduces the product, shows the install, answers the questions a search engine or an assistant gets asked, and links to `/docs` for everything else. A fact that belongs on a documentation page does not get a second copy in the README, so extend the page and link it.
- The `overrides` block in `pnpm-workspace.yaml` holds transitive pins that a direct dependency cannot yet deliver, for example `deepmerge-ts` for GHSA-ggr8-5vv4-36mx, which the newest Prisma still resolves below, and `axios`, which `@apple/apple-ads-platform` pins exactly below its patched release. Drop an entry the moment its parent ships the fixed range, and validate any new one against `pnpm build`, `prisma validate` and a from-scratch `prisma migrate deploy` before committing it.
- The `MINT_VERSION` default in `scripts/mint.sh`, which every local and CI Mintlify run goes through, `VALE_VERSION` in `.github/workflows/docs.yml`, `MCP_PUBLISHER_VERSION` in `.github/workflows/mcp-registry-publish.yml` and `RCLONE_VERSION` and `AGE_VERSION` in the `backup-drill` job of `.github/workflows/ci.yml` are bumped by hand, all but the first together with the checksum beside them, as are the `cloudflared` pin in `docker-compose.tunnel.yml`, the `ASOBEAST_IMAGE_TAG` default in `docker-compose.pull.yml`, which tracks the current release, and the `mcr.microsoft.com/playwright` image tag of the `web-e2e` browser jobs in `ci.yml`, which `pnpm check:playwright-image` holds to the installed `@playwright/test` so a Dependabot bump of Playwright fails `checks` until the tag follows. Dependabot does not cover them, because `/docs` has no manifest by design, the root Compose files are outside its docker directories, a release binary fetched by a workflow is not an action and a container image named in a workflow is not a Dockerfile. CI fails any Compose service whose image floats on `latest`.
- Dependabot pull requests whose highest change is patch or minor merge on their own through `.github/workflows/dependabot-auto-merge.yml`, gated by the required checks on `main`. Majors travel in their own group and wait for a person. `pmOnFail: ignore` in `pnpm-workspace.yaml` keeps `pnpm-lock.yaml` a single YAML document, which Dependabot and the dependency graph need to read it; pnpm 12 would otherwise prepend a document recording its own version. ## Code organization & file size

Decompose by **responsibility**, not by syntactic kind. The target is fewer concepts per file — not fewer lines, and not more files.

- **Soft size budget:** source files ~400 lines, functions ~80 (api) / ~150 (web). ESLint warns past these — treat a warning as "find the seam," not "pad to the limit." Tests and owned `components/ui/*` primitives are exempt.
- **Extract when** code is reused across modules (lift to `@asobeast/shared`, a domain helper, or `lib/`), is a nameable responsibility (a suggestion engine, a spider, a CSV exporter, an alert dispatcher), or is pure logic that deserves its own spec. This repo already does this well: `buckets.ts`, `extraction.ts`, `snapshot-diff.ts`, `visibility.ts`.
- **Colocate when** code is used in exactly one place. Do **not** create dumping-ground `const.ts` / `types.ts` / `utils.ts` files — a constant or type used once lives next to its use. (Contract types shared with the web are the exception: they live in `@asobeast/shared/contracts`.)
- **Oversized NestJS service?** Split into several focused providers inside the same feature module (the idiomatic fix), not one mega-class. Keep controllers thin, services single-responsibility, pure functions in their own unit-tested modules.
- **Oversized React component?** Extract sub-components, column/config definitions and pure formatters into the same feature folder; keep the component as the assembly. Colocation inside the feature folder beats a distant shared folder.
- A large but **cohesive** module of small pure functions (e.g. `audit-checks.ts`) is fine — do not shatter it to hit a line count. Relocating complexity is not reducing it.
- **`max-params` warns on NestJS DI constructors and those warnings are accepted, not acted on.** ESLint cannot exempt constructors, so the rule reports them; constructor injection is named, container-resolved wiring rather than a positional argument list, and a facade that exists only to shrink the count is churn. Treat a long DI constructor as a hint the provider does too much and answer it by splitting the provider — never by grouping its dependencies to silence the warning.
- **Refactor is separate from features:** a structure change and a behavior change are two commits (ideally two branches). Refactors preserve behavior — existing tests pass unchanged (unit specs may be _relocated_ with their code; assertions stay identical, e2e stays green).

## Shared code rules (monorepo discipline)

1. **Contract types live in `@asobeast/shared`.** Any request or response shape the frontend consumes is defined there (for example `AppListItem`, `TrackedKeywordItem`, `AppSummary`, `RankingSeries`, `ApiErrorEnvelope`). API DTO classes implement these interfaces (`implements X` or `satisfies`); the web app types its fetch calls with them. **Prisma generated types never cross the `apps/api` boundary.**
2. `@asobeast/shared` also owns the `Store` string union (`'APP_STORE' | 'GOOGLE_PLAY'`, values identical to the Prisma enum), the store URL parser, and normalization helpers reused by both apps. It must stay dependency light and runtime agnostic: no Nest, no Next, no Node only APIs.
3. `@asobeast/shared` is a **compiled package** (tsup, cjs + esm + dts). Do not switch it to raw TS exports; NestJS's CommonJS build cannot consume just in time TS packages cleanly.
4. Internal dependencies use `"@asobeast/shared": "workspace:*"`. Turborepo's `build` task has `"dependsOn": ["^build"]`, so consumers always see fresh output; `pnpm dev` keeps tsup in watch mode.
5. Never import across packages by relative path.
6. `apps/mcp` is a **consumer like the web app**: it talks to the API only over HTTP and types every call with `@asobeast/shared`. No Prisma, Nest or scraper imports.
7. **`@asobeast/mcp-tools` owns the tool catalog.** `MCP_TOOLS` (reads) and `MCP_WRITE_TOOLS` (writes) are the single definition of the MCP surface: name, title, description, `z.object` input schema, and the route each tool wraps (a `GET` for a read tool; a method, a path and a JSON body for a write tool, with its destructive, idempotent and open world hints and the `outcome` that shapes what an agent reads back). `toolsFor(scope)` decides what a connection lists, `requestOf` turns a tool into an HTTP request, `annotationsOf` produces its annotations, and both transports call those and nothing else: `apps/mcp/src/tools/` for stdio and `apps/api/src/mcp/remote-tools.ts` for `POST /mcp`. It depends on `@asobeast/shared` and `zod` and nothing else, and `parity.test.ts` proves the registration has not drifted.

## Frontend rules (apps/web)

1. **One transport, typed by shared.** The `src/lib/api/` module is the only place that talks to the API — a barrel over one file per domain, with `client.ts` owning `apiFetch`/`ApiError`/`withQuery` and one function per endpoint, every call typed by an `@asobeast/shared` contract. Never redefine a response shape locally and never import Prisma types. The proxy, `src/lib/api/proxy.ts`, is also the only place a request body is read: `readBoundedBody` (`src/lib/api/request-body.ts`) refuses a body larger than `REQUEST_BODY_LIMIT_BYTES` (the 100 KB the API reads, exported by `@asobeast/shared`), counted as received and so before any `Content-Encoding` is decoded, with a `413` envelope and `Connection: close`, by its declared `Content-Length` or as soon as a chunked stream passes the limit, and cancels the rest of the stream instead of buffering it. `FORWARDED_HEADERS` carries `content-encoding` and the proxy never decodes a body, so the API decodes a gzip, deflate or br body itself, applies its limit to the decoded size and answers `415` for any other encoding. `src/proxy.ts` does not match `/api`, `/docs`, `/metrics` or `/admin/queues`, so Next's `proxyClientMaxBodySize`, which truncates instead of refusing, never applies to them, with one narrow exception: a second matcher entry runs it for `/api/backend`, `/docs`, `/admin/queues` and `/.well-known` paths that carry an escape that can fail to decode (a `%` not followed by two hex digits, or the escape of a byte above `%7F`), because Next answers a bare `500` when it cannot decode a dynamic segment and only the proxy runs before that decode. There `lib/api/malformed-path.ts` refuses an undecodable path (the `400` envelope under `/api/backend`, the hidden `404` for the other three, a rewrite to the not found page for an app page, which is refused before the sign in redirect) and passes a decodable one through untouched. A third entry runs it for every path when the request carries `Next-Action`, which it answers with the `404` Next gives an unknown action, because the app defines no server actions; `next.config.ts` caps `experimental.proxyClientMaxBodySize` at `REQUEST_BODY_LIMIT_BYTES`, so a body the proxy refuses is buffered no further than the API would read; on those paths alone Next buffers a body up to its `proxyClientMaxBodySize` before `readBoundedBody` refuses it, so an ordinary escape such as `%20` never runs the proxy; a handler never calls `request.text()`, `request.json()` or `request.arrayBuffer()` on an unbounded body.
2. **The query cache owns freshness.** `src/lib/queries.ts` holds the `appKeys` hierarchy, the `queryOptions` factories and the mutation invalidation helpers (`invalidateKeywordMutation`, `invalidateCompetitorMutation`, …) — the single place invalidation sets are written down; `invalidateStoreConnectionMutation` refreshes the connections and every funnel query. Pages prefetch into a shared `getQueryClient()` and render a `HydrationBoundary`; client feature components use `useSuspenseQuery`/`useMutation`. **`router.refresh()` is banned** — after a mutation, invalidate or seed the cache. A query a page starts with `void prefetchQuery` streams as a pending promise, so inside that page's `HydrationBoundary` it is read only with `useSuspenseQuery` under a local `Suspense` boundary; a query whose value decides whether an element exists, or whose `dataUpdatedAt` a relative time is rendered against, is awaited by the page so the server render and the hydration render read the same cache entry, or the same absence of one. A query that spends a store allowance (the search, similar and developer suggestions, the competitor suggestions) is keyed outside `appKeys.detail(id)`, because that prefix is invalidated whole by a competitor change, a listing refresh and every run stage; it is stale for a day and never retried, and the local suggestion sources share the `appKeys.suggestionsRoot(id)` root and are invalidated with the app by `invalidateLocalSuggestions`.
3. **URL is the state.** Sort, date-range presets, selected keyword ids and filters live in `searchParams` via `nuqs` parsers in `src/lib/search-params.ts` (built from shared unions). No duplicate `useState` for view state. The keywords table remembers the last sort its viewer chose: `useUrlSorting`'s `remember` option keeps it under `asobeast.sort.keywords` in local storage (pure helpers beside the rest of `lib/table/sorting.ts`, validated against the table's columns) and applies it when the URL names neither `sort` nor `dir` (a bare `dir` names the default sort's direction), so an explicit param wins and the default (`KEYWORD_DEFAULT_SORT`, `opportunity`) never enters the URL; `keywordSortParser` is nullable for exactly that reason. The Action Center filters, groups and searches in the browser over the status-scoped list, and the open action lives in `?action=`; its bulk selection is one deliberate exception, because it is transient input to a single mutation and is cleared after it, so it lives in component state. The keyword import dialog's status filter is another: it filters a review that exists only while the dialog holds a file, and closing the dialog discards both, so it lives in component state too. The save dialog's market checkboxes on the metadata page are the third: they are transient input to one save and are discarded when the dialog closes, so they live in component state, while the open localization lives in `?fieldLocale=`. The setup step's suggested market ticks and seed choices are the fourth, and the keyword picker's tab and ticks in the same setup are the fifth, as are the suggested competitor ticks in the same step and the text, store and storefront of the import dialog, for the same reason: each is transient input to one add and are cleared after it, so they live in component state, while the selected countries and the skipped steps stay in the app's setup record on the server (`GET` and `PATCH /apps/{id}/setup`), read through `setupOptions` and written with an optimistic patch. The Google Play connect dialog's choice between signing in with Google and a service account key is another: it picks the fields of one submission and closing the dialog discards it, so it lives in component state. The trending panel's kind and list tabs on the top charts page are a sixth: they pick which of the loaded charts to show and discard nothing, so they live in component state. On the reviews page `score`, `version`, `since`, `replyState`, `sort`, `q` and the open composer `reply` live in the URL, and pressing the **Needs reply** tile also sets `sort=lowest`; the composer's text while typing, the tone and the instruction line, the raised limit of **Show all** (a search raises it too) and whether a card shows its kept translation are the seventh exception, each transient input to one request or a per card toggle that discards nothing, so they live in component state. A translation is seeded into every cached list with `seedReviewTranslation` instead of refetching. A reply save updates the badge and moves the counts in the cached lists (`withReviewReply`, `lib/review-reply-cache.ts`) and marks them stale without refetching, so the open composer stays on screen under a reply state filter it no longer matches. On the app overview `?market=` also scopes the keyword numbers: `keywordScope` (`lib/market.ts`) turns it into the optional `country` of the summary and both histories, no market, one without a listing or an app with a single listing counts every market, and the cards read it through `useKeywordScope`, which defers it with `useDeferredValue` so the previous numbers stay on screen while the next market loads. Which sections of a page are collapsed is a per viewer preference, so it is in neither the URL, which would put it in a shared link, nor component state, which the server render cannot read: the `asobeast_collapsed` cookie holds the collapsed section ids (`lib/collapsed-sections.ts`, page scoped ids such as `competitors.discovery`, declared once beside the page's components and parsed against that list), the page reads it with `cookies()` and hands the ids to `CollapsedSectionsProvider`, and a section is a `CollapsibleCard` (`components/layout/CollapsibleCard.tsx`): its title is the trigger, inside an `h2`, its header controls stay visible while it is collapsed and its content is not mounted, so a collapsed section starts no request of its own. Its content animates open only after the viewer toggles the section, because a section that streams in open would otherwise be drawn at its header height first and shift the page. A cookie, not `localStorage`, because only a cookie lets the server render a collapsed section collapsed and skip what it would fetch; a second page that adopts the cookie passes the union of every page's ids as `known`, or a write would drop the other page's. The keyword breakdown of the comparison matrix lives in `?keyword=`, the way the top 10 sheet of the keywords page lives in `?serp=`.
4. **Boundaries per section.** Every route segment has `loading.tsx` (geometry-matched skeleton) and `error.tsx` (shared `ErrorState`, whose **Try again** resets the failed queries with `useQueryErrorResetBoundary`, refetches every query still in error, mounted or not, with `refetchFailedQueries` (`lib/queries.ts`), which is how the shell's own reads recover because the layout never remounts and how the page's reader finds a fetch in flight when it remounts even after a shell component that mounted first cleared the reset flag, and then calls the boundary's `retry` prop, because a `useSuspenseQuery` that failed in the browser stays in its error state and throws again without fetching until it is reset, and the reset reaches only a read that mounts before the flag is cleared; a new boundary renders `ErrorState` and nothing else); every `useSuspenseQuery` consumer sits under a local `Suspense` boundary, not the whole page. A section the page can do without, such as the review themes strip, reads with `useQuery` and renders `InlineQueryError` (`components/layout`) when it has no data and the request failed, so one secondary request never replaces the page with the segment `error.tsx`; a section the page cannot show without its data keeps `useSuspenseQuery` under its `Suspense`, except inside a dialog, sheet or popover opened on demand (the top 10 sheet, the keyword breakdown sheet), which always reads with `useQuery` and `InlineQueryError`: Radix mounts portal content one render after the segment's retry, when a mounting query hook has already cleared the error reset flag, so **Try again** on a `useSuspenseQuery` there refetches nothing and the page stays on its error.
5. **Domain rendering.** Position is 1-based; `null` means "checked, not found within the captured depth" → render `>100` or `>200` from the row's depth, never `0`. A comparison row lists the apps it has no check for in `unchecked` (the primary app and competitors, absent means every app was checked), and the matrix draws each as a dash named **Not checked yet** and exports it as an empty cell, never as `>200`. Ranking charts use a reversed Y axis (1 on top) on a square root scale (`RANK_AXIS_PROPS` in `components/charts/theme.ts`), so the top 3, top 10 and top 25 bands are tall enough for their labels, and a band label (`RankBandLabel`) is drawn only when its band is at least 14 px tall. `buildRankingChart(series, through)` puts every UTC day from the first check to `through` minus `CHECK_FRESH_DAYS` (or to the last check when later) on the axis, so a day without a check is a gap with no marker, a ranked day between two gaps is a dot (`loneKey`), the tooltip takes `filterNull={false}` so it opens on a day where every value is `null` and reads **Not checked** for a keyword with no check that day, and the empty and insufficient states, **Export CSV** and the CSV rows count checked days only (`checkedDays`, `hasCheck`). Dates are UTC `date` strings formatted with `Intl.DateTimeFormat` pinned to UTC. A date time and a storefront name never come from the engine's own wording, meaning any `Intl.DateTimeFormat` that joins a date with a time (WebKit inserts `at` for `dateStyle` plus `timeStyle` and for explicit hour and minute components alike) and `Intl.DisplayNames`: WebKit, Chromium and Node word them differently and React rejects the mismatch as #418. `formatDateTime` writes the clock itself and `formatCountry` reads `COUNTRY_NAMES`, which `country-names.test.ts` keeps in step with `@asobeast/shared`; `e2e/engine-hydration.spec.ts` runs the route sweep in WebKit. A store price is written by `formatPrice(value, currency)` in the currency the storefront sold it in, pinned to `en-US` and to the fraction digits `format.ts` names per currency, because WebKit's currency data disagrees with Node's for HUF, IDR, COP, PKR and others: the API reads `currency` from the stored raw payload (`currencyOf`, an ISO 4217 code on the snapshot summary, the refresh answer and every `price` change event) and a missing one prints the bare number, never a `$`; `formatUsd` is only for amounts asobeast itself reports in dollars. Traffic/difficulty/opportunity are 0–100 scores. `refresh` returns a snapshot diff to show; `run-daily` and `score` return 202 queued — toast "queued" and let the cache refetch. A keyword that is active and never checked (`latestDepth === null`) renders **Checking…** and the keywords list polls every fifteen seconds for at most forty fetches while such a row exists (`lib/keyword-checks.ts`); a never checked paused row keeps the dash. An active keyword whose `latestCheckedOn` is older than yesterday UTC (`isCheckFresh` and `CHECK_FRESH_DAYS` in `@asobeast/shared`, the rule the position streak reads too) keeps the position cell to its number and swaps the icon of its **Position facts** `InfoTip` for a clock (`staleCheckDay` in `lib/keyword-checks.ts`, the wording in `components/keywords/stale-check.ts`), whose name ends with the day of the last check and whose popover opens with it, and hides the daily delta chip; "today" is the UTC day of the keywords query's `dataUpdatedAt`, never the browser clock, so the server render and hydration agree, and a paused row or a row without the field shows no day. `PageActions` renders **Refresh**, **Run daily** and `RunProgress` only once the app's detail is in the query cache (`useCachedQueryData`; the app layout hydrates it and an unknown id never does), so an unknown app offers no action and sends no run status request. `RunProgress` in `PageActions` polls `GET /apps/{id}/run-status` every ten seconds while `state` is `running` and the run is not paused (`paused` with a state other than `complete` hides the pill and stops the polling) (`lib/run-progress.ts`) and invalidates the app's queries when a stage advances. The top charts view defers its request with `useDeferredValue` and, while the shown chart is not the requested one, keeps it on screen under `ChartPending`, a status pill naming the requested store and country, fixed at the bottom of the viewport so it never covers a toolbar and takes no space in the layout.
6. **Theming & a11y.** shadcn primitives live in `components/ui` (owned, editable); dark mode via `next-themes` class strategy. Icon-only buttons carry `aria-label`, dialogs carry a description and every popover an accessible name (`aria-label` or `aria-labelledby` on its `PopoverContent`; `e2e/popover-names.spec.ts` opens each one under axe), focus never falls to `body` (a control that changes the URL stays mounted with no remounting `key`, a dialog opened from a button is driven by a trigger so Radix restores focus, and an opener replaced by another control hands focus to its replacement), tables carry a caption, a table whose cells hold no link or button and that can scroll sideways is a named focusable region while it overflows (`scrollLabel` with `scrollFocus="overflow"` on `Table`, measured by `lib/scroll-overflow.ts`; `e2e/structural-a11y.spec.ts` lists the routes at 375 px), charts keep `accessibilityLayer`, and colour is never the only signal. A control that starts a request stays focusable while it runs: it takes `aria-disabled` with a guard in `onClick` or `useSingleFlight`, and the base `Button` dims it, never `disabled`, because a disabled control drops focus to `body`. `e2e/request-focus.spec.ts` holds each such control's answer with `holdRequest` (`e2e/held-request.mts`), presses it from the keyboard and asserts focus stays on it while the request runs and after, and closes each confirmation dialog with Escape and Cancel and asserts focus is back on its opener or on the survivor its removal chose; a new control or dialog of that kind adds its row there. When a request removes or replaces the focused control, `lib/focus-handoff.ts` hands focus to a survivor and does so only if the user has not moved it: `useFocusAfterCommit` focuses an element chosen before the commit, after the commit that removed the control (the Action Center bulk bar, the followed charts list), `useCloseFocusHandoff` gives a confirmation dialog's `onCloseAutoFocus` the survivor a confirmed removal chose, usually `siblingControl` of the removed row and otherwise `cardAction`, the card's header button (the alert rows, the competitor cards, the API tokens), `returnFocusTo` returns focus to an opener that is not the dialog's trigger (the snapshot diff after Refresh, the switcher's Import app), `survivingNeighbour` picks the survivor, and `armFocusHandoff` with `useFocusClaim` lets the replacement that mounts later take focus (the follow button, the competitor badge of a chart row, whose cell remounts when the page data changes), and `useFocusGroupClaim` hands focus to the first link or enabled button left in a group when its control leaves while the group stays mounted or mounts without it (the **Capture today** button of a chart column, which hands focus to **Open table**, and of the table actions, which hand it to the follow button; the activation arms `captureFocusKey`). A confirmation dialog that leaves its trigger disabled or replaced decides the target in `onCloseAutoFocus`, as `FollowChartButton` and the reply composer do. A button that a list repeats for each row (the **Reply**, **Translate** and **Show more** of a review card) carries an `aria-label` that begins with its visible text and names its row (`reviewActionLabel` in `components/reviews/review-subject.ts`), and the repeated container is named too, so a button list and voice control can tell the rows apart; rows whose names would be equal (the same stars, author and day) add their position among them, `(2 of 3)`, from `reviewTwins`, and only those rows do, so a unique name never changes. A button whose visible text several views share, **Export CSV** above all, is an `ExportCsvButton` (`components/ExportCsvButton.tsx`): the visible words stay at the start of its name and its subject follows as visually hidden text, never as an `aria-label` that rewords it, because WCAG 2.5.3 Label in Name needs the visible words inside the name; `e2e/export-csv-names.spec.ts` lists the pages. A metric explanation is an `InfoTip` (`components/ui/info-tip.tsx`), an icon button that opens a named and described popover on click, tap or keyboard, never a hover `Tooltip`, because it links to the documentation and must open on touch; a view shows one per metric, beside its label, or once in the header or toolbar of a section whose cards or tiles repeat the metric. A label never sits as a bare text node beside an icon or spinner that a render inserts or swaps, because a browser translator replaces the page's text nodes and React's `insertBefore` against a replaced node throws `NotFoundError`, which the segment's `error.tsx` then shows instead of the page: the base `Button` puts each run of text children in one `<span>` holding one string, the slotted child of `asChild` included, so a changed label is written whole, and a native control with such an icon wraps its label in a `<span>` itself (`e2e/translated-page.spec.ts` replaces every text node the way a translator does and presses each such control). A screenshot thumbnail (`ScreenshotThumb`) is drawn at a fixed height with `width: auto` and `object-contain`, never cropped, because the caption is printed at the top. A tab strip that switches a source without rendering a `TabsContent` uses `TabsOption`, never `TabsTrigger`, so no `aria-controls` names a missing id; `e2e/structural-a11y.spec.ts` lists the routes and the dialog it covers. The header's action group is fixed width, so nothing in it may depend on data below `sm`: the health badge shows only its mark there (its words are `sr-only sm:not-sr-only`), and because colour is never the only signal each state has its own mark, a dot while healthy or checking, a triangle degraded and a crossed circle unreachable. Degraded with "API up · database unavailable" is reserved for the API's own 503 on `/health` (`answeredDatabaseDown` in `components/layout/health-answer.ts`); every other failed poll, the web proxy's 502 and 504 included, reads unreachable, because only the API's own answer proves the API is up; the poll never retries (`retry: false` on `healthOptions`), because each retry of a hung API waits a full proxy timeout and the next poll is the retry; `e2e/operator-status.spec.ts` drives the real proxy for both gateway answers. `e2e/header-narrow.spec.ts` holds `scrollWidth <= innerWidth` at 320 and 375 px with every health state. Text a store user wrote (a review's title, text, developer reply, the owner's reply field) carries `dir="auto"` and its author sits in a `<bdi>`, because the page is left to right and a right to left review is laid out right to left only when told to; the text block fills its row so `text-align: start` is the right edge, and the card chrome around it stays left to right. `e2e/review-direction.spec.ts` pins it.
7. **The shell is a sidebar, and page width is a per-page decision.** `(app)` routes render inside `SidebarProvider` + `SidebarInset`; `(auth)` routes (`/login`, `/register`, `/upgrade`) render a centered card with no sidebar. Of those only `/login` and `/register` are public (`PUBLIC_ROUTES`): `/upgrade` needs a session, because every action and read on it does. A visit without a session cookie is redirected by `src/proxy.ts` to `/login?next=%2Fupgrade`, a stale cookie is moved there by the server render, because `src/proxy.ts` forwards the requested path in `x-asobeast-requested-path` and `apiFetch` calls `redirect` to `signInTarget(...)` when a server render is refused with 401 (`lib/api/server-session.ts`, swept over every signed in route by `e2e/stale-session.spec.ts`), and by `useSignedOutRedirect` once `/auth/status` answers when a cookie goes stale while a page is open, sign in returns to `/upgrade` (`signedInDestination`), and a 402 on `/upgrade` never redirects the page to itself. The page's queries wait for `useAuth().authenticated`. Route groups keep every URL unchanged. Each page picks one of three width utilities from `src/styles/layout.css`: `page-full` for tables and charts that want every pixel (keywords, rankings, competitors, top charts), `page-wide` for dashboards and grids at a 1600 px ceiling (portfolio, overview, actions, changes, reviews, metadata, and the whole `/admin` area), and `page-reading` at 720 px for prose and forms (settings, integrations, audit, setup). Gutters come from `page-gutter`, which folds `env(safe-area-inset-*)` into the density scale — never per-page padding. The dashboard lays out by its own width through `@container/dashboard`, because the collapsible sidebar makes the viewport a poor proxy for the content box. The metadata page does the same through `@container/metadata`. A grid whose columns depend on the content box beside the sidebar uses a container query, as these two pages do, and its cards carry `min-w-0` so a long badge or token wraps instead of widening the page; user supplied text in a flex item or a shrink to fit column takes `wrap-anywhere`, because `break-words` leaves the box as wide as its longest word.
8. **Charts go through the chart system.** `src/components/charts/theme.ts` owns axes, grid, margins, heights, the series palette and the stroke-pattern order; no chart configures those inline and no chart references `--chart-N` directly. Multi-series charts distinguish series by stroke pattern as well as colour, and every chart has loading, empty and insufficient (fewer than four points) states at its real height. A control that changes the key of a query a mounted chart reads defers it with `useDeferredValue` (the range tabs of the overview cards and of the ratings history on the reviews page), because a `Suspense` boundary that suspends again hides what it shows with `display: none` unless the update is deferred, and Recharts then measures the container as 0 by 0 and logs a size warning on every render until the data lands.
9. **Tables go through the table kit, and judged numbers go through the grade scale.** A data table is a `@tanstack/react-table` v9 instance assembled from `components/data-table/` (sortable header, search, facet, chips, column menu, filtered empty state) with its pure logic in `lib/table/`; sorting and filtering happen in the browser and live in the URL through `search-params.ts`, and column visibility, like the keywords table's remembered sort (rule 3), is a per viewer preference kept in local storage, the other being which sections of a page are collapsed, which is a cookie because the server render reads it (rule 3). A score, a position, a rating or a coverage share is graded by `lib/grade.ts` into strong, fair, weak or poor, rendered by `components/ui/graded.tsx`, and always carries the word as well as the colour. `--rank-band-*` and `--score-*` stay for charts that show a distribution.
10. **Orange is action, blue is information, status keeps its own hues.** `--primary` is the landing orange (`--brand-500`) in both themes with dark ink text (`--primary-foreground`, 8.67:1) and darkens to `--primary-hover` on hover; it fills controls and is never text on a surface, because it is 2.1:1 on the light background and reads as `--warning` in either theme. A link styled button is the text colour with a `decoration-primary` underline, an informational badge uses `--info` (blue), and a meter that reports a level uses the status tokens, never `primary`. A view shows one `default` button per independent task: a trigger that opens a dialog is `outline`, the dialog's submit is `default`, and a per row action is `secondary` or `outline`. The filled button's focus ring is solid and offset from its fill; other controls keep their own focus indicator. The active sidebar item tints its icon with `--sidebar-primary`, which is the deeper `--brand-700` in the light theme so the icon clears 3:1 on the active row. `TEXT_PAIRS` in `components/tokens/token-groups.ts` lists every pair the theme promises, status text on `--muted` and on its own tint included, and `tokens.test.ts` measures them in whole sRGB bytes, as the browser renders them. A `-subtle` tint is opaque, mixed with `--card`, so a badge or a sticky cell on a tinted row never paints the tint twice. Text takes a token colour, never an opacity modifier (`styles/utility-classes.test.ts`), and a paused or secondary row mutes its text with `--muted-foreground` instead of `opacity`. `e2e/contrast.spec.ts` runs axe `color-contrast` on every signed in and signed out route in both themes, with no exclusion. The product is written `AsoBeast` in interface text (`PRODUCT_NAME` in `lib/brand.ts` where the string is the name itself) and stays lowercase in every technical identifier; `lib/brand.test.ts` enforces it.

## Domain rules that are easy to get wrong

1. **Both stores are live.** The Prisma enum, shared `Store` union and URL parser cover App Store and Google Play, and `SUPPORTED_STORES` lists both. Play search indexes **title (30), short description (80) and long description (4000)** — there is no subtitle and no keyword field, so those two stay Apple-only concepts everywhere (types, lints, audit weight 0, hidden in the web). Play's indexed 80-char short description (`summary`) is its equivalent surface: it is auto-tracked (`DESCRIPTION` source), linted (`lintShortDescription`) and coverage-checked. The 501 `StoreNotSupportedError` path stays wired for any _future_ store, not for Play.
2. **The iOS keyword field (100 chars) is private, and there is one per App Store localization, edited in one place.** It never appears on the store page and cannot be scraped; the owner types it on the metadata page (source `KEYWORD_FIELD`). It is counted in characters, the way App Store Connect counts it, with `keywordFieldChars` against `KEYWORD_FIELD_CHAR_LIMIT`, the same `countChars` the title and subtitle use, so a letter such as ą or a Chinese, Japanese or Korean character counts once. The 100 character cap on one tracked phrase (`TRACKED_KEYWORD_CHAR_LIMIT`) is counted in characters too: `checkKeywordText` and the listing combinations use `countChars`, and the `track_keywords` tool relies on zod, which measures a string's `max` in code points. `countChars` counts Unicode code points and `truncateChars` cuts by the same unit, both in `packages/shared/src/aso/limits.ts`, so a Han character outside the Basic Multilingual Plane such as 𠮷 counts once and an emoji sequence counts by its parts; a store field is never measured with `String.length` or cut with `String.slice`, and never counted in grapheme clusters, because `Intl.Segmenter` answers differently in Node, Chromium and WebKit. `countMaxLengthChars` stays the count `class-validator`'s `MaxLength` uses and is not a store limit. `KeywordField` (tenant owned, RLS, `@@id([appId, localization])`, explicit localization tags, never `NULL`) stores the normalized phrases in submission order, and is the only source of truth: a tracked keyword is in a keyword field when a saved field of a localization its market reads (`keywordFieldLocalizations` in `@asobeast/shared`, which answers English (U.K.) for a home country an older release imported without checking it is a storefront) holds its normalized text, which `indexKeywordFields` in `keywords/keyword-field-index.ts` answers and `reportedSource` reports. Never store membership on `TrackedKeyword` again. **What an app ships is `AppLocalization`** (tenant owned, RLS, `@@id([appId, localization])`, `origin` `manual` or `detected` as text validated in code): the home localization (`homeLocalization`, never stored, never removable), plus its rows, plus any localization with a saved field, joined in one place, `AppLocalizationsService.list`. **I-FIELD:** a non empty save of a localization other than the home one upserts its row as `manual` inside the save transaction through `recordAppLocalizations`, never downgrading `detected`; an emptied field keeps its row and only `DELETE /apps/{id}/localizations/{localization}` removes one. **Every save goes through `KeywordFieldWriter`**, the one transaction (`QuotaService.admitKeywordMarkets` first, which takes the quota lock, then the per app field lock) that stores the phrases, records the localization, tracks every phrase in every market of `trackIn`, and stops tracking a dropped phrase as `KEYWORD_FIELD` in every market that reads the localization unless another field read there holds it; `remove` is the same transaction with an empty field and the row deleted. `trackIn` is a subset of the app's markets (`appMarkets`: home first, then every country in which the app tracks a keyword, active or paused) whose storefront reads the localization (`trackInError`), and may be empty; untracking a keyword never edits a field. The pure rules live in `keywords/localization-markets.ts` (`readsKeywordField`, `readerRole`, `readersOf`), `keyword-field-save-plan.ts` and `market-keyword-fields.ts`; a preview computes them and writes nothing. The editor exists on the metadata page only. The keywords page reports through `GET /apps/{id}/keyword-fields/market` and never writes a field, and the words read twice and split phrases it shows are diagnostics that never reach coverage, the audit or an Action Center rule. `GET` and `PUT /apps/{id}/keyword-field` without a query still mean the home storefront's default localization, which is where the upgrade put every field saved before; `PUT` calls the writer with `trackIn = [country]` and answers as before.
3. **Rate limits.** The iTunes endpoints informally tolerate roughly 20 requests per minute per IP; the `appstore` worker runs concurrency 1 with a limiter from `SCRAPE_ITUNES_RPM` (default 15). Google Play is more sensitive: the `gplay` worker runs concurrency 1 with a limiter from `SCRAPE_GPLAY_RPM` (default 10) that spaces **job starts**. A Play score job fans out to 12–20 sequential requests (1 search + 1–9 suggest-reach probes + 10 detail `getApp` enrichments) and an App Store score job to 3–11 (1 search + 1–9 probes + 1 continuation lookup), while a depth-200 Play rank job uses roughly eight requests versus one for Apple. Never call store endpoints in bulk outside the queue (the only exceptions: small, user initiated lookups, meaning keyword suggestions, a name search and a similar apps lookup, each bounded by an hourly allowance).
4. **One app, per-market keyword tracking; one search serves everyone, including across tenants.** `Keyword`, `KeywordMetric` and `SerpEntry` are **global** and carry no policy: two workspaces tracking "habit tracker" in the US share one search rather than paying for two, which is the entire efficiency argument for the shared keyword row and is worth far more under multi-tenancy than under one tenant. What is tenant-owned is the **tracking relation** and the recorded position, so `checkKeyword` reads its trackers through the escape hatch, asks `CollectionEligibility` which of the owning workspaces may still be collected for, and then writes rankings and fires alerts inside each of those. The gate matters because the search is shared: without it a workspace that is suspended, unentitled or past its keyword limit keeps receiving fresh rows whenever another tenant happens to schedule the same phrase. Quota counts keyword-market pairs tracked by a workspace, never global keyword rows. An app is a single row; countries live on keyword tracking (`Keyword` is scoped by `text, store, country`), so a single app owns keywords across storefronts, added and filtered per market on the keyword monitor. `checkKeyword` searches `keyword.country` (not `app.country`) and records positions for the primary app and all its competitors in that storefront from one search — never one search per app. The same phrase tracked in two markets is two keyword rows checked by two searches; rankings differ per storefront. Each added market multiplies daily search volume against the same `SCRAPE_ITUNES_RPM` budget; `GET /jobs/budget` estimates the fan-out and the settings budget card surfaces it. A market is suggested, never guessed: `GET /apps/{id}/market-suggestions` (`MarketSuggestionsService`) joins the languages the newest home snapshot declares (`extractRawFacts(...).languages`, normalized by `declaredLanguage` in `@asobeast/shared`) with `storefrontsForLanguages`, which answers the first localization in a storefront's read order whose language is declared, with its role; English is never suggested, the home market is left out and a Google Play or competitor app answers an empty list. `POST /apps/{id}/market-seed` seeds one market through `MarketSeedService`: it captures the market listing with `refreshListing`, extracts `seedCandidates` (`keywords/listing-seed.ts`, the same `TITLE` and `SUBTITLE` sources, Play `TITLE` and `DESCRIPTION`, and `MARKET_SEED_LIMIT` the home import uses through `syncFromSnapshot`, reading the shipped localizations the storefront captures beside the native ones), leaves a phrase the app already tracks there, active or paused, as it is, plans the rest against the plan's keyword room with `planSeed` inside `admitKeywordMarkets`, reports what does not fit as `skipped` and never answers 403, and hands the new rows to `FirstPositionChecks.schedule`, then `enqueueFirstScores`, then `MarketListingRequests.request`. Every path that starts tracking a keyword (a manual add, an import, a seed and `KeywordFieldWriter.announce`) queues the first position check before the first score, because the store queues are FIFO at concurrency 1 and a score costs 3 to 11 requests where a check costs one; the writer checks only the keywords its save activated. A storefront without a listing of the app answers `unavailable` and writes nothing. The first capture of a market listing for a primary app asks `LocalizationDetection.request` without spending, with that market added to the markets it probes, `CRON_LOCALIZATION_SWEEP` repeats the request weekly for every primary App Store app of the workspaces the daily run collects for through `LocalizationSweep` (`jobs/`), and `LocalizedListingCapture` reads `capturedLocalizations(market, shipped)` (`apps/market-localizations.ts`), the native localizations plus every shipped localization the storefront reads besides its default (`shippedLocalizations`, which always counts the home localization), for a primary app only, which `localizationReads` counts in the budget. `latestLocalizedTexts` and the listing market switcher read the captured localizations a market still captures, so a localization the app stopped shipping is no longer judged; `listingTexts` stays native only for the home auto tracking. Category ranks, reviews, the ratings history and auto-tracked keywords stay on the home market. Top charts are read for any storefront through `GET /charts`, and `checkCategory` records its positions from the same `ChartCapture` the page reads. The listing is per market: `AppSnapshot.country` and `ChangeEvent.country` are nullable and `NULL` is the home storefront, `apps/api/src/apps/listing.ts` is the only place that says so, and every read of `appSnapshot` or `changeEvent` carries `HOME_LISTING`, `HOME_EVENTS` or a market filter from it (`listing-reads.guard.spec.ts` fails the build otherwise). A listing also has a localization: `AppSnapshot.localization` and `ChangeEvent.localization` are nullable, `NULL` is the storefront's default localization, and every helper in `listing.ts` scopes to it unless it is given a tag, so an existing read never sees a localized snapshot by accident; `eventsOfMarket` is the one helper that reads every localization of a market, for the changes timeline. For an App Store storefront whose default is English other than English (U.S.), `nativeLocalizations(country)` in `@asobeast/shared` names the native localizations it also reads; `LocalizedListingCapture` asks for each right after the default listing is captured, stores it only when the store serves one (`servesLocalization`) or one was stored before, records its changes without an alert and its screenshots in its own language, and a failure of one never fails the default capture. The first native snapshot a capture stores also records its localization as `detected` through `recordAppLocalizations` (later captures record nothing, so a removal sticks until detection runs). Every capture of a market listing for a primary App Store app also records the market's default localization as `detected` when `provenDefaultLocalization` (`apps/market-default-localization.ts`) says the store serves it: the listing differs, by `servesLocalization`, from the newest home listing and from every additional localization `LocalizedListingCapture.capture` read in that market during the same capture, which answers those listings and whether every lookup answered. `MarketLocalizationRecorder` runs after that capture, records nothing while a lookup failed, never records the home localization and never fails the capture. The default of a market is never a probe candidate, because the probe compares against the market's own default listing; a removed default comes back on the next capture that proves it. `POST /apps/{id}/localizations/detect` queues one deferred `DETECT_LOCALIZATION` job per candidate (`detectionCandidates`: a localization an app market reads that the app does not ship and whose language the home listing supports), which `LocalizationDetection.probe` answers with `getApp(…, localization)` and `servesLocalization`, recording `detected` only when the served text differs from both the probe market's default listing and the home listing, because a storefront answers a localization the app does not ship with its primary text, which is the home listing in another market. A localization whose text equals the default listing is invisible to both, and one whose text equals the home listing is invisible to the probe, which is why `manual` exists. Coverage judges a keyword within each localization of its market (`judgeFields`), the keyword field of each localization included (`judgingSurfaces` in `metadata/listing-surfaces.ts`; a market other than home gets a keyword field cell only once a field it reads is saved), auto tracking interleaves the home localizations native first, and `GET /jobs/budget` counts one read per localization `capturedLocalizations` names as `localizations`. The lookup and the product page take the localization in different formats (`app-store-languages.ts`); a malformed lookup `lang` is an HTTP 400, so the map is exhaustive and tested. A market is captured for the markets in which the primary app tracks keywords, for the app and its competitors, as the `REFRESH_APP` job with a `country`, counted in the `apps` stage and reported as `marketListings`; coverage and relevance judge a keyword against the listing of its own market and fall back to the home one.
5. **Opportunity is derived, never stored.** Traffic and difficulty persist in `KeywordMetric`; opportunity is computed in the read layer only, as `(min(volume, 30) / 30) ^ 1.25 * (100 - difficulty)` (`scoring/opportunity.ts`). It is the same for every app tracking the keyword; relevance is reported next to it and never multiplied in (`scoring/keyword-opportunity.ts`).
6. **Position semantics.** 1 based; `null` means "checked, not found within `depth`" (default 200). Store the row even when null.
7. **Tenancy is enforced by the database, not by remembering to filter.** Every tenant-owned table has a `tenant_isolation` policy reading `app.workspace_id`, and every Prisma operation runs in a transaction that calls `app_enter_workspace` and switches to the non-owner `asobeast_app` role — without that switch a superuser or the table owner bypasses the policies entirely. A query with no workspace in scope therefore returns nothing rather than everything, so **service code does not carry `workspaceId` in a `where` clause**; it resolves the workspace from `WorkspaceContext` when it writes, and lets the policies scope what it reads. Work that genuinely spans tenants — account resolution, the scheduled pipeline, retention, operator health — goes through `CrossTenantAccess`, whose one method demands a written justification. `DEFAULT_WORKSPACE_ID` is a bootstrap value; an ESLint rule fails the build if it reaches any other service. Migrations and the seed must run as a role that bypasses the policies (the superuser the images already use). State that outlives a request and is keyed by a tenant owned id, such as a single flight map, is keyed by `WorkspaceContext.require(...)` plus the id, because a map hit answers before any policy runs (`ActionsAiService`); a map consulted only after the row was read under the policies, as `AuditService.runAi` does, is equivalent. `AppSetup` (tenant owned, RLS, `@@id([appId])`) keeps the guided setup of a primary app; `status` and `skipped` are text validated in code against `SETUP_STATUSES` and `SETUP_STEPS`, and the portfolio answers its summary through `setupSummary` from `@asobeast/shared`. `PATCH /apps/{id}/setup` holds `selectedMarkets` to the storefronts of the app's store with `assertStorefront` in `AppSetupService.update` (never in the DTO, which does not know the store), refusing a code the setup does not already hold and that is not the app's home country with `400`, so a client that reads a list and writes it back never fails on an older entry.
8. **Scrapers break.** Parse failures fail the job (BullMQ retries with backoff) and must never take down request handling. A route that reaches a store while the client waits carries `@UseInterceptors(StoreDeadlineInterceptor)`: the providers hand its `AbortSignal` to the scraper and stop retrying once it passes, so the request answers the store's `502` within `ON_DEMAND_STORE_DEADLINE_MS` (20 s, below the MCP gateway's 25 s and the web proxy's 30 s) and the cancelled store call writes nothing afterwards. An answer that arrives after the deadline is discarded rather than stored, because the scrapers swallow a cut sub request; a proxy pool lease waits no longer than the deadline, a deadline abort never counts against an endpoint's health, and pool initialization runs outside the scope (`outsideStoreDeadline`). Queued work runs outside that scope and keeps its retries; an App Store attempt is still abandoned after 15 s, and an attempt cut by that bound is retried, never trusted. An app the store no longer lists is a fact, not a failure: `ListingCaptureService` turns a `StoreAppNotFoundError` in the home storefront into `App.delistedAt` (the first such answer, kept until the next home capture or import clears it), a queued refresh finishes on it in every market, `AppRunStatusService` expects no listing of a delisted app or competitor, a `StoreAppNotFoundError` in any other storefront adds that market to `App.unlistedMarkets` (removed by the next capture of that market, never `delistedAt`, because many apps are sold in some storefronts only) and `AppRunStatusService` expects no listing of that app in those markets, and the contract answers the optional `delistedAt` on the app detail, the app list, the competitor items and the portfolio.
9. **Authentication is mandatory, and self registration never joins a workspace that already holds data.** Every request is authenticated by `AuthGuard` (session cookie or `asob_` Bearer token) and then authorized by `EntitlementGuard`; `@Public()` is the only authentication bypass. **`AUTH_REGISTRATION_WORKSPACE` decides where a registration lands, and it defaults to `own` in every mode**: only the bootstrap owner joins `ws_default`, every later account gets its own workspace and owns it, and open registration is safe precisely because no two accounts share a workspace and the RLS policies scope every read. The `shared` value drops every sign up into `ws_default` as a `member` instead, and it is an explicit opt-in for an instance whose sign ups are all trusted with the data already there; it **refuses to boot** with `BILLING_ENABLED=true`, because hosted registration is open to strangers. Sharing a workspace with a teammate is what the invite flow in `workspace-team.service.ts` is for, never self registration, so do not re-tie the workspace decision to `BILLING_ENABLED`: a flag about payment must not decide who reads whose data. Registration decides that under a `pg_advisory_xact_lock`, creating the workspace and the user in one transaction, so concurrent first registrations cannot both bootstrap and a duplicate email cannot leave an orphan workspace. `BILLING_ENABLED` is also the premium seam — unentitled requests get **402**; entitlement and plan live on `Workspace` (`plan`, `trialEndsAt`, `planExpiresAt`, `billingCustomerId`, `subscriptionId`), never on `User`, because a workspace has one plan whatever the size of the team. Account and paywall routes stay reachable via `@AllowUnentitled()`, and an unentitled workspace keeps every session read and export while every write, every on-demand action and every `asob_` token request answers 402 — data is theirs, capacity is what they pay for. The per address count of rejected credentials (`CredentialRateLimiter`, 120 a minute, recorded by `CredentialResolver` for `AuthGuard` and the admin gate alike) is spent only after the credential has been looked up and refused, so an accepted credential is never counted or refused because of the address it arrives from, and a request with no client address, such as an in process MCP dispatch, is not counted. Only a credential that was looked up is counted: a session cookie that fails verification (`AuthService.verifySession`, another secret, expired or carrying no `jti`) and an `Authorization` header without an `asob_` token (`apiToken`) are answered 401 and never counted, because neither costs a lookup or can be guessed, so a browser signed out by an `AUTH_SECRET` rotation reaches the sign in page instead of a 429; a validly signed cookie whose session row is gone or whose session version is stale is looked up and counted like a refused token. Never gate an accepted credential on a bucket that more than one client can share; rejected ones still share the address bucket, so behind a web app at `TRUST_PROXY=0` every browser's rejections count as one client. An invitation link proves the invited mailbox only if it travelled by mail alone, so `POST /workspace/invites` hands the token back in `acceptPath` through `acceptPathFor` (`apps/api/src/auth/invite-link.ts`) and nowhere else: never after the email was sent, and after a failed send or without mail only when the instance cannot email or registration is closed; otherwise `acceptPath` is the bare `INVITE_PATH`. An owner who could read the token could accept their own invitation for a stranger's address, and that stranger's later password recovery would sign them in to the owner's workspace. Every session cookie names a `Session` row through its `jti`: the table is an operator table (`OPERATOR_TABLES`, `operator_only` policy, cascade from `User`) that is read and written only inside `CrossTenantAccess`, and `AuthService.userOfSession` accepts a cookie only while `SessionStore.find` returns an unexpired row of the claimed user whose `sessionVersion` still matches, in the one query that used to read the user. `POST /auth/logout` ends the caller's own row through `AuthService.endSession` before it clears the cookie and never touches another session, and the retention job removes expired rows. Changing or recovering a password ends every session through `sessionVersion`, deletes every `Session` row and every `ApiToken` of that user in the same transaction (`endSessions`, `revokeApiTokens`), because `resolveToken` never reads `sessionVersion` and a token minted during a briefly held session must not outlive the owner's recovery. A route that manages credentials, team membership or the workspace's deletion carries `@SessionOnly()`, enforced in `TokenScopeGuard` from `req.credential`: token creation and revocation, password change, deletion scheduling and cancel, invite creation and revocation, member removal, and posting and withdrawing a review reply answer 403 to every `asob_` token, write scope included, so a leaked agent token cannot mint a successor that outlives its own revocation or schedule the workspace's erasure. A new route of that kind takes the decorator, and the `token-scope` e2e fails if an MCP write tool ever wraps one. **A mailbox gets one trial, ever, not a workspace and not an address.** `mailboxOf` (`auth/mailbox-key.ts`) reduces an address to its mailbox (lowercase, the `+tag` dropped on every domain, dots dropped and `googlemail.com` folded into `gmail.com` for Gmail only), on top of `canonicalAddress` (`auth/canonical-address.ts`), which `isDisposableEmail` shares (NFKC, quotes around the local part removed, the domain's trailing dot dropped and a unicode domain read in its ASCII form) and `TrialClaims` stores an HMAC of it under `AUTH_SECRET` as a `TrialClaim` row, an operator table with no workspace and no foreign key, so it outlives the erasure of the workspace that took the trial and holds no address. A trial starts only when its claim is won: at confirmation where a confirmation email is sent, so nobody can use up a mailbox they cannot read, and at registration where none is, because nothing can prove the mailbox there. A claim exists only for a trial that started: `EmailVerificationService.writeTerms` gives the claim back when the guarded workspace write matches nothing. A lost claim, and any address on a domain `mailchecker` lists as disposable, still creates the account and signs it in, but starts no trial and logs a warning naming the address: `Workspace.trialDeclinedAt` records the refusal, `canStartTrial` reads it and `trialAwaitsConfirmation` is `false`. `normalizeEmail` and the stored login email do not change, the mailbox is only the trial key and the recipient key of the daily confirmation email allowance (rule 19). `TrialClaimBackfill` claims the owners of workspaces that already had a trial on boot, in the background through `registerInBackground` so it never delays listening and retries a failure, and only `BILLING_ENABLED` runs any of this. Rotating `AUTH_SECRET` forgets every claim.
10. **Both MCP surfaces are mandatory-token surfaces, read-only unless the token is write scoped.** `apps/mcp` is the stdio binary and authenticates like any other client: it sends `ASOBEAST_API_TOKEN` (`asob_…`) as a Bearer header on every request, and a boot-time preflight (`/auth/me`) exits non-zero against a missing or invalid token or an unentitled instance and reads the token's `tokenScope`. `apps/api/src/mcp/` is the remote endpoint: `POST /mcp` takes the same `asob_` token through `AuthGuard`, refuses a session cookie with 401, and dispatches each tool in process through `InProcessGateway.send` (a method, a URL and an optional JSON body) rather than over a socket, so the inner route's own guards, `StorableTextPipe`, `ValidationPipe`, plan write budget and quota run unchanged. Every tool in `MCP_TOOLS` is a `GET` annotated `readOnlyHint: true` and must stay so: **a write tool never joins that list**. The seven tools in `MCP_WRITE_TOOLS` (`track_keywords`, `untrack_keyword`, `add_competitor`, `remove_competitor`, `set_action_status`, `add_annotation`, `delete_annotation`) are listed only to a token whose scope is `write`: `McpBridge.admit` attaches that scope as `req.auth`, the factory reads it from `authInfo`, and stdio reads it from the preflight; anything but an explicit `write` lists reads only. The listing is a convenience, the authority is `TokenScopeGuard` on the inner route, so a read token that named a write tool would still get 403. A write tool wraps an existing route, never a new one or parallel logic, declares honest hints (`destructiveHint` for a delete, `openWorldHint` for anything that reaches the store), and returns a slim `outcome` rather than the route's whole answer. A failed write with status 0 or 5xx, or a 2xx answer the client could not read, says the change may or may not have been applied. On stdio the JSON-RPC stream owns stdout, so all diagnostics go to stderr and the token is never logged. `POST /mcp` draws the plan's `mcpRequestsPerMinute` budget one unit per JSON-RPC message in the body (`messageCountOf`), so a batch of n costs n through one `INCRBY` and is refused whole with the rate limit `429` when the window cannot cover it, uncounted when n exceeds the whole budget because no window could ever serve it; a single request of any kind still costs one. **`packages/mcp-tools` must never import an MCP SDK package**: it is the single definition both transports read, and an SDK import there would put a bundled type identity between two packages that must stay interchangeable.
11. **The admin surfaces bypass Nest's guards, so they carry their own gate.** Bull Board mounts its own Express router and `SwaggerModule.setup` registers on the Express adapter, so `AuthGuard`/`EntitlementGuard` never run for `/admin/queues` or the `/docs*` routes. `configureAdminSurfaces` — called from `main.ts` before `app.listen` and from the e2e app — resolves the session cookie or `asob_` token itself and answers **404** (never 401/403: the surface does not confirm it exists) unless the caller is an entitled **platform operator**. It also keeps the resolved token's **scope**: `/admin/queues` is the one write-capable admin surface, so a read-scoped token gets 404 on any non-`GET`/`HEAD`/`OPTIONS` method there while still reading the dashboard. `/admin/queues` is always gated that way; the `/docs*` routes are gated only under `API_DOCS=owner` (the default), because `public` serves them to anyone and `off` never registers them. Bull Board then re-asserts that grant through `requireAdminAccess`, so an application that forgets the wiring fails closed. A final gate mounted on the `/admin` prefix (`ADMIN_AREA_SURFACE`, after the specific surfaces) applies the same operator check to every other path below it, `/admin/capacity` and `/admin/proxy-pool` included, so those controllers answer `404`, never `401`, `402`, `403` or `429`, to a caller who is not the operator, and a new operator controller is hidden without being listed; that surface does not require a plan in force (`requiresPlan: false`), because `GET /admin/capacity` and `GET /admin/proxy-pool` keep answering `200` to an operator session without a plan. A controller under `admin/` still calls `requirePlatformOperator`; the gate is the first line, the handler the second. The gate resolves credentials through `CredentialResolver`, the provider `AuthGuard` uses, so a refused credential spends the per address rejection budget there too, and a spent budget still answers 404 on these surfaces, never 429; the 429 that address then meets on every other route tells a prober only that a gate counted, which every instance mounts except the `/docs*` routes under `API_DOCS=off`. Middleware order is the reason `main.ts` is the right place: Nest registers module middleware during `app.init()`, which `listen()` triggers, so an `app.use` in `main.ts` lands ahead of it. Both surfaces are reachable only through the web app's origin, via route handlers at the **identical path** (`apps/web/src/app/admin/queues`, `/docs`, `/docs-json`, `/docs-yaml`), because both SPAs build asset URLs from their mount path. Each of those route handlers exports `POST`, `PUT`, `PATCH`, `DELETE` and `OPTIONS` from `lib/api/refused-methods.ts` (the not found envelope, answered without calling the API) unless it forwards the method, because Next.js answers `405`, and `204` with an `Allow` header for `OPTIONS`, for a method a route file does not export, which confirms the route; a new hidden surface does the same. A new Swagger route variant must be added to `DOCS_ROUTES`; a missing entry silently serves the whole OpenAPI document to anonymous callers. `src/proxy.ts` exempts these surfaces from the sign in redirect so a token reaches their gate. Under `/admin` it exempts only `admin/queues`, because every other `/admin` path is a page, so no admin page may be named `queues`.

    **The platform operator is not a workspace owner.** `isPlatformOperator` in `apps/api/src/auth/platform-operator.ts` is the only definition: the `owner` of the bootstrap workspace. It has to be, because hosted registration makes every customer the `owner` of their own workspace, so `role === 'owner'` alone would hand every customer the instance-wide surfaces. Every cross-tenant surface authorizes with it and nothing else — `configureAdminAccess` (queues, docs, metrics, support), `SupportController`, `SupportDirectoryController`, `MetricsController`, `CapacityController` and `ProxyPoolController` — and each answers **404** to a tenant owner. The overview's optional `activation` block counts, across every workspace, the primary apps imported in the last `ACTIVATION_WINDOW_DAYS` that ranked within a day and those that completed setup. A controller refuses through `requirePlatformOperator(user, notFound)`, never an inline check. The web `/admin` area gates in its layout with `viewerAdminAccess`: a viewer who is not the operator gets the in shell not found page, answered with HTTP `200` and a `noindex` robots tag because `(app)/loading.tsx` has already started the stream when the layout calls `notFound()` (the API, `/admin/queues`, `/docs*`, `/metrics` and an unknown `/admin/*` path answer a real `404`), and an operator whose workspace has no plan in force gets a notice saying so, because the support, queue, metrics and docs gate needs an entitled operator too. The API is the authority: every endpoint behind it refuses on its own. `OwnerGuard` and the account deletion check stay plain workspace-owner checks, because owning your own workspace is exactly what authorizes them. `platform-operator.ts` is the one service file the `DEFAULT_WORKSPACE_ID` ESLint rule exempts, alongside `auth.service.ts`. `isOperatorWorkspace` in the same file is the one check for the bootstrap workspace, and that workspace cannot be suspended: `WorkspaceSuspension.suspend` answers 409, and `node dist/auth/abuse/workspace-suspension.cli.js restore ws_default` is the way back for an instance an earlier release left suspended. The operator's own workspace cannot be scheduled for deletion while any account exists outside it (`409`), because registration bootstraps the operator only for the first account ever created. `AccountDeletionService` checks again before it claims the row and once more inside the erasing transaction under the registration advisory lock (`auth/registration-lock.ts`), and cancels the schedule instead of erasing.

12. **The Action Center is deterministic; AI is optional garnish.** Every recommendation in `apps/api/src/actions/` is a pure function of stored data with named exported constants and boundary tests — AI may only summarize an action that already exists, never create, rank, re-order or suppress one, and the whole feature works with `OPENAI_API_KEY` unset. An action's `fingerprint` is `sha256(rule~appId~store~country~keywordId~discriminator)` and **excludes every volatile magnitude** (positions, scores, counts, observation dates); including one would mint a new action every run and destroy the `open/snoozed/done/dismissed/resolved` lifecycle. 13. **A request never waits on Redis through a BullMQ connection.** BullMQ connections keep an offline queue and retry forever, so a command issued while Redis is down never settles and the request behind it hangs until the web proxy gives up with a 504. Every Redis read or counter on a request path goes through `FailFastRedis` (`apps/api/src/redis/`), a dedicated ioredis client with `enableOfflineQueue: false` and a 500 ms `commandTimeout`, and the caller chooses the policy at the call site: `run` fails closed with `RedisUnavailableError` (503 and `Retry-After`), `runOpen` fails open with a fallback value. Both policies cover only an unreachable or timed out Redis; an error Redis answers with, such as `WRONGTYPE`, is a bug rather than an outage and propagates unchanged. **Fail closed anything that could be abused or that queues work Redis must run**: the authentication throttler, the recovery limiter and the on demand limiter. **Fail open anything that only meters or decorates**: plan request counters, the rejected credential count, abuse counting, run keys and operator metrics. Never read `queue.getBackend().client` for a read or a counter a request reaches; `/health` and the first run status still do, and only because each races its own one second timer. Enqueueing a job still goes through the queue and still waits for Redis, which is a known gap and not a pattern to copy, but a bounded one: `redisConnection` gives every BullMQ connection the `reconnectDelay` backoff `FailFastRedis` uses (50 ms steps, capped at 2 s) and no retry budget (`maxRetriesPerRequest: null`), so the first enqueue after Redis returns waits two seconds at most, and `redis-outage.e2e-spec.ts` measures it. BullMQ prints a connection error with `console.error`, outside the JSON log, whenever its `Queue` or `Worker` has no `'error'` listener. `QueueErrorReporter` (`apps/api/src/jobs/`) attaches one to every `Queue` and every `WorkerHost` worker it discovers at bootstrap and sends outage errors to the shared `RedisOutageLog`, which `FailFastRedis` uses too, so the whole API names an outage once every thirty seconds; any other queue error is logged at error level. A new queue or processor is picked up by discovery. Never attach a second listener per class or silence `console.error`. `AppRunStatusService` answers `GET /apps/{id}/run-status` from `AppSnapshot`, `KeywordRanking` and `CategoryRank` rows counted since the daily trigger, or since midnight UTC once it passed, and never reads a queue, so the run pill polls it every ten seconds without touching Redis. It answers `paused: true` when `CollectionEligibility.forWorkspace` refuses the workspace (suspended, or no plan in force with billing on), leaves `state` and the counts as stored rows give them, and adds no `RunState` value. Nothing in boot may wait on Redis, or the listeners never attach and the API never listens: `BillingWorker` and `PipelineWorker` hand `registerSchedules()` to `registerInBackground` from `onModuleInit`, which never awaits it, reports every failure through `reportQueueError` and tries again every thirty seconds until it succeeds or the queue closes. Shutdown may not wait on Redis either: when three pings through `FailFastRedis` go unanswered (an error reply counts as an answer), `QueueShutdown` force closes every worker, queue and flow producer before `@nestjs/bullmq` closes them gracefully, because a graceful `Worker.close()` waits for a main loop that cannot run and a graceful `quit` waits behind any command queued offline, and the shared BullMQ config sets `forceDisconnectOnShutdown: false`, because `@nestjs/bullmq` otherwise awaits the client of a flow producer that never connected. `PrismaService` disconnects in `onApplicationShutdown`, after the HTTP server closed and, because `PrismaModule` is a global module imported before `JobsModule`, after the workers drained, and gives up after two seconds, because `pg` `Pool.end()` waits for every checked out client; a disconnect in `onModuleDestroy` ended the transaction of a request still in its query and held the whole stop behind a query blocked on PostgreSQL. `shutdown-database.e2e-spec.ts` and `redis-down-shutdown-database.e2e-spec.ts` pin both. A signalled stop then ends with `process.exit(0)` (`enableShutdownHooks` with `useProcessExit`, `graceful-shutdown.ts`), never by re-raising the signal, because the API is PID 1 in its container, where the kernel ignores a re-raised `SIGTERM`, so an abandoned query or a Redis socket the force close left open would keep the process alive until Docker's `SIGKILL`; `graceful-exit.e2e-spec.ts` pins it. A request still open then is not waited for either: `QueueShutdown` arms `HttpDrain` (`apps/api/src/jobs/`) before it force closes, `UNREACHABLE_DRAIN_MS` (2 s) later `server.closeAllConnections()` cuts every open connection, and a warning names the force close, because the commands a force closed BullMQ connection had queued never settle (`ioredis` 6 `disconnect()` during the reconnect delay leaves its offline queue pending) and Bull Board's router, which sits on those connections and not on `FailFastRedis`, would hold `server.close()` until the client or the web proxy's 30 s timeout gave up. With Redis answering nothing is armed and a request in flight completes. A stop with Redis unreachable therefore takes the three pings, at most two more seconds and the disconnects, well inside Docker's 10 s default, and `redis-down-shutdown-in-flight.e2e-spec.ts` holds a Bull Board request across it.

Each review drops the function words of the storefront's languages and of its own guessed language, or, when the guess is null, of every language that ties for the most function words it holds (`reviewLanguages`), so a short review no guess can place is still read in the languages it could be. It calls no store and no model. A review translation lives on the `Review` row (`translationLanguage`, `sourceLanguage`, `translatedTitle`, `translatedText`, `translatedAt`), one language at a time: `ReviewTranslator` answers the kept translation for the same language without spending, otherwise spends one `AiGateway` call under `reviewTranslation` after every check that can refuse (an unknown review, no words, an unknown language), and the sync clears it (`TRANSLATION_CLEARED`) when an edit changes the title or the text; the write is matched on the title and text that were translated, so a translation of text the sync just replaced is answered and never kept. The review travels in the same untrusted block as a draft, and an answer holding a link or an address the review does not is refused with `502` (`foreignContacts`). `ReviewItem.language` is a read layer guess (`reviewLanguage`: script first, then function words, `null` when unsure) that only decides where the web offers **Translate**, falling back to the storefront's language. `reviews.reply_negative` keeps reading the store's reply on Google Play only; the owner's mark is not an input to the rule, and its link opens `?replyState=needs_reply&sort=lowest`. `POST` and `DELETE /apps/{id}/reviews/{reviewId}/reply/post` (`ReviewReplyPoster`) send the kept `ReviewReply.text` and take no body; both are `@SessionOnly()`, open to members, synchronous, never queued or retried. A post holds the text to the store limit before any request, opens the store's connection (`openAppStoreReviews`, `openPlayPublisher`, `409` without a usable one), and on success writes both halves of the reply state in one transaction: `ReviewReply.postedAt`, `postedText`, `postState` (`pending` until Apple publishes, `published` for Google, validated against `REVIEW_POST_STATES`), `storeResponseId`, `postedByUserId` and `repliedAt`, and `Review.repliedAt` and `replyText`, so `replyStateOf`, `replyStateWhere`, the counts and `reviews.reply_negative` read a real reply with no new state. The App Store feed's review id is not App Store Connect's, so `AscReviewLocator` lists the home territory's customer reviews newest first down to three days before `reviewedAt` (at most `ASC_REVIEW_LOCATE_MAX_PAGES` without a date), `matchCustomerReview` matches rating, title, body and nickname and refuses two candidates it cannot tell apart, and the found id is kept in `ReviewReply.storeReviewId` for every later post and the withdraw (a kept id that answers `404` is located again once). Apple overwrites a response on a second `POST` and Google edits in place, so an update is a second post; `isPostEdited` derives "edited since posting". A withdraw exists for the App Store only (`DELETE /v1/customerReviewResponses/{id}`), clears the post columns and the two `Review` columns and keeps the text and `storeReviewId`; on Google Play it answers `409`. A `403` on a review resource is a missing role, never a rejected key: it sets `StoreConnection.replyAccess` to `forbidden` (`allowed` after a success, reset by a verify or a new key) and answers `403`, and the connection stays active. A Google sign in posts through its refresh token only when it granted the `androidpublisher` scope (`GoogleAccountCredentials.canReply`); one that did not is `forbidden` from connect and answers `409` with `PLAY_REPLIES_NEED_CONSENT`. The store errors map to HTTP in `review-reply-post-errors.ts`.

22. **The keyword breakdown judges with coverage's own functions and never guesses a listing.** `GET /apps/{id}/keywords/{keywordId}/breakdown` (`KeywordBreakdownService`) reads stored rows only and reaches no store. It builds each app's surfaces with `judgingSurfaces`, the primary app with its non empty saved fields and a competitor with none, judges the phrase with `coversKeyword` so it never disagrees with the coverage table, and reports an accent folded word (`searchKey`) as `folded` without counting it. Each localization is judged alone, because App Store search never combines words of two localizations. A localization the market searches that has not been captured for an app is listed in `unread`, never borrowed from another storefront. `ranking: null` is never checked, `position: null` is checked and not found. A competitor note is a pure rule in `keyword-breakdown-insights.ts` with named thresholds (`RATINGS_GAP_FACTOR`, `RATINGS_MIN_GAP`, `SETTLING_DAYS`); the ratings rule compares two ratings only when both come from the keyword's market listing. The web renders the server's `segments` and decides no match itself, and reads the breakdown with `useQuery` under `appKeys.compareRoot`, so a keyword change refreshes it and a failure never replaces the page. The MCP read tool `keyword_breakdown` wraps the same route.

23. **A console key is sealed, owner only, and the funnel is read from the store's own report.** Connecting a store console is optional and off until `STORE_CONNECT_ENCRYPTION_KEY` is set (`SECRET_BOX` is `null`, `GET /store-connections` answers `available: false`, every change but a disconnect answers `409`, the schedule is removed and nothing reaches Apple; a stored key that no longer decrypts answers `409` with `CREDENTIAL_UNREADABLE` and marks the connection rejected). One connection per workspace and store, through `GET /store-connections` and `PUT`, `POST …/verify`, `POST …/sync` and `DELETE /store-connections/{store}`; every change is `@SessionOnly()` with `OwnerGuard`, so no `asob_` token, write scope included, can replace or remove a key, and a member reads the state. `PUT` verifies the key with Apple before anything is stored (`422` refused, `502` unreachable, `400` for a key that is not a P-256 PKCS8 PEM, which `normalizePrivateKey` rebuilds when a password field joined its lines), replaces any earlier key and its report requests, and queues a sync. The credential is sealed as one JSON string by `SecretBox` (AES-256-GCM, `v1.<key id>.<iv>.<tag>.<body>`) with the context `store-connection:<workspaceId>:<store>`, so a ciphertext copied into another workspace never opens; `STORE_CONNECT_ENCRYPTION_KEY_PREVIOUS` opens an older one and `StoreConnectionService.openAppStore` and `openPlay` reseal it. The issuer ID, key ID and public key fingerprint are kept in clear; the sealed value is never answered, exported (`SECRET_FIELDS`) or logged (PEM blocks and signed tokens are scrubbed). Report access is learned, never asked: a `201` creating a report request records `admin`, a `403` records `readOnly` with the sentence that an Admin key is needed once, and an existing request is adopted by listing first. The sync runs in its own `store-connect` queue at concurrency 1, outside the store request budget and the proxy pool, one deduplicated job per workspace and store, fanned out by `CRON_STORE_REPORTS` to the workspaces `ActiveWorkspaces.forDailyRun` names and queued by connect, verify and sync. It matches each primary App Store app to the key's apps by store id (an app the key cannot see is `unmatched`), lists each visible app's remote requests on every run so an ongoing request Apple stopped or dropped is placed again, requests the one time snapshot and the ongoing Discovery and Engagement report, downloads at most `MAX_INSTANCES_PER_RUN` (200) daily instances newer than each request's `lastProcessingDate` in ascending processing date order, keeps the gzip in `StoreReportInstance.raw` for `RETENTION_STORE_REPORTS_DAYS`, and pivots the rows by header name into `StoreFunnelDay` (app, date, territory, source type, page type) with an upsert that never lets an older processing date overwrite a newer one; `lastProcessingDate` only advances. An Apple error for one app, or a report that cannot be downloaded or read, stops only that app or that request for the run and leaves `PARTIAL_SYNC` in `lastError`; a segment whose size differs stops that request for the run, a checksum mismatch is only logged, a `429` ends the run normally, a `401` or `403` from the App Store Connect API after the request phase marks the connection `rejected` with the reason (`refusalOf`: the missing agreement code `FORBIDDEN.REQUIRED_AGREEMENTS_MISSING_OR_EXPIRED` names the agreement, anything else the refused key) and fails the job as unrecoverable, while a refused segment download is a plain error and never rejects the key, and a `5xx` is retried once. A territory is resolved to a storefront through `countryOfTerritory` or kept with a `null` country, which every market filter leaves out and "all markets" counts. `GET /apps/{id}/funnel` answers `connected: false` and empty series for a competitor, an app without an ongoing `requested` request of an active connection, or with the feature off, even when rows survive a disconnect; otherwise a zero filled daily series and the 7, 14 and 28 day windows of complete days against the period before. A day is complete once it is three days old and no later than the newest stored day of the app (`reportedThrough`), derived at read time and never stored, so a sync that falls behind never turns missing days into zeros. Conversion is Get taps divided by unique impressions on the App Store, as Apple reports them; a dimension a store does not report is `null`, never estimated. When the key may read it, the sync also downloads the detailed report into `StoreFunnelPageDay` (one row per date, territory and page title, `no page` dropped) with its own `detailedReportId` and `detailedLastProcessingDate`; any error on the detailed report but a rate limit, while listing or applying it, only skips that lane for the run and never rejects the key or holds back the standard report, and the funnel answers the optional `pages` of the last 28 complete days, default page first. `GET /apps/{id}/changes/impact` merges an optional `funnel` block into every window only while the app's store connection reports it (`measureChangeFunnel`): the same number of complete days before the change and from the day of the change on, `measured` when every day after is final, `pending` while Apple finishes them, `unmeasured` when the console reports nothing for the whole period before; without a connection the field is absent, so the response stays as it was. Both conversion rules read 21 or 14 calendar days of the home market ending at `completeThrough` and hold an existing action as `withheld` instead of resolving or confirming it while the console stops reporting the app (`ActionFunnel.reporting`), a day of the window is missing, page views move past `CONVERSION_PAGE_VIEW_TOLERANCE`, or a page or the default page has under `CPP_MIN_UNIQUE_IMPRESSIONS`. Google Play connects a service account instead (`PUT /store-connections/GOOGLE_PLAY` with `serviceAccountJson` and a `pubsite_prod` `bucket`, picked by `StoreConnectionBodyPipe`; a body whose `store` differs from the path is `400`): the JSON must hold an RSA PEM key (`400` otherwise), verification lists `stats/store_performance/` once with a `devstorage.read_only` token (`401`, `403` and `404` answer `422`, the last naming the bucket), the sealed credential is `{ clientEmail, privateKeyId, privateKey, bucket }`, `issuerId` stores the email and `keyId` the private key id, and `reportAccess` is `admin` at once because Google has no request step. Google Play also connects through the owner's own Google account when `GOOGLE_PLAY_OAUTH_CLIENT_ID`, `GOOGLE_PLAY_OAUTH_CLIENT_SECRET` and `WEB_PUBLIC_URL` are set (otherwise `GOOGLE_OAUTH_CLIENT` is `null`, `GET /store-connections` answers `googleSignIn: false` and both sign in routes answer `409`; a stored Google account connection is never rejected for it, because the configuration of the instance is not the credential, so verify answers `409` and the sync fails and retries): `POST /store-connections/GOOGLE_PLAY/sign-in` with the `bucket` answers the Google consent address (offline access, `prompt=consent`, PKCE S256, scopes `openid email devstorage.read_only`) carrying a state that `SecretBox` seals with the context `play-sign-in:<workspaceId>:<userId>` around the bucket, the PKCE verifier and a ten minute expiry (`sign-in-state.ts`); Google returns to the web page `PLAY_SIGN_IN_PATH` (`/integrations/google-play`), which posts the code and the state once to `POST …/sign-in/complete`. That route opens the state for the same owner and workspace only (`400` otherwise), redeems the code (`400` when Google refuses it), refuses an answer whose granted scopes leave out storage with `422`, lists the bucket with the refresh token exactly as a key is checked, and stores `{ email, refreshToken, bucket }` sealed like any credential, with `credential = 'googleAccount'`, `issuerId` the email and `keyId` the Google subject; both routes are `@SessionOnly()` with `OwnerGuard`. `GcsApi` takes a `GoogleGrant` (the service account's JWT bearer assertion or the refresh token grant, built by `GcsApiFactory`) and the account it reads as, and `playRefusal` (`play/play-refusal.ts`) is the one wording of a Play refusal for connect, verify and sync: a token answer is a refusal only for the OAuth codes `invalid_grant`, `invalid_client`, `unauthorized_client` and `redirect_uri_mismatch` (any other `4xx` stays a retryable `GcsError`, a `429` a rate limit), and a refused token names the deleted key or the revoked sign in, or the instance's OAuth client when Google answers `invalid_client`, `unauthorized_client` or `redirect_uri_mismatch` (`CLIENT_REFUSED`, also `409` on `…/sign-in/complete`), a `403` names the account and the Account permissions tab, and only a `404` names the bucket, because Cloud Storage answers `404` for a bucket that does not exist even to an account without access. `PlayReportSync` lists each primary Play app's files under its package prefix (at most `MAX_LISTED_OBJECTS`, `unmatched` when the bucket holds none), checks the bucket once per run (a refusal or a missing bucket rejects the connection), marks an app `forbidden` when Google refuses its listing or a file, skips a file that vanished or cannot be read (`PLAY_PARTIAL_SYNC`) without holding back the rest, skips a file listed above `PLAY_REPORT_MAX_BYTES` and stops reading one past it, keeps search terms storable (`MAX_TERM_CHARS`, no NUL, no lone surrogate) and counts within int4, and downloads the current and the previous month's country and traffic source files only when the object's `generation` changed, recorded as a `MONTHLY` `StoreReportInstance` whose `remoteId` is the object name and generation. The country file writes `StoreFunnelDay` rows with `sourceType = 'all'` and the country code as territory, the traffic source file rows with `territory = 'all'` and `country = null` (`funnelScope`): a market reads the first set and "all markets" the second, so the two breakdowns are never summed; visitors land in `pageViews` and acquisitions in `gets`, Play conversion is acquisitions divided by visitors and `impressions` stay `null`. A newer generation replaces the month's rows of its breakdown in the same transaction, so a row Google dropped does not linger. The traffic file also replaces the month's `StoreFunnelSearchTerm` rows (tenant owned, RLS, unique on app, month and raw term), and `GET /apps/{id}/keywords` gives a Play keyword of a reporting Play connection the optional `playAcquisitions` of the newest complete month, or the month in progress when it is the only one, whose `normalized` term equals `normalizeText` of the keyword, summing the spellings of that month; an App Store keyword carries no field.

Root `.env` (Compose only): `POSTGRES_PASSWORD` and `AUTH_SECRET`, both required and non-empty, plus settings Compose hands to one service each. The API receives `AUTH_COOKIE_SECURE`, `LOG_LEVEL` and `WEB_PUBLIC_URL`, the last in place of the value in `apps/api/.env` (that file also configures `pnpm dev` on port 3000) and defaulting to `http://localhost:3001`, the port both stacks publish. The web app receives `TRUST_PROXY` and `STATUS_PAGE_URL`; the API's own `TRUST_PROXY` stays pinned to `1`, the web app, so the root value never reconfigures it. `ASOBEAST_IMAGE_OWNER` and `ASOBEAST_IMAGE_TAG` are read only by `docker-compose.pull.yml` and pick which published images that stack runs; they default to the images this repository publishes at the current version, so pinning an older release is the only reason to set them. `TUNNEL_TOKEN` and `ASOBEAST_DOMAIN` are read only by `docker-compose.tunnel.yml`, the optional Cloudflare Tunnel overlay that terminates TLS at Cloudflare's edge and stops publishing host port 3001, so the machine listens for nothing.

## What NOT to do

- No breaking change to the HTTP contract, the `@asobeast/shared` contract types or the MCP tool surface inside `1.x`; removal, renaming and narrowing all need `2.0.0`. Add alongside instead.
- No hand-cut release while the pipeline is healthy; Release Please owns tags, versions and `CHANGELOG.md`.
- No `fix` without a regression test that was observed failing for the reported symptom first.
- No alternative ORMs, queue systems, HTTP clients, package managers or task runners; the stack is fixed.
- No store calls in tests; providers are mocked in unit and e2e tests.
- No manual SQL migrations; always `prisma migrate dev`.
- No scraper imports outside the `StoreProvider` interface; all scraping goes through the provider layer.
- No OpenAI call and no CDN language download to read screenshot text; no screenshot caption in `uncovered`, in the keyword field suggestion or in an Action Center rule.
- No MCP tool that changes data outside `MCP_WRITE_TOOLS`, none listed to a token that is not write scoped, and none that calls a route the web app does not already use.
- No keyword field editor outside the metadata page, and no keyword field written outside `KeywordFieldWriter`; the keywords page only reports.
- No market added by guessing availability; suggestions come from declared languages and a market is seeded only by `MarketSeedService`.
- No chart fetched outside `ChartCaptureService.captureToday`, and no `CategoryRank` written from a provider call.
- No console credential read outside `StoreConnectionService.openAppStore` and `openPlay`, no store report request outside the `store-connect` queue, and no estimate where Apple or Google report nothing.
- No review reply written outside `ReviewRepliesService` and `ReviewReplyAssistant`, no review translation written outside `ReviewTranslator`, no review reply posted outside `ReviewReplyPoster` or without a person's click, and no AI draft or translation that bypasses `AiGateway`.
- No comments inside code. DRY, KISS, CLEAN CODE.
