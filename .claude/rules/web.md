# Frontend rules

## Frontend rule 1: One transport, typed by shared

The `src/lib/api/` module is the only place that talks to the API — a barrel over one file per domain, with `client.ts` owning `apiFetch`/`ApiError`/`withQuery` and one function per endpoint, every call typed by an `@asobeast/shared` contract. Never redefine a response shape locally and never import Prisma types. The proxy, `src/lib/api/proxy.ts`, is also the only place a request body is read: `readBoundedBody` (`src/lib/api/request-body.ts`) refuses a body larger than `REQUEST_BODY_LIMIT_BYTES` (the 100 KB the API reads, exported by `@asobeast/shared`), counted as received and so before any `Content-Encoding` is decoded, with a `413` envelope and `Connection: close`, by its declared `Content-Length` or as soon as a chunked stream passes the limit, and cancels the rest of the stream instead of buffering it. `FORWARDED_HEADERS` carries `content-encoding` and the proxy never decodes a body, so the API decodes a gzip, deflate or br body itself, applies its limit to the decoded size and answers `415` for any other encoding. `src/proxy.ts` does not match `/api`, `/docs`, `/metrics` or `/admin/queues`, so Next's `proxyClientMaxBodySize`, which truncates instead of refusing, never applies to them, with one narrow exception: a second matcher entry runs it for `/api/backend`, `/docs`, `/admin/queues` and `/.well-known` paths that carry an escape that can fail to decode (a `%` not followed by two hex digits, or the escape of a byte above `%7F`), because Next answers a bare `500` when it cannot decode a dynamic segment and only the proxy runs before that decode. There `lib/api/malformed-path.ts` refuses an undecodable path (the `400` envelope under `/api/backend`, the hidden `404` for the other three, a rewrite to the not found page for an app page, which is refused before the sign in redirect) and passes a decodable one through untouched. A third entry runs it for every path when the request carries `Next-Action`, which it answers with the `404` Next gives an unknown action, because the app defines no server actions; `next.config.ts` caps `experimental.proxyClientMaxBodySize` at `REQUEST_BODY_LIMIT_BYTES`, so a body the proxy refuses is buffered no further than the API would read; on those paths alone Next buffers a body up to its `proxyClientMaxBodySize` before `readBoundedBody` refuses it, so an ordinary escape such as `%20` never runs the proxy; a handler never calls `request.text()`, `request.json()` or `request.arrayBuffer()` on an unbounded body.

## Frontend rule 2: The query cache owns freshness

`src/lib/queries.ts` holds the `appKeys` hierarchy, the `queryOptions` factories and the mutation invalidation helpers (`invalidateKeywordMutation`, `invalidateCompetitorMutation`, …) — the single place invalidation sets are written down; `invalidateStoreConnectionMutation` refreshes the connections and every funnel query. Pages prefetch into a shared `getQueryClient()` and render a `HydrationBoundary`; client feature components use `useSuspenseQuery`/`useMutation`. **`router.refresh()` is banned** — after a mutation, invalidate or seed the cache. A query a page starts with `void prefetchQuery` streams as a pending promise, so inside that page's `HydrationBoundary` it is read only with `useSuspenseQuery` under a local `Suspense` boundary; a query whose value decides whether an element exists, or whose `dataUpdatedAt` a relative time is rendered against, is awaited by the page so the server render and the hydration render read the same cache entry, or the same absence of one. A query that spends a store allowance (the search, similar and developer suggestions, the competitor suggestions) is keyed outside `appKeys.detail(id)`, because that prefix is invalidated whole by a competitor change, a listing refresh and every run stage; it is stale for a day and never retried, and the local suggestion sources share the `appKeys.suggestionsRoot(id)` root and are invalidated with the app by `invalidateLocalSuggestions`.

## Frontend rule 3: URL is the state

Sort, date-range presets, selected keyword ids and filters live in `searchParams` via `nuqs` parsers in `src/lib/search-params.ts` (built from shared unions). No duplicate `useState` for view state. The keywords table remembers the last sort its viewer chose: `useUrlSorting`'s `remember` option keeps it under `asobeast.sort.keywords` in local storage (pure helpers beside the rest of `lib/table/sorting.ts`, validated against the table's columns) and applies it when the URL names neither `sort` nor `dir` (a bare `dir` names the default sort's direction), so an explicit param wins and the default (`KEYWORD_DEFAULT_SORT`, `opportunity`) never enters the URL; `keywordSortParser` is nullable for exactly that reason. The keywords page's opportunity zone lives in `?zone=` (`keywordZoneParser`, `quickWins`, `worthFighting`, `easyPickings`, `lowPriority`, absent means none) as one more key of `keywordFilterParsers` and one more hidden column filter, so the table, its count, its chips, Clear all and its CSV read it like every other filter, and its filter value carries the two thresholds (`ZoneFilterValue`) because a `filterFn` has no other way to read a preference; the thresholds that cut the zones (default popularity 20, difficulty 25, `lib/keyword-zones.ts`) are a per viewer preference under `asobeast.map.thresholds` in local storage through `useStoredPreference`, never in the address, because a link must not change what its `zone` means for the recipient. The keywords table's `type` filter (`?type=`, any of `KEYWORD_CLASSES`) is a URL filter like `source` and `bucket`: a hidden `type` column filters through `oneOf`, a keyword the API sent no class for matches no selected type, and its chip and facet label come from `KEYWORD_CLASS_LABELS` (`components/keywords/keyword-class.ts`). The keywords page opens its opportunity map above the zone filtered table with `?view=map` (`keywordViewParser`, default `table` left out of the address, and not a key of `keywordFilterParsers`, so **Clear all** keeps the view), and the map's roving focus dot, active dot and open position history dot are component state, the same class as the range tabs of the position history popover: each is transient input that discards nothing. The Action Center filters, groups and searches in the browser over the status-scoped list, and the open action lives in `?action=`; its bulk selection is one deliberate exception, because it is transient input to a single mutation and is cleared after it, so it lives in component state. The keyword import dialog's status filter is another: it filters a review that exists only while the dialog holds a file, and closing the dialog discards both, so it lives in component state too, as does the part of a long file the dialog is on. The save dialog's market checkboxes on the metadata page are the third: they are transient input to one save and are discarded when the dialog closes, so they live in component state, while the open localization lives in `?fieldLocale=`. The setup step's suggested market ticks and seed choices are the fourth, and the keyword picker's tab and ticks in the same setup are the fifth, as are the suggested competitor ticks in the same step and the text, store and storefront of the import dialog, for the same reason: each is transient input to one add and are cleared after it, so they live in component state, while the selected countries and the skipped steps stay in the app's setup record on the server (`GET` and `PATCH /apps/{id}/setup`), read through `setupOptions` and written with an optimistic patch. The Google Play connect dialog's choice between signing in with Google and a service account key is another: it picks the fields of one submission and closing the dialog discards it, so it lives in component state. The billing wall's interval is another: it is transient input to one Checkout session and a change starts a new one, so it lives in component state, while the selected plan lives in `?plan=`; so is the open question of the wall's FAQ, which discards nothing and names nothing a link should carry. The trending panel's kind and list tabs on the top charts page are a sixth: they pick which of the loaded charts to show and discard nothing, so they live in component state. On the reviews page `score`, `version`, `since`, `replyState`, `sort`, `q` and the open composer `reply` live in the URL, and pressing the **Needs reply** tile also sets `sort=lowest`; the composer's text while typing, the tone and the instruction line, the raised limit of **Show all** (a search raises it too) and whether a card shows its kept translation are the seventh exception, each transient input to one request or a per card toggle that discards nothing, so they live in component state. The range tabs of the position history popover on the keywords page are the eighth: they pick which window of one keyword's history to draw and discard nothing, and closing the popover resets them, so they live in component state. The keywords page switches between its tracked table and the discovered list with `?tab=` (`keywordsTabParser`, `tracked` left out of the address), and the discovered sub tabs live in `?state=` (`discoveryStateParser`, `all` left out); the list is fetched once per market and the sub tabs filter in the browser. The discovered table's selected rows are the ninth exception, transient input to one request that a successful track clears, kept per sub tab and discarded with the market, so they live in component state. A discovery mutation seeds the cached list with `withoutDiscoveries` and invalidates `appKeys.keywordDiscoveriesRoot`, which sits under `appKeys.detail(id)` because the read touches stored rows only; the list polls every fifteen seconds for at most forty fetches while `checks.pending` is positive (`keywordDiscoveriesPollInterval`). A translation is seeded into every cached list with `seedReviewTranslation` instead of refetching. A reply save updates the badge and moves the counts in the cached lists (`withReviewReply`, `lib/review-reply-cache.ts`) and marks them stale without refetching, so the open composer stays on screen under a reply state filter it no longer matches. On the app overview `?market=` also scopes the keyword numbers: `keywordScope` (`lib/market.ts`) turns it into the optional `country` of the summary and both histories, no market, one without a listing or an app with a single listing counts every market, and the cards read it through `useKeywordScope`, which defers it with `useDeferredValue` so the previous numbers stay on screen while the next market loads. Which sections of a page are collapsed is a per viewer preference, so it is in neither the URL, which would put it in a shared link, nor component state, which the server render cannot read: the `asobeast_collapsed` cookie holds the collapsed section ids (`lib/collapsed-sections.ts`, page scoped ids such as `competitors.discovery`, declared once beside the page's components and parsed against that list), the page reads it with `cookies()` and hands the ids to `CollapsedSectionsProvider`, and a section is a `CollapsibleCard` (`components/layout/CollapsibleCard.tsx`): its title is the trigger, inside an `h2`, its header controls stay visible while it is collapsed and its content is not mounted, so a collapsed section starts no request of its own. Its content animates open only after the viewer toggles the section, because a section that streams in open would otherwise be drawn at its header height first and shift the page. A cookie, not `localStorage`, because only a cookie lets the server render a collapsed section collapsed and skip what it would fetch; a second page that adopts the cookie passes the union of every page's ids as `known`, or a write would drop the other page's. The keyword breakdown of the comparison matrix lives in `?keyword=`, the way the search results sheet of the keywords page lives in `?serp=` and the day it shows in `?serpDate=`, absent for the newest captured day. The last release a viewer opened on `/whats-new` is another per viewer preference in local storage, under `asobeast.whatsNew.seen` (`lib/whats-new/seen-release.ts`): its server snapshot is `undefined`, so the unread dot of `WhatsNewMenuItem` appears only after hydration, `null` (never opened) reads unread, a value newer than the newest shown release reads seen, and a write that storage refuses is kept in memory for the session; the page marks the newest shown release seen when it mounts, and the `storage` event clears the dot in every other tab. The alerts page keeps `app` (one app), `type` (event names) and `q` in the URL through `alertFeedParsers`; `app` and `type` go to `GET /alerts/events` so every page is full of matching events, and `q` filters the loaded events in the browser (`searchEvents`), because a sentence is computed and the feed is paged. When a viewer last read the alerts is a per viewer preference in the cookie `asobeast_alerts_seen` (`lib/alerts-seen.ts`, an ISO instant), read by the layout and handed to `AlertsSeenProvider` the way the collapsed sections are, so the **New** marks on `/alerts` are in the server render; the sidebar dot is `newest > seen`, where `newest` is `GET /alerts/events?limit=1` read with `useQuery` (no data, no dot, so the server render and hydration agree), visiting `/alerts` writes the newest event's time, and the page keeps the value it found on mount so the marks stay during the visit. The Gap analysis section of the competitors page keeps its tab in `?gaps=` (`gaps`, `winnable`, `threats`, `lead`) and its own `gapSort`, `gapDir`, `gapQ` and `gapCountry` (`GAP_URL_KEYS`), because the matrix beside it owns `sort`, `dir`, `q` and `country`; the keyword behind a row lives in the existing `?keyword=`, and the overview's `Visibility | Share of voice` toggle in `?visView=`. The market, search and sort of the lists filter and sort in the browser over the one analysis answer, which is read with `useQuery` and no server prefetch. Whether the setup checklist pill is collapsed is a per viewer preference under `asobeast.checklist.collapsed` read through `useStoredPreference` (local storage with an in memory fallback), not in the URL or a cookie, because the server render never needs it: the pill (`components/checklist/ChecklistPill.tsx`) renders only after `useAuth` has hydrated and only for an entitled viewer, as a fixed element at `z-10` below the sticky bulk bars and every dialog, with a spacer in the page so it never covers the last row, and it hides itself while its read fails, is loading, is dismissed or is complete. The `(app)` layout awaits `workspaceChecklistOptions` for a signed in viewer and hydrates it in a `HydrationBoundary` around the whole shell, because `HydrationBoundary` defers a query that already exists in the cache to an effect: a page boundary that dehydrated the checklist after the pill had started its own fetch would hydrate with no data and fail with React #418.

## Frontend rule 4: Boundaries per section

Every route segment has `loading.tsx` (geometry-matched skeleton) and `error.tsx` (shared `ErrorState`, whose **Try again** resets the failed queries with `useQueryErrorResetBoundary`, refetches every query still in error, mounted or not, with `refetchFailedQueries` (`lib/queries.ts`), which is how the shell's own reads recover because the layout never remounts and how the page's reader finds a fetch in flight when it remounts even after a shell component that mounted first cleared the reset flag, and then calls the boundary's `retry` prop, because a `useSuspenseQuery` that failed in the browser stays in its error state and throws again without fetching until it is reset, and the reset reaches only a read that mounts before the flag is cleared; a new boundary renders `ErrorState` and nothing else); every `useSuspenseQuery` consumer sits under a local `Suspense` boundary, not the whole page. A section the page can do without, such as the review themes strip, reads with `useQuery` and renders `InlineQueryError` (`components/layout`) when it has no data and the request failed, so one secondary request never replaces the page with the segment `error.tsx`; a section the page cannot show without its data keeps `useSuspenseQuery` under its `Suspense`, except inside a dialog, sheet or popover opened on demand (the search results sheet, the keyword breakdown sheet, the position history popover), which always reads with `useQuery` and `InlineQueryError`: Radix mounts portal content one render after the segment's retry, when a mounting query hook has already cleared the error reset flag, so **Try again** on a `useSuspenseQuery` there refetches nothing and the page stays on its error.

## Frontend rule 5: Domain rendering

Position is 1-based; `null` means "checked, not found within the captured depth" → render `>100` or `>200` from the row's depth, never `0`. An unranked row with a last ranked position reads `>200 (was #14)` as one string in the position cell (`lostPosition`, from `lastRankedPosition` and `lastRankedOn`, falling back to `previousPosition` on an older API), with the day in its title; the history popover and every other readout keep the bare bound. A comparison row lists the apps it has no check for in `unchecked` (the primary app and competitors, absent means every app was checked), and the matrix draws each as a dash named **Not checked yet** and exports it as an empty cell, never as `>200`. Ranking charts use a reversed Y axis (1 on top) on a square root scale (`RANK_AXIS_PROPS` in `components/charts/theme.ts`), so the top 3, top 10 and top 25 bands are tall enough for their labels, and a band label (`RankBandLabel`) is drawn only when its band is at least 14 px tall. `buildRankingChart(series, through)` puts every UTC day from the first check to `through` minus `CHECK_FRESH_DAYS` (or to the last check when later) on the axis, so a day without a check is a gap with no marker, a ranked day between two gaps is a dot (`loneKey`), the tooltip takes `filterNull={false}` so it opens on a day where every value is `null` and reads **Not checked** for a keyword with no check that day, and the empty and insufficient states, **Export CSV** and the CSV rows count checked days only (`checkedDays`, `hasCheck`). Dates are UTC `date` strings formatted with `Intl.DateTimeFormat` pinned to UTC. A date time and a storefront name never come from the engine's own wording, meaning any `Intl.DateTimeFormat` that joins a date with a time (WebKit inserts `at` for `dateStyle` plus `timeStyle` and for explicit hour and minute components alike) and `Intl.DisplayNames`: WebKit, Chromium and Node word them differently and React rejects the mismatch as #418. `formatDateTime` writes the clock itself and `formatCountry` reads `COUNTRY_NAMES`, which `country-names.test.ts` keeps in step with `@asobeast/shared`; `e2e/engine-hydration.spec.ts` runs the route sweep in WebKit. A store price is written by `formatPrice(value, currency)` in the currency the storefront sold it in, pinned to `en-US` and to the fraction digits `format.ts` names per currency, because WebKit's currency data disagrees with Node's for HUF, IDR, COP, PKR and others: the API reads `currency` from the stored raw payload (`currencyOf`, an ISO 4217 code on the snapshot summary, the refresh answer and every `price` change event) and a missing one prints the bare number, never a `$`; `formatUsd` is only for amounts asobeast itself reports in dollars. Traffic/difficulty/opportunity are 0–100 scores. `refresh` returns a snapshot diff to show; `run-daily` and `score` return 202 queued — toast "queued" and let the cache refetch. A keyword that is active and never checked (`latestDepth === null`) renders **Checking…** and the keywords list polls every fifteen seconds for at most forty fetches while such a row exists (`lib/keyword-checks.ts`); a never checked paused row keeps the dash. An active keyword whose `latestCheckedOn` is older than yesterday UTC (`isCheckFresh` and `CHECK_FRESH_DAYS` in `@asobeast/shared`, the rule the position streak reads too) keeps the position cell to its number and swaps the icon of its **Position history** button (`PositionHistoryPopover`) for a clock (`staleCheckDay` in `lib/keyword-checks.ts`, the wording in `components/keywords/stale-check.ts`), whose name ends with the day of the last check and whose popover opens with it, and hides the daily delta chip; "today" is the UTC day of the keywords query's `dataUpdatedAt`, never the browser clock, so the server render and hydration agree, and a paused row or a row without the field shows no day. Every checked keyword carries that button; its popover reads one keyword's `GET /apps/{id}/rankings` and the listing changes of the keyword's own market, both only while open, draws the chart without markers and an `InlineQueryError` under it when only the listing changes fail, keeps the previous range on screen with `keepPreviousData` and caps its height at the space Radix measured, scrolling inside. `PageActions` renders **Refresh**, **Run daily** and `RunProgress` only once the app's detail is in the query cache (`useCachedQueryData`; the app layout hydrates it and an unknown id never does), so an unknown app offers no action and sends no run status request. `RunProgress` in `PageActions` polls `GET /apps/{id}/run-status` every ten seconds while `state` is `running` and the run is not paused (`paused` with a state other than `complete` hides the pill and stops the polling) (`lib/run-progress.ts`) and invalidates the app's queries when a stage advances. The top charts view defers its request with `useDeferredValue` and, while the shown chart is not the requested one, keeps it on screen under `ChartPending`, a status pill naming the requested store and country, fixed at the bottom of the viewport so it never covers a toolbar and takes no space in the layout.

## Frontend rule 6: Theming & a11y

shadcn primitives live in `components/ui` (owned, editable); dark mode via `next-themes` class strategy. Icon-only buttons carry `aria-label`, dialogs carry a description and every popover an accessible name (`aria-label` or `aria-labelledby` on its `PopoverContent`; `e2e/popover-names.spec.ts` opens each one under axe), focus never falls to `body` (a control that changes the URL stays mounted with no remounting `key`, a dialog opened from a button is driven by a trigger so Radix restores focus, and an opener replaced by another control hands focus to its replacement), tables carry a caption, a table whose cells hold no link or button and that can scroll sideways is a named focusable region while it overflows (`scrollLabel` with `scrollFocus="overflow"` on `Table`, measured by `lib/scroll-overflow.ts`; `e2e/structural-a11y.spec.ts` lists the routes at 375 px), charts keep `accessibilityLayer`, and colour is never the only signal. A control that starts a request stays focusable while it runs: it takes `aria-disabled` with a guard in `onClick` or `useSingleFlight`, and the base `Button` dims it, never `disabled`, because a disabled control drops focus to `body`. `e2e/request-focus.spec.ts` holds each such control's answer with `holdRequest` (`e2e/held-request.mts`), presses it from the keyboard and asserts focus stays on it while the request runs and after, and closes each confirmation dialog with Escape and Cancel and asserts focus is back on its opener or on the survivor its removal chose; a new control or dialog of that kind adds its row there. When a request removes or replaces the focused control, `lib/focus-handoff.ts` hands focus to a survivor and does so only if the user has not moved it: `useFocusAfterCommit` focuses an element chosen before the commit, after the commit that removed the control (the Action Center bulk bar, the followed charts list), and a caller that names the leaving control waits while focus stays on it and drops the target once the user moves focus elsewhere, because an unrelated re-render can commit before the removal does, `useCloseFocusHandoff` gives a confirmation dialog's `onCloseAutoFocus` the survivor a confirmed removal chose, usually `siblingControl` of the removed row and otherwise `cardAction`, the card's header button (the alert rows, the competitor cards, the API tokens), `returnFocusTo` returns focus to an opener that is not the dialog's trigger (the snapshot diff after Refresh, the switcher's Import app), `survivingNeighbour` picks the survivor, and `armFocusHandoff` with `useFocusClaim` lets the replacement that mounts later take focus (the follow button, the competitor badge of a chart row, whose cell remounts when the page data changes), and `useFocusGroupClaim` hands focus to the first link or enabled button left in a group when its control leaves while the group stays mounted or mounts without it (the **Capture today** button of a chart column, which hands focus to **Open table**, and of the table actions, which hand it to the follow button; the activation arms `captureFocusKey`). A confirmation dialog that leaves its trigger disabled or replaced decides the target in `onCloseAutoFocus`, as `FollowChartButton` and the reply composer do. A button that a list repeats for each row (the **Reply**, **Translate** and **Show more** of a review card) carries an `aria-label` that begins with its visible text and names its row (`reviewActionLabel` in `components/reviews/review-subject.ts`), and the repeated container is named too, so a button list and voice control can tell the rows apart; rows whose names would be equal (the same stars, author and day) add their position among them, `(2 of 3)`, from `reviewTwins`, and only those rows do, so a unique name never changes. A button whose visible text several views share, **Export CSV** above all, is an `ExportCsvButton` (`components/ExportCsvButton.tsx`): the visible words stay at the start of its name and its subject follows as visually hidden text, never as an `aria-label` that rewords it, because WCAG 2.5.3 Label in Name needs the visible words inside the name; `e2e/export-csv-names.spec.ts` lists the pages. A metric explanation is an `InfoTip` (`components/ui/info-tip.tsx`), an icon button that opens a named and described popover on click, tap or keyboard, never a hover `Tooltip`, because it links to the documentation and must open on touch, and a popover that holds data rather than a metric explanation, such as the position history, is its own component on the `Popover` primitives, never an `InfoTip`; a view shows one per metric, beside its label, or once in the header or toolbar of a section whose cards or tiles repeat the metric. A label never sits as a bare text node beside an icon or spinner that a render inserts or swaps, because a browser translator replaces the page's text nodes and React's `insertBefore` against a replaced node throws `NotFoundError`, which the segment's `error.tsx` then shows instead of the page: the base `Button` puts each run of text children in one `<span>` holding one string, the slotted child of `asChild` included, so a changed label is written whole, a native control with such an icon wraps its label in a `<span>` itself, and `SelectItem` and `SelectValue` put their text in one `<span>` too (`textInSpans`, `components/ui/text-spans.tsx`, which `Button` shares), because Radix portals the chosen item's text into the trigger and React's `removeChild` throws the same way when the dropdown opens, changes or unmounts, and a table cell renders an element rather than a bare string, because a cell remounts whenever its column definitions are rebuilt, as the import review's are on every market change. Text a render changes while its element stays mounted is one string per element, a template string such as ``{`${count} selected`}`` rather than `{count} selected`, because React writes a changed text node in place and the translator has already detached it, so the page keeps the old translated words without any error; and so is a label beside an icon that a render swaps or adds (a status badge, a done step); `Separated` and `MatchedText` follow the same rule, and a list whose rows can show a different item on the next render keys each row by the item it shows, so a new item remounts its row (`serpRowKeys` keys the search results by app). The keyword cell (`KeywordCell`) draws `matchedIn` through `MatchedText`, whose marks carry a hidden label naming the surface and a tint per surface (title green, subtitle and short description blue, keyword field amber), so colour is never the only signal, and a render that flips the marks on or off writes elements, never a bare text node. `e2e/translated-page.spec.ts` replaces every text node the way a translator does and presses each such control, opens the reviews filters, closes, refills and changes the market of the import dialog, steps the search results sheet through its days and compares each row with an untranslated read of the same day, and changes a keyword selection, a character counter, the overview market, including one whose trend gains its data, and the status of an action in its sheet. A screenshot thumbnail (`ScreenshotThumb`) is drawn at a fixed height with `width: auto` and `object-contain`, never cropped, because the caption is printed at the top. A tab strip that switches a source without rendering a `TabsContent` uses `TabsOption`, never `TabsTrigger`, so no `aria-controls` names a missing id; `e2e/structural-a11y.spec.ts` lists the routes and the dialog it covers. The header's action group is fixed width, so nothing in it may depend on data below `sm`: the health badge shows only its mark there (its words are `sr-only sm:not-sr-only`), and because colour is never the only signal each state has its own mark, a dot while healthy or checking, a triangle degraded and a crossed circle unreachable. Degraded with "API up · database unavailable" is reserved for the API's own 503 on `/health` (`answeredDatabaseDown` in `components/layout/health-answer.ts`); every other failed poll, the web proxy's 502 and 504 included, reads unreachable, because only the API's own answer proves the API is up; the poll never retries (`retry: false` on `healthOptions`), because each retry of a hung API waits a full proxy timeout and the next poll is the retry; `e2e/operator-status.spec.ts` drives the real proxy for both gateway answers. `e2e/header-narrow.spec.ts` holds `scrollWidth <= innerWidth` at 320 and 375 px with every health state. Text a store user wrote (a review's title, text, developer reply, the owner's reply field) carries `dir="auto"` and its author sits in a `<bdi>`, because the page is left to right and a right to left review is laid out right to left only when told to; the text block fills its row so `text-align: start` is the right edge, and the card chrome around it stays left to right. `e2e/review-direction.spec.ts` pins it. The alert rules list (`AlertRules`) is one component for the add email alert, add webhook and edit dialogs; its switches and save buttons stay focusable while a request runs.

## Frontend rule 7: The shell is a sidebar, and page width is a per-page decision

`(app)` routes render inside `SidebarProvider` + `SidebarInset`; `(auth)` routes (`/login`, `/register`, the link landings) render a centered card with no sidebar; `(wall)` routes (`/upgrade`, `/confirm-email`) render full width under a header with the theme toggle and a sign out, need a session, and are where an account that owes a step is sent. Only `/login` and `/register` are public (`PUBLIC_ROUTES`): `/upgrade` needs a session, because every action and read on it does. A visit without a session cookie is redirected by `src/proxy.ts` to `/login?next=%2Fupgrade`, a stale cookie is moved there by the server render, because `src/proxy.ts` forwards the requested path in `x-asobeast-requested-path` and `apiFetch` calls `redirect` to `signInTarget(...)` when a server render is refused with 401 (`lib/api/server-session.ts`, swept over every signed in route by `e2e/stale-session.spec.ts`), and by `useSignedOutRedirect` once `/auth/status` answers when a cookie goes stale while a page is open, sign in returns to `/upgrade` (`signedInDestination`), and a 402 on `/upgrade` never redirects the page to itself. The page's queries wait for `useAuth().authenticated`. Route groups keep every URL unchanged. Each page picks one of four width utilities from `src/styles/layout.css`: `page-full` for tables and charts that want every pixel (keywords, rankings, competitors, top charts), `page-wide` for dashboards and grids at a 1600 px ceiling (portfolio, overview, actions, alerts, changes, reviews, metadata, and the whole `/admin` area), `page-checkout` at 1216 px for the billing wall, whose two columns and strip must hold together on a laptop, and `page-reading` at 720 px for prose and forms (settings, integrations, audit, setup). Gutters come from `page-gutter`, which folds `env(safe-area-inset-*)` into the density scale — never per-page padding. The dashboard lays out by its own width through `@container/dashboard`, because the collapsible sidebar makes the viewport a poor proxy for the content box. The metadata page does the same through `@container/metadata`. A grid whose columns depend on the content box beside the sidebar uses a container query, as these two pages do, and its cards carry `min-w-0` so a long badge or token wraps instead of widening the page; user supplied text in a flex item or a shrink to fit column takes `wrap-anywhere`, because `break-words` leaves the box as wide as its longest word.

## Frontend rule 8: Charts go through the chart system

`src/components/charts/theme.ts` owns axes, grid, margins, heights, the series palette and the stroke-pattern order; no chart configures those inline and no chart references `--chart-N` directly. The soft fill under a line is `SeriesFade` with `FADE_STOPS` from `theme.ts`, and the rank tiers, ticks and marker dots of a rank chart come from `charts/rank-layers.tsx`. Multi-series charts distinguish series by stroke pattern as well as colour, and every chart has loading, empty and insufficient (fewer than four points) states at its real height. A control that changes the key of a query a mounted chart reads defers it with `useDeferredValue` (the range tabs of the overview cards and of the ratings history on the reviews page), because a `Suspense` boundary that suspends again hides what it shows with `display: none` unless the update is deferred, and Recharts then measures the container as 0 by 0 and logs a size warning on every render until the data lands. A chart leaves the app as a picture only through `lib/chart-image/` and `useChartImage` (`components/charts/use-chart-image.ts`, behind `ChartImageButtons` and the position history icon): `renderChartPng` clones the Recharts surface, resolves every `var()` and copies the computed paint of each element onto it (the picture is an `img`, which sees none of the page's stylesheets or web fonts), waits for the chart to rest with timers, never `requestAnimationFrame`, and draws the caption and legend with the canvas text API in the colours of the theme the viewer is in. The copy path hands the clipboard the promise of the PNG synchronously from the click, falls back to a download, and a button exists only while the chart draws a line. The keywords page's opportunity map (`components/keywords/map/`) is a Recharts `ScatterChart` through that system (`SCORE_AXIS_PROPS` and `THRESHOLD_LINE_PROPS` in `theme.ts`, `CHART_HEIGHT.hero`, four `ReferenceArea`s from `zone-layers.tsx`, one `Scatter` with `isAnimationActive={false}`): x is difficulty and y is popularity on the whole numbers the table shows; a dot's fill is its rank state (filled ranking, ring not ranking) and its shape how certain its popularity is (circle measured, diamond an Apple floor answer), never colour alone; at most five dots carry a label (`labelledIds`); a dot is one module level `shape` function that reads its state from context, because a `shape` function created inside the component remounts every dot and drops focus to `body`, with a transparent 24 px circle as its target so a click never falls through to the zone under it; the `svg` is `role="group"` with `tabIndex={-1}` while `accessibilityLayer` stays on, and the map draws loading, empty, insufficient (`trendState`) and filtered out states at `CHART_HEIGHT.hero`; its rows are the zone column's faceted rows (`useKeywordsAcrossZones`, memoized on the faceted row model so a row selection or a sort does not redraw the dots), every filter but the zone, so a chosen zone dims dots instead of removing them.

## Frontend rule 9: Tables go through the table kit, and judged numbers go through the grade scale

A data table is a `@tanstack/react-table` v9 instance assembled from `components/data-table/` (sortable header, search, facet, chips, column menu, filtered empty state) with its pure logic in `lib/table/`; sorting and filtering happen in the browser and live in the URL through `search-params.ts`, and column visibility, like the keywords table's remembered sort (rule 3), is a per viewer preference kept in local storage, the other being which sections of a page are collapsed, which is a cookie because the server render reads it (rule 3). The keywords table's Columns menu also holds the listing marks choice, the id `listingMarks` in the same stored choices (default on, `listingMarksOption` in `components/keywords/listing-marks-option.tsx`, passed to `ColumnMenu` as an `options` entry), which the keyword cell reads through `ListingMarksContext` so the columns are not rebuilt when it changes. A score, a position, a rating or a coverage share is graded by `lib/grade.ts` into strong, fair, weak or poor, rendered by `components/ui/graded.tsx`, and always carries the word as well as the colour. `--rank-band-*` and `--score-*` stay for charts that show a distribution. A table kit footer is a column definition's `footer` rendered by `components/data-table/DataTableFooter.tsx` from `table.getFooterGroups()`, sticky and opaque, over `table.getRowModel().rows` so it follows every filter; the keywords table totals row (`lib/keyword-totals.ts`) puts the counts in the keyword cell, the average position and top 10 count in the position cell and the two score means under their columns, writes each figure as one string per element, and counts as a row in `aria-rowcount` and `aria-rowindex`; the Insights column (`lib/keyword-insights.ts`) shows the first two applicable of dropping, page 1 close, beatable and not in listing, hidden below `md` by default.

## Frontend rule 10: Orange is action, blue is information, status keeps its own hues

`--primary` is the landing orange (`--brand-500`) in both themes with dark ink text (`--primary-foreground`, 8.67:1) and darkens to `--primary-hover` on hover; it fills controls and is never text on a surface, because it is 2.1:1 on the light background and reads as `--warning` in either theme. A link styled button is the text colour with a `decoration-primary` underline, an informational badge uses `--info` (blue), and a meter that reports a level uses the status tokens, never `primary`. A view shows one `default` button per independent task: a trigger that opens a dialog is `outline`, the dialog's submit is `default`, and a per row action is `secondary` or `outline`. The filled button's focus ring is solid and offset from its fill; other controls keep their own focus indicator. The active sidebar item tints its icon with `--sidebar-primary`, which is the deeper `--brand-700` in the light theme so the icon clears 3:1 on the active row. `TEXT_PAIRS` in `components/tokens/token-groups.ts` lists every pair the theme promises, status text on `--muted` and on its own tint included, and `tokens.test.ts` measures them in whole sRGB bytes, as the browser renders them. A `-subtle` tint is opaque, mixed with `--card`, so a badge or a sticky cell on a tinted row never paints the tint twice. `--primary-subtle` is the one orange tint, the background of the selected plan card on the billing wall under its `--primary` ring; it carries the foreground and the muted text, which `TEXT_PAIRS` measures, and never orange text. The type scale in `styles/typography.css` has one step above `display`, `hero` (2.25 rem), for the wall's heading and its plan prices from `sm`; nothing in the application shell uses it. `cn` (`lib/utils.ts`) knows every step through `TYPE_STEPS`, which `typography.test.ts` holds to the scale, so a `text-display` passed to a primitive replaces its font size instead of being merged away as a text colour. Text takes a token colour, never an opacity modifier (`styles/utility-classes.test.ts`), and a paused or secondary row mutes its text with `--muted-foreground` instead of `opacity`. `e2e/contrast.spec.ts` runs axe `color-contrast` on every signed in and signed out route in both themes, with no exclusion. The product is written `AsoBeast` in interface text (`PRODUCT_NAME` in `lib/brand.ts` where the string is the name itself) and stays lowercase in every technical identifier; `lib/brand.test.ts` enforces it.
