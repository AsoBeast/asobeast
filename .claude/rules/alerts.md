# Alert rules

## Domain rule 17: Alert emails are subscription mail; account and billing emails are transactional

Every alert email carries RFC 8058 `List-Unsubscribe` and `List-Unsubscribe-Post` headers when `WEB_PUBLIC_URL` is https, and a footer link to `/unsubscribe`. `POST /email-alerts/{id}/unsubscribe?token=` is public, checks an HMAC of the alert id and its current recipient address under `AUTH_SECRET`, so changing the address retires earlier links, deactivates only that alert, answers `204` and never redirects; a `GET` never unsubscribes. The worker sends only to active alerts. Account and billing mail never carry the headers. Every email carries `Auto-Submitted: auto-generated`. A report's HTML part stays under 90 KB: `formatBatchEmail` steps its per block line cap down only while the HTML would exceed it, and the text part keeps every cap. `rating.dropped` and `review.spike` are raised from stored rows by `ListingAlerts` (`apps/api/src/apps/listing-alerts.service.ts`, from the home capture of a primary app, only when the displayed average fell by whole tenths and deepened against the previous capture) and `ReviewSpikeAlerts` (`reviews/`, from the review sync, only when this sync's inserts carried a day over `max(5, 3 × median of 28 days)`); both write their outbox row whether or not a channel listens, a channel's `ratingDropTenths` filters drops per delivery (`withRatingDropsAtLeast`, `receivesInstant`), and `ESSENTIAL_ALERT_EVENTS` in `@asobeast/shared` names the events a default subscription carries. A subscription's `rankDropThreshold` filters at delivery only, clamped to at least `ALERT_RANK_DROP_THRESHOLD`, because `AlertsDispatcher.collect` records every detected move for the feed before any subscription is checked. The first daily completion after a workspace's first ranked primary app creates one essential email alert to the owner (`DefaultAlertsService`, called by `DefaultAlertsRun` before the flush) when mail works and `WEB_PUBLIC_URL` is https, claiming `Workspace.defaultAlertsAt` in the same transaction as the row; every hand made `EmailAlert` or `Webhook` claims the same marker, so the defaults exist once and never return after a delete or an unsubscribe, and the first email of a `defaultOrigin` alert opens with one sentence claimed through `introSentAt`. A daily update's subject is `leadOf`'s sentence, its moves are ordered by `moveImpact` and each rank group lists five rows.

## Domain rule 19: An email alert recipient confirms the address before anything is mailed to it

`EmailAlert.confirmedAt` stays null until the recipient presses the button on the web page `/confirm-alert`, which posts to the public `POST /email-alerts/{id}/confirm?token=` (a click, never a `GET`, like the unsubscribe). The token is an HMAC of the alert id, the lowercased address and `confirmationSentAt` (`confirmation-token.ts`, on `link-token.ts` beside the unsubscribe token), so a new send, an address change or an unsubscribe retires every earlier link, and it expires after `CONFIRMATION_DAYS` (7). `confirmationSentAt` is reserved before the mail leaves by a conditional update against the row it was read from, so of two concurrent sends only one goes out, and a resend reserves it before it claims the daily allowances, so a resend that loses the race spends none and is held to the cooldown; a send that fails restores the earlier time, which keeps the earlier link, and every path that sends nothing gives back both allowances, including a transaction that fails after claiming them; and create and update answer the optional `confirmationSent` whenever they asked a recipient to confirm. Every reader of `EmailAlert` that delivers (`AlertsDispatcher`, `AlertFlushService` and `AlertsWorker`) goes through `DELIVERABLE_EMAIL_ALERTS` or `isDeliverable`, and a new reader does the same; the test send needs only a confirmed recipient, so a paused alert can still be tested. An address is confirmed at creation only when it is the verified account email of a member of the same workspace, which the RLS policy on `User` scopes. Everything else waits, fail closed: without `WEB_PUBLIC_URL` no link can be built, so nothing is mailed and the recipient stays unconfirmed (`EmailAlertConfirmation.canSend`). Changing the address resets the confirmation and mails the new address. An unsubscribe withdraws the confirmation and stamps `unsubscribedAt`, so resend answers `409` for that alert until its address changes and it no longer counts as waiting. The confirmation email carries the alert's unsubscribe link, so a recipient who never asked can stop being asked, and the optional `EmailAlertItem.unsubscribed` lets the settings row say so instead of offering a resend that would be refused. The upgrade migration confirmed only the alerts that were active. The confirmation email is transactional (`sendAccountMail`, kind `alert-confirmation`). The default alert confirms at creation when the owner's address is verified; where verification is not required (`BILLING_ENABLED=false`) it is created waiting and the confirmation email goes to the owner as `AsoBeast`, and where it is required an unverified owner waits with the marker unset. `EmailAlertItem.confirmed` is optional for compatibility, and absent means confirmed. Rationing: create, update, resend and test are each limited to 10 requests a minute per workspace with `RetryAfterThrottlerGuard`, as `POST /workspace/invites` is; a workspace holds at most `MAX_EMAIL_ALERTS` (25) email alerts, `MAX_UNCONFIRMED_EMAIL_ALERTS` (5) of them unconfirmed, answering `403`, counted and written under a per workspace `pg_advisory_xact_lock`; a resend waits `CONFIRMATION_RESEND_COOLDOWN_SECONDS` (one hour) after the last confirmation that went out, answering `429`; and `ConfirmationMailLimiter` allows 20 confirmation mails a day per workspace and 5 per recipient mailbox across every workspace, keyed by `sha256(mailboxOf(address))`, so a plus tag, a unicode or punycode domain, Gmail dots and `googlemail.com` are one recipient (the reduction of rule 9, never a second one, and unkeyed because the counter lives one UTC day), checking both in one script and counting either only when both have room, failing closed through `FailFastRedis` with `429`.

## Domain rule 24: The alert feed reads what the run recorded, never what a channel received

`GET /alerts/events` (`AlertEventFeed`) lists `AlertEvent` rows of the last `ALERT_FEED_DAYS` (30) days newest first, keyset paged by `(createdAt, id)` with an opaque cursor, for every workspace member and any `asob_` token, with or without a subscription: the daily run writes the outbox row of every detected event before any subscription is consulted (`AlertsDispatcher.collect`), `ALERT_DELIVERY=instant` writes it already settled (`flushedAt` set, so the flush never claims it, and a failure to record it never stops delivery), and the only detection gated on a listener is `review.new`, which the feed leaves out together with `digest.weekly` (`ALERT_FEED_EVENTS` is `WEBHOOK_EVENTS` minus `ALERT_FEED_EXCLUDED_EVENTS`, so a new event joins by joining `WEBHOOK_EVENTS`, and an event that needs a feed row needs an `outboxRows` branch). The confirmed copy of a drop or exit (`CONFIRMED_KEY_PREFIXES`), the events of a removed app (`AlertEvent.appId` has no foreign key) and a row whose payload cannot be worded (skipped with a warning) are not listed. The sentence is `sentenceOf(payload, false)`, the one wording of every channel, and the web builds the link from the typed payload and `primaryAppId`, so the API never learns a web route. `AlertEvent.keywordId` is how `appId` finds the entrants (`appId` null) of the keywords an app actively tracks; rows recorded before it existed carry none. The instance floors (`ALERT_RANK_DROP_THRESHOLD`, `ALERT_REVIEW_SCORE_MAX`, `ALERT_ACTIONS_MIN_PRIORITY`) decide whether an event exists; a per subscription threshold filters at delivery, never at detection, or the feed would show only what the strictest subscription asked for.
