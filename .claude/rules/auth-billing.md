# Authentication, registration and billing rules

## Domain rule 9: Authentication is mandatory, and self registration never joins a workspace that already holds data

Every request is authenticated by `AuthGuard` (session cookie or `asob_` Bearer token) and then authorized by `EntitlementGuard`; `@Public()` is the only authentication bypass. **`AUTH_REGISTRATION_WORKSPACE` decides where a registration lands, and it defaults to `own` in every mode**: only the bootstrap owner joins `ws_default`, every later account gets its own workspace and owns it, and open registration is safe precisely because no two accounts share a workspace and the RLS policies scope every read. The `shared` value drops every sign up into `ws_default` as a `member` instead, and it is an explicit opt-in for an instance whose sign ups are all trusted with the data already there; it **refuses to boot** with `BILLING_ENABLED=true`, because hosted registration is open to strangers. Sharing a workspace with a teammate is what the invite flow in `workspace-team.service.ts` is for, never self registration, so do not re-tie the workspace decision to `BILLING_ENABLED`: a flag about payment must not decide who reads whose data. Registration decides that under a `pg_advisory_xact_lock`, creating the workspace and the user in one transaction, so concurrent first registrations cannot both bootstrap and a duplicate email cannot leave an orphan workspace. `BILLING_ENABLED` is also the premium seam — unentitled requests get **402**; entitlement and plan live on `Workspace` (`plan`, `trialEndsAt`, `planExpiresAt`, `billingCustomerId`, `subscriptionId`), never on `User`, because a workspace has one plan whatever the size of the team. Account and paywall routes stay reachable via `@AllowUnentitled()`, and an unentitled workspace keeps every session read and export while every write, every on-demand action and every `asob_` token request answers 402 — data is theirs, capacity is what they pay for. The per address count of rejected credentials (`CredentialRateLimiter`, 120 a minute, recorded by `CredentialResolver` for `AuthGuard` and the admin gate alike) is spent only after the credential has been looked up and refused, so an accepted credential is never counted or refused because of the address it arrives from, and a request with no client address, such as an in process MCP dispatch, is not counted. Only a credential that was looked up is counted: a session cookie that fails verification (`AuthService.verifySession`, another secret, expired or carrying no `jti`) and an `Authorization` header without an `asob_` token (`apiToken`) are answered 401 and never counted, because neither costs a lookup or can be guessed, so a browser signed out by an `AUTH_SECRET` rotation reaches the sign in page instead of a 429; a validly signed cookie whose session row is gone or whose session version is stale is looked up and counted like a refused token. Never gate an accepted credential on a bucket that more than one client can share; rejected ones still share the address bucket, so behind a web app at `TRUST_PROXY=0` every browser's rejections count as one client. An invitation link proves the invited mailbox only if it travelled by mail alone, so `POST /workspace/invites` hands the token back in `acceptPath` through `acceptPathFor` (`apps/api/src/auth/invite-link.ts`) and nowhere else: never after the email was sent, and after a failed send or without mail only when the instance cannot email or registration is closed; otherwise `acceptPath` is the bare `INVITE_PATH`. An owner who could read the token could accept their own invitation for a stranger's address, and that stranger's later password recovery would sign them in to the owner's workspace. Every session cookie names a `Session` row through its `jti`: the table is an operator table (`OPERATOR_TABLES`, `operator_only` policy, cascade from `User`) that is read and written only inside `CrossTenantAccess`, and `AuthService.userOfSession` accepts a cookie only while `SessionStore.find` returns an unexpired row of the claimed user whose `sessionVersion` still matches, in the one query that used to read the user. `POST /auth/logout` ends the caller's own row through `AuthService.endSession` before it clears the cookie and never touches another session, and the retention job removes expired rows. Changing or recovering a password ends every session through `sessionVersion`, deletes every `Session` row and every `ApiToken` of that user in the same transaction (`endSessions`, `revokeApiTokens`), because `resolveToken` never reads `sessionVersion` and a token minted during a briefly held session must not outlive the owner's recovery. A route that manages credentials, team membership or the workspace's deletion carries `@SessionOnly()`, enforced in `TokenScopeGuard` from `req.credential`: token creation and revocation, password change, deletion scheduling and cancel, invite creation and revocation, member removal, and posting and withdrawing a review reply answer 403 to every `asob_` token, write scope included, so a leaked agent token cannot mint a successor that outlives its own revocation or schedule the workspace's erasure. A new route of that kind takes the decorator, and the `token-scope` e2e fails if an MCP write tool ever wraps one. **A mailbox gets one trial, ever, not a workspace and not an address.** `mailboxOf` (`auth/mailbox-key.ts`) reduces an address to its mailbox (lowercase, the `+tag` dropped on every domain, dots dropped and `googlemail.com` folded into `gmail.com` for Gmail only), on top of `canonicalAddress` (`auth/canonical-address.ts`), which `isDisposableEmail` shares (NFKC, quotes around the local part removed, the domain's trailing dot dropped and a unicode domain read in its ASCII form) and `TrialClaims` stores an HMAC of it under `AUTH_SECRET` as a `TrialClaim` row, an operator table with no workspace and no foreign key, so it outlives the erasure of the workspace that took the trial and holds no address. A mailbox already claimed at registration, and any address on a domain `mailchecker` lists as disposable, still creates the account and signs it in, but is offered no trial and logs a warning naming the address: `Workspace.trialDeclinedAt` records the refusal, `canStartTrial` reads it and `trialAwaitsCheckout` is `false`; `EmailVerificationService.writeTerms` writes that refusal only. **The hosted trial is a Stripe subscription in `trialing`, started by Checkout on a verified card.** The session carries `subscription_data.trial_period_days` from `TRIAL_DAYS`, `payment_method_collection: 'always'` and `missing_payment_method: 'cancel'`; nothing stamps a trial on a workspace any more and `grantTrial` does not exist. `TrialOffers` (`auth/trial-offers.ts`) is the one reader of the offer rule `trialOfferFor` (`canStartTrial`, an unclaimed mailbox, an owner; never the address's confirmation), and it reads the claim through `CrossTenantAccess` because `TrialClaim` is an operator table a request scope cannot see; `BillingService.checkout`, `GET /auth/plan` (`trialOffer`) and `GET /auth/me` (`trialAwaitsCheckout`) all read it, so the page and the server agree. The claims are settled once per trial by `TrialStarts.settle`, called by the webhook after every projection and by the reconciler after every attempt, on `Workspace.trialClaimedAt` under a per workspace advisory lock, so a reconcile and a webhook that land together never read each other's claims as lost: the owner's mailbox, and the card fingerprint under the `trial-claim:card:` prefix when the saved method is a `card` (a `link` method claims nothing, which is why Radar's free trial abuse control is on the dashboard checklist). A lost claim calls `StripeService.cancelRefusedTrial` (no invoice, nothing charged) before the marker is written, never a release, and `markRefused` in the same transaction leaves the workspace with no trial and no subscription, `trialDeclinedAt` set and the id in `Workspace.trialRefusedSubscriptionId`, which `isRefusedTrial` and `notRefusedTrial` use to keep every later event of that subscription off the row; `GET /auth/plan` answers the optional `trialRefused` until the workspace holds a plan, and `TrialNotifier` sends the one refusal email. `trialStartedAt` and `trialEndsAt` are written by the projection from Stripe's `trial_start` and `trial_end`; `trialStartedAt` is never changed once set except by a refusal, which clears it because no trial ran, and a subscription that stopped entitling, gone or never paid, never keeps a `trialEndsAt` ahead, so a cancelled or declined card trial never revives through the legacy `trial` plan. `firstPaidAt` is written by `FirstPayment.record` from the subscription's latest invoice when it is paid above zero, before the webhook's ordering guard, and `effectOf(status, everPaid)` answers `recoverable` for a `past_due` that never paid, which `AccountPlan.trialChargeFailed` reports; `active` at trial end is an hour before the charge and is not a paid signal. `billingInterval` is written from the catalog for an entitling status so the notices and the banner can name the price without a Stripe read. `planScopeOf` answers `trialingLimits` while `subscriptionStatus` is `trialing` and the effective plan is paid: the chosen plan's limits with the AI allowance at `TRIAL_AI_CALLS_PER_MONTH`; `subscriptionStatus` is a required input. `GET /auth/me` answers `entryStep` from `entryStepOf` (`auth/entry-step.ts`), the one rule for what a signed in account still owes: `confirm-email` for an owner whose address is unconfirmed on an instance that sends confirmation mail, `choose-plan` for an owner whose workspace never held a subscription, a trial or a paid period (`heldPlanOf`), absent for everyone else, members and lapsed workspaces included, and on a self hosted instance. The web sends an account to its step from `(app)/layout.tsx`, `AuthGate`, `/upgrade` and `/confirm-email` (`entryDestination` in `lib/auth-routes.ts`), both standing down on a checkout return until the reconcile has refreshed the account, and `POST /billing/checkout` answers `403` while the step is `confirm-email`, so the order register, confirm, pay, dashboard holds on the server. The wall at `/upgrade` is payment left and plans right in the `(wall)` layout around Stripe's embedded Checkout (`STRIPE_PUBLISHABLE_KEY`) or the hosted redirect; every session carries `branding_settings` from `CHECKOUT_BRAND[theme]` in `@asobeast/shared` (the card surface `--card` of the `theme` the request names, so the iframe sits inside the wall's raised payment panel on one colour, the brand orange button, rounded, Inter, the product name; `checkout-brand.test.ts` holds the literals to the tokens) and `locale: 'en'`, and the web remounts the iframe with a new session when the theme toggles. `signUpSteps` (`lib/sign-up-steps.ts`) turns `entryStep` and `emailVerified` into the three steps the wall and the confirmation page show above their heading, and answers nothing for an account that owes no step. Checkout Elements (card fields drawn on the page) are never built, because the hosted instance sells through Managed Payments, which does not allow them, nor a choice of payment methods. `trialAwaitsConfirmation` and `trialAwaitsCheckout` keep their meaning and stay informational. A deletion request stops the renewal of a `trialing`, `active` or `past_due` subscription (`AccountDeletionService.stopRenewal`, which releases a subscription schedule first and records the subscription in `Workspace.deletionStoppedSubscriptionId` only when it was the one that stopped it), and cancelling or withdrawing the deletion restores what it stopped. Terms acceptance is `User.termsAcceptedAt` and `termsVersion` (`auth/terms-acceptance.ts`), written at registration and invite acceptance on a billing instance only; bump `TERMS_VERSION` when asobeast.com/terms changes. The operator workspace is not exempt. `normalizeEmail` and the stored login email do not change, the mailbox is only the trial key and the recipient key of the daily confirmation email allowance (rule 19). `TrialClaimBackfill` claims the owners of workspaces that already had a trial on boot, in the background through `registerInBackground` so it never delays listening and retries a failure, and only `BILLING_ENABLED` runs any of this. Rotating `AUTH_SECRET` forgets every claim.
