# Admin surface rules

## Domain rule 11: The admin surfaces bypass Nest's guards, so they carry their own gate

Bull Board mounts its own Express router and `SwaggerModule.setup` registers on the Express adapter, so `AuthGuard`/`EntitlementGuard` never run for `/admin/queues` or the `/docs*` routes. `configureAdminSurfaces` — called from `main.ts` before `app.listen` and from the e2e app — resolves the session cookie or `asob_` token itself and answers **404** (never 401/403: the surface does not confirm it exists) unless the caller is an entitled **platform operator**. It also keeps the resolved token's **scope**: `/admin/queues` is the one write-capable admin surface, so a read-scoped token gets 404 on any non-`GET`/`HEAD`/`OPTIONS` method there while still reading the dashboard. `/admin/queues` is always gated that way; the `/docs*` routes are gated only under `API_DOCS=owner` (the default), because `public` serves them to anyone and `off` never registers them. Bull Board then re-asserts that grant through `requireAdminAccess`, so an application that forgets the wiring fails closed. A final gate mounted on the `/admin` prefix (`ADMIN_AREA_SURFACE`, after the specific surfaces) applies the same operator check to every other path below it, `/admin/capacity` and `/admin/proxy-pool` included, so those controllers answer `404`, never `401`, `402`, `403` or `429`, to a caller who is not the operator, and a new operator controller is hidden without being listed; that surface does not require a plan in force (`requiresPlan: false`), because `GET /admin/capacity` and `GET /admin/proxy-pool` keep answering `200` to an operator session without a plan. A controller under `admin/` still calls `requirePlatformOperator`; the gate is the first line, the handler the second. The gate resolves credentials through `CredentialResolver`, the provider `AuthGuard` uses, so a refused credential spends the per address rejection budget there too, and a spent budget still answers 404 on these surfaces, never 429; the 429 that address then meets on every other route tells a prober only that a gate counted, which every instance mounts except the `/docs*` routes under `API_DOCS=off`. Middleware order is the reason `main.ts` is the right place: Nest registers module middleware during `app.init()`, which `listen()` triggers, so an `app.use` in `main.ts` lands ahead of it. Both surfaces are reachable only through the web app's origin, via route handlers at the **identical path** (`apps/web/src/app/admin/queues`, `/docs`, `/docs-json`, `/docs-yaml`), because both SPAs build asset URLs from their mount path. Each of those route handlers exports `POST`, `PUT`, `PATCH`, `DELETE` and `OPTIONS` from `lib/api/refused-methods.ts` (the not found envelope, answered without calling the API) unless it forwards the method, because Next.js answers `405`, and `204` with an `Allow` header for `OPTIONS`, for a method a route file does not export, which confirms the route; a new hidden surface does the same. A new Swagger route variant must be added to `DOCS_ROUTES`; a missing entry silently serves the whole OpenAPI document to anonymous callers. `src/proxy.ts` exempts these surfaces from the sign in redirect so a token reaches their gate. Under `/admin` it exempts only `admin/queues`, because every other `/admin` path is a page, so no admin page may be named `queues`.

**The platform operator is not a workspace owner.** `isPlatformOperator` in `apps/api/src/auth/platform-operator.ts` is the only definition: the `owner` of the bootstrap workspace. It has to be, because hosted registration makes every customer the `owner` of their own workspace, so `role === 'owner'` alone would hand every customer the instance-wide surfaces. Every cross-tenant surface authorizes with it and nothing else — `configureAdminAccess` (queues, docs, metrics, support), `SupportController`, `SupportDirectoryController`, `MetricsController`, `CapacityController` and `ProxyPoolController` — and each answers **404** to a tenant owner. The overview's optional `activation` block counts, across every workspace, the primary apps imported in the last `ACTIVATION_WINDOW_DAYS` that ranked within a day and those that completed setup. A controller refuses through `requirePlatformOperator(user, notFound)`, never an inline check. The web `/admin` area gates in its layout with `viewerAdminAccess`: a viewer who is not the operator gets the in shell not found page, answered with HTTP `200` and a `noindex` robots tag because `(app)/loading.tsx` has already started the stream when the layout calls `notFound()` (the API, `/admin/queues`, `/docs*`, `/metrics` and an unknown `/admin/*` path answer a real `404`), and an operator whose workspace has no plan in force gets a notice saying so, because the support, queue, metrics and docs gate needs an entitled operator too. The API is the authority: every endpoint behind it refuses on its own. `OwnerGuard` and the account deletion check stay plain workspace-owner checks, because owning your own workspace is exactly what authorizes them. `platform-operator.ts` is the one service file the `DEFAULT_WORKSPACE_ID` ESLint rule exempts, alongside `auth.service.ts`. `isOperatorWorkspace` in the same file is the one check for the bootstrap workspace, and that workspace cannot be suspended: `WorkspaceSuspension.suspend` answers 409, and `node dist/auth/abuse/workspace-suspension.cli.js restore ws_default` is the way back for an instance an earlier release left suspended. The operator's own workspace cannot be scheduled for deletion while any account exists outside it (`409`), because registration bootstraps the operator only for the first account ever created. `AccountDeletionService` checks again before it claims the row and once more inside the erasing transaction under the registration advisory lock (`auth/registration-lock.ts`), and cancels the schedule instead of erasing.
