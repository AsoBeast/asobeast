# Screenshot caption rules

## Domain rule 16: Screenshot captions are read on the host, per snapshot, and are a weak surface

Every snapshot records its ordered screenshots in `SnapshotScreenshot` (tenant owned, RLS, cascades with the snapshot) inside the transaction that creates it, for both stores and for every listing, market listings included, and the read is queued right after that transaction commits. The language set comes from the snapshot's own storefront (`listingMarket(app.country, snapshot.country)`), or from its own localization when it has one (`ocrLanguagesFor`), never from `app.country` alone. Only App Store screenshots are read, in the `screenshots` queue at concurrency 1, by `ScreenshotReader` inside the job's workspace scope: it downloads through `ScreenshotImageSource` (the one module that fetches a store image, `1080x0w.jpg` renditions of Apple's image hosts for the OCR by default and, through `readListed`, an App Store or Google Play image exactly as the listing shows it for the creative analysis (domain rule 14), never the proxy pool and never a store request budget; `IconImageSource` reads the `512x0w` renditions of two icon addresses through the same source, bounded by the on demand store deadline when the refresh runs in a request), prepares the image with `sharp`, reads it with the `OcrEngine`, keeps only the large confident lines (`selectCaption`) and caches the result in `ScreenshotText`, which is **shared across workspaces and carries no policy** because the pixels are public, exactly like `Keyword`. A cache row is keyed by the asset key (the address without its size segment) and the recipe (`OCR_RECIPE_VERSION`, currently `ocr2:`, plus the languages). The engine is always given a local `langPath` and `cacheMethod: 'none'`; a language pack is never fetched at runtime. tesseract.js runs inside a worker thread of `TesseractOcrEngine` (`screenshots/ocr-thread.ts`), never in the API's main thread, because the library throws its own worker's failures from an event listener: a damaged pack then ends that thread and fails the read, the job retries with backoff, and the API keeps serving. The thread file imports only packages and types, because Jest starts it from TypeScript through Node's type stripping. Reading never calls OpenAI and never touches `AiGateway`. Caption text is **not** an indexed field: it never changes `uncovered`, the keyword field suggestion or an Action Center rule (`REGRESSION_INDEXED_FIELDS` is an explicit list), and it reaches the audit only through `screenshots-caption-keywords` when no AI analysis exists. `ChangeField` has two screenshot members beyond the legacy count: `screenshots` keeps its numeric before and after and fires exactly when the count changes, `screenshotImages` fires for a replacement or a reorder at an unchanged count, and `screenshotCaptions` is recorded by `CaptionChangeRecorder` once per snapshot and only when both snapshots are fully read with one and the same recipe. Every screenshot comparison stays inside one listing (same app, same stored country, through `listingIn` and `eventsIn`); a market listing's events carry its market and dispatch nothing, like every market change. Coverage reads the captions of the listing that judged each row, `GET /apps/:id/screenshots?country=` reads a market listing, and the audit check reads the home listing only. An optional `ChangeEvent.detail` carries the structure; alerts receive only the field and the two readable values. Google Play screenshots are recorded and diffed, never read. `SCREENSHOT_OCR=false` keeps all recording and image diffing and stops every screenshot download and read; a changed icon address is still checked by downloading its two `512x0w` renditions, because that comparison is what keeps a CDN rotation out of the timeline, and a Google Play icon has no Apple rendition to check, so its changes always record.
