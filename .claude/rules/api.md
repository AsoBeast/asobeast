# API rules

## Conventions

- Every controller input is a DTO validated with `class-validator`; global `ValidationPipe` with `whitelist: true`.
- The `path` of an error envelope is the request path without its query string (`pathWithoutQuery`, `apps/api/src/common/request-path.ts`), and Nest's unknown route message is cut the same way (`withoutQueryEcho`), because a client that puts a credential in a URL must not get it back in a response body. Anything that builds an `ApiErrorEnvelope` for a request calls `pathWithoutQuery`; the web proxy's own envelope already uses `nextUrl.pathname`.
- Text reaches a service only through `@Param`, `@Query` or `@Body` arguments, where the global `StorableTextPipe` runs ahead of the `ValidationPipe` and refuses a NUL character (`404` in a path id, `400` elsewhere) because PostgreSQL text cannot store it, and an unpaired surrogate (`400`) because the Prisma query protocol cannot carry it. It also refuses a body or query nested more than `MAX_NESTING_DEPTH` (64) levels with `400`, passwords included, because the `ValidationPipe` after it recurses and would otherwise throw a `RangeError` as a `500`. A field that is only hashed, never stored (a password, a one time token), carries `@HashedOnly()` and is skipped; `@IsPassword()` applies it. The mark lives on the DTO class and survives `extends`, but a class built with `PartialType`, `PickType` or `OmitType` does not inherit it and must apply `@HashedOnly()` again; until it does the field is scanned, which refuses a NUL rather than storing one. A controller never reads `req.params`, `req.query` or `req.body` itself; `McpController` is the one exception, because its tool arguments are dispatched in process to `GET` routes that carry the same pipe. Do not map the database error in `AllExceptionsFilter` instead: server sourced text must stay a visible `500`.
- All scraping goes through the `StoreProvider` interface in `apps/api/src/store-providers/`. No other module may import a scraper library. This isolation contains parser breakage and lets a future cloud version swap in proxies or a data API.
- Store raw scraper payloads in `raw` Json columns; parsers change, raw data allows reprocessing.
- Every email is a React Email template rendered with `renderEmail` inside `EmailLayout` (`apps/api/src/mail/`). Never build email HTML by string concatenation. A template is a pure component whose props carry everything it shows, including the web origin; colours come from `email-theme.ts`.
- A migration never assumes `_prisma_migrations` exists. `prisma migrate dev` replays every migration into a shadow database that has no such table, so a migration that reads it guards the read with `to_regclass('_prisma_migrations')` inside PL/pgSQL. `apps/api/test/migration-replay.e2e-spec.ts` replays the whole history that way. A released migration is edited only to make it replayable, and the edit ships with a forward migration that rewrites the stored checksum from the released value to the edited one, as `20261008092139_record_plain_play_whats_new_checksum` does. `migrate dev` stops at a changed checksum before it applies anything, so a database that holds the released checksum runs `pnpm --filter api db:deploy` once first.
- `installs` is `BigInt` (kept for future Google Play); JSON serialization patched in `apps/api/src/main.ts`.

## Domain rule 1: Both stores are live

The Prisma enum, shared `Store` union and URL parser cover App Store and Google Play, and `SUPPORTED_STORES` lists both. Play search indexes **title (30), short description (80) and long description (4000)** — there is no subtitle and no keyword field, so those two stay Apple-only concepts everywhere (types, lints, audit weight 0, hidden in the web). Play's indexed 80-char short description (`summary`) is its equivalent surface: it is auto-tracked (`DESCRIPTION` source), linted (`lintShortDescription`) and coverage-checked. The 501 `StoreNotSupportedError` path stays wired for any _future_ store, not for Play.

## Domain rule 3: Rate limits

The iTunes endpoints informally tolerate roughly 20 requests per minute per IP; the `appstore` worker runs concurrency 1 with a limiter from `SCRAPE_ITUNES_RPM` (default 15). Google Play is more sensitive: the `gplay` worker runs concurrency 1 with a limiter from `SCRAPE_GPLAY_RPM` (default 10) that spaces **job starts**. A Play score job fans out to 12–20 sequential requests (1 search + 1–9 suggest-reach probes + 10 detail `getApp` enrichments) and an App Store score job to 3–11 (1 search + 1–9 probes + 1 continuation lookup), while a depth-200 Play rank job uses roughly eight requests versus one for Apple. Never call store endpoints in bulk outside the queue (the only exceptions: small, user initiated lookups, meaning keyword suggestions, a name search and a similar apps lookup, each bounded by an hourly allowance).

## Domain rule 4: One app, per-market keyword tracking; one search serves everyone, including across tenants

`Keyword`, `KeywordMetric` and `SerpEntry` are **global** and carry no policy: two workspaces tracking "habit tracker" in the US share one search rather than paying for two, which is the entire efficiency argument for the shared keyword row and is worth far more under multi-tenancy than under one tenant. What is tenant-owned is the **tracking relation** and the recorded position, so `checkKeyword` reads its trackers through the escape hatch, asks `CollectionEligibility` which of the owning workspaces may still be collected for, and then writes rankings and fires alerts inside each of those. The gate matters because the search is shared: without it a workspace that is suspended, unentitled or past its keyword limit keeps receiving fresh rows whenever another tenant happens to schedule the same phrase. Quota counts keyword-market pairs tracked by a workspace, never global keyword rows. An app is a single row; countries live on keyword tracking (`Keyword` is scoped by `text, store, country`), so a single app owns keywords across storefronts, added and filtered per market on the keyword monitor. `checkKeyword` searches `keyword.country` (not `app.country`) and records positions for the primary app and all its competitors in that storefront from one search — never one search per app. `SerpEntry` holds the top `SERP_CAPTURE_DEPTH` results of each check, and a reader that means the top 10 (entrants, movers, volatility, competitors in the top 10, discovery) filters with `TOP_TEN_ROWS` from `rankings/top-ten.ts`. The same phrase tracked in two markets is two keyword rows checked by two searches; rankings differ per storefront. Each added market multiplies daily search volume against the same `SCRAPE_ITUNES_RPM` budget; `GET /jobs/budget` estimates the fan-out and the settings budget card surfaces it. A market is suggested, never guessed: `GET /apps/{id}/market-suggestions` (`MarketSuggestionsService`) joins the languages the newest home snapshot declares (`extractRawFacts(...).languages`, normalized by `declaredLanguage` in `@asobeast/shared`) with `storefrontsForLanguages`, which answers the first localization in a storefront's read order whose language is declared, with its role; English is never suggested, the home market is left out and a Google Play or competitor app answers an empty list. `POST /apps/{id}/market-seed` seeds one market through `MarketSeedService`: it captures the market listing with `refreshListing`, extracts `seedCandidates` (`keywords/listing-seed.ts`, the same `TITLE` and `SUBTITLE` sources, Play `TITLE` and `DESCRIPTION`, and `MARKET_SEED_LIMIT` the home import uses through `syncFromSnapshot`, reading the shipped localizations the storefront captures beside the native ones), leaves a phrase the app already tracks there, active or paused, as it is, plans the rest against the plan's keyword room with `planSeed` inside `admitKeywordMarkets`, reports what does not fit as `skipped` and never answers 403, and hands the new rows to `FirstPositionChecks.schedule`, then `enqueueFirstScores`, then `MarketListingRequests.request`. Every path that starts tracking a keyword (a manual add, an import, a seed and `KeywordFieldWriter.announce`) queues the first position check before the first score, because the store queues are FIFO at concurrency 1 and a score costs 3 to 11 requests where a check costs one; the writer checks only the keywords its save activated. A storefront without a listing of the app answers `unavailable` and writes nothing. The first capture of a market listing for a primary app asks `LocalizationDetection.request` without spending, with that market added to the markets it probes, `CRON_LOCALIZATION_SWEEP` repeats the request weekly for every primary App Store app of the workspaces the daily run collects for through `LocalizationSweep` (`jobs/`), and `LocalizedListingCapture` reads `capturedLocalizations(market, shipped)` (`apps/market-localizations.ts`), the native localizations plus every shipped localization the storefront reads besides its default (`shippedLocalizations`, which always counts the home localization), for a primary app only, which `localizationReads` counts in the budget. `latestLocalizedTexts` and the listing market switcher read the captured localizations a market still captures, so a localization the app stopped shipping is no longer judged; `listingTexts` stays native only for the home auto tracking. Category ranks, reviews, the ratings history and auto-tracked keywords stay on the home market. Top charts are read for any storefront through `GET /charts`, and `checkCategory` records its positions from the same `ChartCapture` the page reads. The listing is per market: `AppSnapshot.country` and `ChangeEvent.country` are nullable and `NULL` is the home storefront, `apps/api/src/apps/listing.ts` is the only place that says so, and every read of `appSnapshot` or `changeEvent` carries `HOME_LISTING`, `HOME_EVENTS` or a market filter from it (`listing-reads.guard.spec.ts` fails the build otherwise). A listing also has a localization: `AppSnapshot.localization` and `ChangeEvent.localization` are nullable, `NULL` is the storefront's default localization, and every helper in `listing.ts` scopes to it unless it is given a tag, so an existing read never sees a localized snapshot by accident; `eventsOfMarket` is the one helper that reads every localization of a market, for the changes timeline. For an App Store storefront whose default is English other than English (U.S.), `nativeLocalizations(country)` in `@asobeast/shared` names the native localizations it also reads; `LocalizedListingCapture` asks for each right after the default listing is captured, stores it only when the store serves one (`servesLocalization`) or one was stored before, records its changes without an alert and its screenshots in its own language, and a failure of one never fails the default capture. The first native snapshot a capture stores also records its localization as `detected` through `recordAppLocalizations` (later captures record nothing, so a removal sticks until detection runs). Every capture of a market listing for a primary App Store app also records the market's default localization as `detected` when `provenDefaultLocalization` (`apps/market-default-localization.ts`) says the store serves it: the listing differs, by `servesLocalization`, from the newest home listing and from every additional localization `LocalizedListingCapture.capture` read in that market during the same capture, which answers those listings and whether every lookup answered. `MarketLocalizationRecorder` runs after that capture, records nothing while a lookup failed, never records the home localization and never fails the capture. The default of a market is never a probe candidate, because the probe compares against the market's own default listing; a removed default comes back on the next capture that proves it. `POST /apps/{id}/localizations/detect` queues one deferred `DETECT_LOCALIZATION` job per candidate (`detectionCandidates`: a localization an app market reads that the app does not ship and whose language the home listing supports), which `LocalizationDetection.probe` answers with `getApp(…, localization)` and `servesLocalization`, recording `detected` only when the served text differs from both the probe market's default listing and the home listing, because a storefront answers a localization the app does not ship with its primary text, which is the home listing in another market. A localization whose text equals the default listing is invisible to both, and one whose text equals the home listing is invisible to the probe, which is why `manual` exists. Coverage judges a keyword within each localization of its market (`judgeFields`), the keyword field of each localization included (`judgingSurfaces` in `metadata/listing-surfaces.ts`; a market other than home gets a keyword field cell only once a field it reads is saved), auto tracking interleaves the home localizations native first, and `GET /jobs/budget` counts one read per localization `capturedLocalizations` names as `localizations`. The lookup and the product page take the localization in different formats (`app-store-languages.ts`); a malformed lookup `lang` is an HTTP 400, so the map is exhaustive and tested. A market is captured for the markets in which the primary app tracks keywords, for the app and its competitors, as the `REFRESH_APP` job with a `country`, counted in the `apps` stage and reported as `marketListings`; coverage and relevance judge a keyword against the listing of its own market and fall back to the home one. A keyword nobody tracks is searched only by keyword discovery (domain rule 26), which writes the capture for everybody and never a `KeywordRanking`, and writes it only while no workspace tracks the phrase, because a same day capture would become the entrant alert baseline of the daily run (`entrantBaseline`).

## Domain rule 5: Opportunity is derived, never stored

Traffic and difficulty persist in `KeywordMetric`; opportunity is computed in the read layer only, as `(min(volume, 30) / 30) ^ 1.25 * (100 - difficulty)` (`scoring/opportunity.ts`). It is the same for every app tracking the keyword; relevance is reported next to it and never multiplied in (`scoring/keyword-opportunity.ts`).

## Domain rule 6: Position semantics

1 based; `null` means "checked, not found within `depth`" (default 200). Store the row even when null.

## Domain rule 7: Tenancy is enforced by the database, not by remembering to filter

Every tenant-owned table has a `tenant_isolation` policy reading `app.workspace_id`, and every Prisma operation runs in a transaction that calls `app_enter_workspace` and switches to the non-owner `asobeast_app` role — without that switch a superuser or the table owner bypasses the policies entirely. A query with no workspace in scope therefore returns nothing rather than everything, so **service code does not carry `workspaceId` in a `where` clause**; it resolves the workspace from `WorkspaceContext` when it writes, and lets the policies scope what it reads. Work that genuinely spans tenants — account resolution, the scheduled pipeline, retention, operator health — goes through `CrossTenantAccess`, whose one method demands a written justification. `DEFAULT_WORKSPACE_ID` is a bootstrap value; an ESLint rule fails the build if it reaches any other service. Migrations and the seed must run as a role that bypasses the policies (the superuser the images already use). State that outlives a request and is keyed by a tenant owned id, such as a single flight map, is keyed by `WorkspaceContext.require(...)` plus the id, because a map hit answers before any policy runs (`ActionsAiService`); a map consulted only after the row was read under the policies, as `AuditService.runAi` does, is equivalent. `AppSetup` (tenant owned, RLS, `@@id([appId])`) keeps the guided setup of a primary app; `status` and `skipped` are text validated in code against `SETUP_STATUSES` and `SETUP_STEPS`, and the portfolio answers its summary through `setupSummary` from `@asobeast/shared`. `PATCH /apps/{id}/setup` holds `selectedMarkets` to the storefronts of the app's store with `assertStorefront` in `AppSetupService.update` (never in the DTO, which does not know the store), refusing a code the setup does not already hold and that is not the app's home country with `400`, so a client that reads a list and writes it back never fails on an older entry.

## Domain rule 8: Scrapers break

Parse failures fail the job (BullMQ retries with backoff) and must never take down request handling. A route that reaches a store while the client waits carries `@UseInterceptors(StoreDeadlineInterceptor)`: the providers hand its `AbortSignal` to the scraper and stop retrying once it passes, so the request answers the store's `502` within `ON_DEMAND_STORE_DEADLINE_MS` (20 s, below the MCP gateway's 25 s and the web proxy's 30 s) and the cancelled store call writes nothing afterwards. An answer that arrives after the deadline is discarded rather than stored, because the scrapers swallow a cut sub request; a proxy pool lease waits no longer than the deadline, a deadline abort never counts against an endpoint's health, and pool initialization runs outside the scope (`outsideStoreDeadline`). Queued work runs outside that scope and keeps its retries; an App Store attempt is still abandoned after 15 s, and an attempt cut by that bound is retried, never trusted. A store job that meets an unavailable database (`isDatabaseUnavailable`, `apps/api/src/prisma/database-fault.ts`) goes back to the queue delayed, like a busy proxy pool, and spends no attempt until it is a day old (`BUSY_POOL_LIMIT_MS`), and a database error never counts against a proxy endpoint. An app the store no longer lists is a fact, not a failure: `ListingCaptureService` turns a `StoreAppNotFoundError` in the home storefront into `App.delistedAt` (the first such answer, kept until the next home capture or import clears it), a queued refresh finishes on it in every market, `AppRunStatusService` expects no listing of a delisted app or competitor, a `StoreAppNotFoundError` in any other storefront adds that market to `App.unlistedMarkets` (removed by the next capture of that market, never `delistedAt`, because many apps are sold in some storefronts only) and `AppRunStatusService` expects no listing of that app in those markets, and the contract answers the optional `delistedAt` on the app detail, the app list, the competitor items and the portfolio. A not found answer records either fact only when no capture of the same app and storefront stored that listing after the read started: `recordUnlisted` writes under `lockListing` (`apps/listing-lock.ts`, an advisory lock keyed by app and storefront that the capture transaction takes before its snapshot) and requires no snapshot of the listing captured at or after the read's start, so a not found read that finishes after a capture which found the app writes nothing and raises nothing. The same compare and set that records either fact raises `app.delisted` or `app.unlisted_market` once, from `ListingAlerts.listingLost`: a market only when a listing of it was stored before, for a primary app and for a competitor, in the capture's own workspace scope, never failing the capture and never asking whether a channel listens.

## Domain rule 13: A request never waits on Redis through a BullMQ connection

BullMQ connections keep an offline queue and retry forever, so a command issued while Redis is down never settles and the request behind it hangs until the web proxy gives up with a 504. Every Redis read or counter on a request path goes through `FailFastRedis` (`apps/api/src/redis/`), a dedicated ioredis client with `enableOfflineQueue: false` and a 500 ms `commandTimeout`, and the caller chooses the policy at the call site: `run` fails closed with `RedisUnavailableError` (503 and `Retry-After`), `runOpen` fails open with a fallback value. Both policies cover only an unreachable or timed out Redis; an error Redis answers with, such as `WRONGTYPE`, is a bug rather than an outage and propagates unchanged. **Fail closed anything that could be abused or that queues work Redis must run**: the authentication throttler, the recovery limiter and the on demand limiter. **Fail open anything that only meters or decorates**: plan request counters, the rejected credential count, abuse counting, run keys and operator metrics. Never read `queue.getBackend().client` for a read or a counter a request reaches; `/health` and the first run status still do, and only because each races its own one second timer. Enqueueing a job still goes through the queue and still waits for Redis, which is a known gap and not a pattern to copy, but a bounded one: `redisConnection` gives every BullMQ connection the `reconnectDelay` backoff `FailFastRedis` uses (50 ms steps, capped at 2 s) and no retry budget (`maxRetriesPerRequest: null`), so the first enqueue after Redis returns waits two seconds at most, and `redis-outage.e2e-spec.ts` measures it. BullMQ prints a connection error with `console.error`, outside the JSON log, whenever its `Queue` or `Worker` has no `'error'` listener. `QueueErrorReporter` (`apps/api/src/jobs/`) attaches one to every `Queue` and every `WorkerHost` worker it discovers at bootstrap and sends outage errors to the shared `RedisOutageLog`, which `FailFastRedis` uses too, so the whole API names an outage once every thirty seconds; any other queue error is logged at error level. A new queue or processor is picked up by discovery. Never attach a second listener per class or silence `console.error`. `AppRunStatusService` answers `GET /apps/{id}/run-status` from `AppSnapshot`, `KeywordRanking` and `CategoryRank` rows counted since the daily trigger, or since midnight UTC once it passed, and never reads a queue, so the run pill polls it every ten seconds without touching Redis. It answers `paused: true` when `CollectionEligibility.forWorkspace` refuses the workspace (suspended, or no plan in force with billing on), leaves `state` and the counts as stored rows give them, and adds no `RunState` value. Nothing in boot may wait on Redis, or the listeners never attach and the API never listens: `BillingWorker` and `PipelineWorker` hand `registerSchedules()` to `registerInBackground` from `onModuleInit`, which never awaits it, reports every failure through `reportQueueError` and tries again every thirty seconds until it succeeds or the queue closes. Shutdown may not wait on Redis either: when three pings through `FailFastRedis` go unanswered (an error reply counts as an answer), `QueueShutdown` force closes every worker, queue and flow producer before `@nestjs/bullmq` closes them gracefully, because a graceful `Worker.close()` waits for a main loop that cannot run and a graceful `quit` waits behind any command queued offline, and the shared BullMQ config sets `forceDisconnectOnShutdown: false`, because `@nestjs/bullmq` otherwise awaits the client of a flow producer that never connected. `PrismaService` disconnects in `onApplicationShutdown`, after the HTTP server closed and, because `PrismaModule` is a global module imported before `JobsModule`, after the workers drained, and gives up after two seconds, because `pg` `Pool.end()` waits for every checked out client; a disconnect in `onModuleDestroy` ended the transaction of a request still in its query and held the whole stop behind a query blocked on PostgreSQL. `shutdown-database.e2e-spec.ts` and `redis-down-shutdown-database.e2e-spec.ts` pin both. A signalled stop then ends with `process.exit(0)` (`enableShutdownHooks` with `useProcessExit`, `graceful-shutdown.ts`), never by re-raising the signal, because the API is PID 1 in its container, where the kernel ignores a re-raised `SIGTERM`, so an abandoned query or a Redis socket the force close left open would keep the process alive until Docker's `SIGKILL`; `graceful-exit.e2e-spec.ts` pins it. A request still open then is not waited for either: `QueueShutdown` arms `HttpDrain` (`apps/api/src/jobs/`) before it force closes, `UNREACHABLE_DRAIN_MS` (2 s) later `server.closeAllConnections()` cuts every open connection, and a warning names the force close, because the commands a force closed BullMQ connection had queued never settle (`ioredis` 6 `disconnect()` during the reconnect delay leaves its offline queue pending) and Bull Board's router, which sits on those connections and not on `FailFastRedis`, would hold `server.close()` until the client or the web proxy's 30 s timeout gave up. With Redis answering nothing is armed and a request in flight completes. A stop with Redis unreachable therefore takes the three pings, at most two more seconds and the disconnects, well inside Docker's 10 s default, and `redis-down-shutdown-in-flight.e2e-spec.ts` holds a Bull Board request across it.

## Domain rule 14: Every AI call goes through `AiGateway` and spends the monthly allowance

`OPENAI_CLIENT` is private to `AiModule`; a feature calls `AiGateway.spend`, or `reserve` when the request is accepted and `charge` when queued work runs, and never the client. The allowance is `PLAN_LIMITS[plan].aiCallsPerMonth` per workspace per UTC calendar month (`aiPeriodOf`), counted from the tenant owned `AiCall` ledger, where `reserved` and `counted` rows count and `released` rows do not; the meter on `GET /auth/plan` reads the same rows, so it can never disagree with the limiter. A call is counted when the model answered, usable or not (`UnusableAnswerError`), and released when it never answered. Reserve only after every check that can refuse the request, so a 4xx never costs a call. A spent allowance answers **429** with `aiAllowance` and `Retry-After`, never 402, because the web redirects every 402 to `/upgrade`. Self hosted instances are unlimited unless `AI_CALLS_PER_MONTH` is set. During a Stripe trial the allowance is `TRIAL_AI_CALLS_PER_MONTH` whatever the plan. Every call asks for one output ceiling, `AI_MAX_OUTPUT_TOKENS` (default 16,384), because a reasoning model spends that budget on reasoning before it answers; a feature never sets its own. A call someone is waiting on keeps the client's 60 s timeout, and only a queued call (`background`, today the creative analysis) waits up to 180 s, in one SDK attempt because its job retries it, so every attempt fits inside `CREATIVE_RUN_TIMEOUT_MS`; the web proxy gives up after 30 s. The creative analysis embeds every App Store and Google Play image as a data URL (`CreativeImages`, through `ScreenshotImageSource.readListed`), so the provider never downloads a store image itself; an image on another host keeps its address, and a store image that cannot be downloaded fails the run with `LISTING_IMAGE_UNAVAILABLE`. `OPENAI_BASE_URL` points that one client at any OpenAI compatible API. `createOpenAiClient` is the only reader, passes it to the SDK explicitly (`null` when unset, so the SDK never reads the raw environment), and withholds the OpenAI organization and project headers from any host `aiProviderOf` does not name `openai`.

## Domain rule 18: A route that spends store capacity says so and spends an on-demand allowance

A handler that reaches a store while the client waits, or queues store jobs a caller can repeat, carries `@SpendsStoreCapacity()` and spends one `OnDemandLimiter` action from `ON_DEMAND_ACTIONS` (`refresh`, `runDaily`, `score`, `suggestions`, `spider`, `importApp`, `addCompetitor`, `storeLookup`, `chartCapture`), sized per plan in `PLAN_LIMITS`. Refresh, localization detection, deep search, app import, competitor add, the market seed, the store search, the competitor suggestions and the chart capture hand the spend to their service as a callback, which calls it after every check that can refuse the request and before the first store call or `queue.add`, so for those routes a `400`, `403` or `404`, or a request that finds nothing to queue, costs nothing; a deep search finds nothing when each lookup is stored for today or its job is still in the queue. Market availability, run daily and score still consume in the controller before the service runs; suggestions hand the spend to the service, which calls it only when a store strategy has something to look up: `StoreSuggestions.plan` (`keywords/store-suggestions.ts`) reads every local input first and answers no lookup for `search` without an active tracked keyword, for `developer` without a developer id and for `competitorSearch` when no competitor listing it reads (the one in the market, or the home listing of a competitor with none there) holds a seed phrase, a phrase of two or more words that is not made only of the brand words of its own competitor's title, where a phrase one competitor uses seeds as readily as a shared one and the shared ones come first (`CompetitorSearchPlanner`, seeds from `competitor-seeds.ts`, at most `COMPETITOR_SEED_LIMIT`), the lookup it returns makes store calls only, `suggestAround` (`keywords/store-hints.ts`) keeps the answers of the seeds that answered and rethrows only when every lookup failed, so `ProxyEgress` still falls back on a block, and `STORE_SUGGESTION_STRATEGIES` in `@asobeast/shared` names the strategies; a new route follows the callback pattern. A store lookup spends `storeLookup`, hourly, for a name search (`GET /store/search`) and for the similar apps half of `GET /apps/{id}/competitors/suggestions`, whose keyword result half costs nothing and is still answered, with `similar: "unavailable"`, when the store fails or the allowance is spent. `pnpm check:rate-classes` only sees handlers that already call `limiter.consume(`, so a new route that queues store jobs proves its allowance in its own e2e spec (`apps/api/test/spider-capacity.e2e-spec.ts` is the pattern). A deep search probe asks `CollectionEligibility.forWorkspace` in `StoreJobsHandler` inside its own workspace scope before it takes an egress endpoint, so a plan that lapsed or a suspension that began after the probe was queued stops its store request; keyword jobs are judged per tracker by `forKeyword`. Localization detection spends `refresh`, never a new action, and consumes it only once at least one `DETECT_LOCALIZATION` job was queued, so a request with every candidate shipped or already asked today costs nothing; its probe asks `CollectionEligibility.forWorkspace` in `StoreJobsHandler` the way a deep search probe does. Work a person starts to explore, today the deep search and localization probes, is queued with `DEFERRED_JOB_OPTIONS` (a BullMQ `priority`), because BullMQ serves every job without a priority before any prioritized one. The jobs of the daily run carry none and must stay that way. Self hosted instances run with `onDemand: null` and are unmetered.
