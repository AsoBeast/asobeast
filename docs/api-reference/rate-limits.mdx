Limits exist to protect two different things. Request rate protects the API and the database. Store capacity protects the proxy pool and the daily run, because an API caller that triggers a refresh spends exactly what a dashboard user spends by clicking refresh.

## Limits are per workspace

Every limit counts against the workspace, never against the token or the client address. Minting a second token buys no extra capacity, and several people behind one office address do not share a bucket.

Counters live in Redis, so every API instance sees the same window.

Two things are counted per client address instead, because no workspace is known yet when they happen: the authentication endpoints, and rejected credentials. A caller that presents a session cookie or an `asob_` token the API refuses may do so 120 times a minute from one address before the next attempt is answered with `429` without a lookup. A credential the API accepts costs nothing against that count, so a working client never meets it.

An IPv4 client address is counted on its own, and an IPv4 address written in IPv4-mapped IPv6 form counts as that IPv4 address. An IPv6 client address is counted by the /64 network it belongs to, because one connection is usually assigned a whole /64 and could otherwise reset the count by moving to the next address in it. Two devices on one IPv6 network therefore share an allowance.

## Self hosted instances are unlimited

With `BILLING_ENABLED` set to `false` there are no API rate limits at all beyond the existing authentication throttle, which answers a refusal with the same error envelope, `retryAfterSeconds` and `Retry-After` as the plan limits. See [How are sign in attempts throttled?](/security/authentication#how-are-sign-in-attempts-throttled) The only cost of a read is your own machine, and the only real constraint is store collection, bounded by `SCRAPE_ITUNES_RPM` and `SCRAPE_GPLAY_RPM`. See [The daily pipeline and rate limits](/concepts/pipeline).

AI calls are the one exception an operator can opt in to, with `AI_CALLS_PER_MONTH`.

Everything below applies to a metered instance.

## Request size limits apply everywhere

These ceilings are resource safety rather than plan capacity, so they hold on a self hosted instance too.

| Limit | Value | Endpoint |
| --- | --- | --- |
| Keywords per bulk add | 200 | `POST /apps/{id}/keywords` |
| Rows per keyword import | 500 | `POST /apps/{id}/keywords/import` and `POST /apps/{id}/keywords/import/preview` |
| Bytes of one import request | 100 KB, as for every request | the same two endpoints |
| Characters per keyword phrase | 100 | `POST /apps/{id}/keywords` and `PUT /apps/{id}/keyword-field` |
| Characters of keyword field text | 1,000 | `PUT /apps/{id}/keyword-field` |
| UTF-8 bytes of the normalized keyword field | 100 | `PUT /apps/{id}/keyword-field` |

A keyword is also capped at five words. Each tracked keyword market costs one real store search every day, so a pasted spreadsheet column or a scripting mistake would otherwise multiply a workspace's daily store volume without anyone choosing to. Exceeding any of these returns `400` and writes nothing, so a refused batch never lands half applied. Split a larger list across several requests.

A keyword import is different from a bulk add: a problem with one row, such as a phrase over 100 characters or an unknown storefront, comes back as an invalid row in the `200` answer and the other rows are imported. Only a problem with the request itself, such as more than 500 rows, answers `400` and writes nothing.

The keyword field text may run to 1,000 characters, so spacing and duplicates in a pasted field never cost a refusal. The 100 byte limit applies to the field once it is normalized, counted in UTF-8 the way App Store Connect counts it. See [App Store and Google Play](/concepts/stores) for how a save is measured.

## Three request classes

| Class | What it covers | Drawn from |
| --- | --- | --- |
| Read | Anything that returns stored data, including exports and the keyword import preview, which validates rows and writes nothing | The generous per minute budget |
| Write | Configuration changes such as adding a keyword or a competitor | The tighter write budget |
| Store | Refresh, run daily, score and keyword suggestions | The write budget, plus its own on demand allowance |

Reading a year of stored rankings is cheap. Triggering a refresh is not, which is why store endpoints carry a separate on demand allowance on top of the request rate.

Three classes do not mean three budgets. There are two per minute budgets, one for reads and one shared by writes and store requests, and a single daily allowance every class spends from. The class names how a request is priced, never how much room it buys.

A class is also not a permission. A read only token may call any endpoint that does not change data, including the store touching lookups, and it spends store capacity when it does.

## What each plan allows

| Limit | Indie | Ultimate |
| --- | --- | --- |
| Read requests per minute | 300 | 900 |
| Write requests per minute | 60 | 200 |
| Requests per day | 40,000 | 400,000 |
| Requests in parallel | 16 | 48 |
| Refresh per day | 50 | 500 |
| Run daily per day | 5 | 20 |
| Score per day | 100 | 1,000 |
| Keyword suggestions per hour | 60 | 300 |

A trial runs at Indie limits. A workspace whose plan has lapsed keeps the same read allowance, because its data stays readable and exportable while its capacity does not.

## Read the headers

Every response carries the tightest limit the request touched.

| Header | Meaning |
| --- | --- |
| `RateLimit-Limit` | The allowance for the window closest to closing |
| `RateLimit-Remaining` | What is left in that window |
| `RateLimit-Reset` | Seconds until that window reopens |
| `Retry-After` | Present on `429` only. Seconds until the refused request can succeed |

A client that reads `RateLimit-Remaining` and honours `Retry-After` never needs to guess.

## A 429 names the window that closed

```json
{
  "statusCode": 429,
  "error": "Too Many Requests",
  "message": "Rate limit reached: the indie plan allows 60 write requests per minute. Wait 34 seconds before the next one, because retrying before then will fail.",
  "path": "/apps/cl123/keywords",
  "timestamp": "2026-08-14T10:30:26.118Z",
  "rateLimit": {
    "window": "minute",
    "rateClass": "write",
    "plan": "indie",
    "limit": 60,
    "resetSeconds": 34,
    "upgradeTo": "ultimate"
  },
  "retryAfterSeconds": 34
}
```

`window` is `minute`, `hour`, `day` or `concurrent`. Waiting for `resetSeconds` is the whole fix for every window except `concurrent`, where you reduce how many requests you have open at once.

## A spent on demand allowance names its action

Refresh, run daily, score and keyword suggestions each carry an allowance of their own, counted per day, or per hour for keyword suggestions. When one is spent the `429` carries the same `rateLimit` object with `rateClass` set to `store`, and `action` names which allowance closed: `refresh`, `runDaily`, `score` or `suggestions`.

```json
{
  "statusCode": 429,
  "error": "Too Many Requests",
  "message": "Run daily limit reached: the trial plan allows 5 requests per day. Try again in 12 hours 52 minutes.",
  "path": "/apps/cl123/run-daily",
  "timestamp": "2026-10-05T10:30:26.118Z",
  "rateLimit": {
    "window": "day",
    "rateClass": "store",
    "plan": "trial",
    "limit": 5,
    "resetSeconds": 46275,
    "upgradeTo": "indie",
    "action": "runDaily"
  },
  "retryAfterSeconds": 46275
}
```

The allowance resets at 00:00 UTC for a daily window and at the top of the hour for an hourly one, so `Retry-After` is the exact wait.

## A rate limit is not a quota

Four refusals look similar and mean different things. Conflating them makes all four unfixable.

| Status | Envelope field | What it means | What fixes it |
| --- | --- | --- | --- |
| `429` | `rateLimit` | Too many requests too quickly | Wait for the reset, or upgrade for a larger allowance |
| `429` | `aiAllowance` | The month's AI calls are spent | Wait for the 1st, or upgrade for a larger allowance |
| `403` | `quota` | A plan capacity limit such as apps or tracked keyword markets | Remove something, or upgrade |
| `402` | `entitlement` | The workspace has no live plan | Start a plan at the upgrade path in the envelope |

Waiting does not help a `403`, and upgrading a plan does not clear a `429` that is already in flight.

## The monthly AI allowance

The four endpoints that call OpenAI (`POST /actions/{id}/explain`, `POST /apps/{id}/metadata/assistant`, `POST /apps/{id}/audit/ai/runs` and the deprecated `POST /apps/{id}/audit/ai`) also spend a monthly allowance of AI calls. When it is spent they answer `429` with an `aiAllowance` object and a `Retry-After` that points at 00:00 UTC on the 1st; see [A spent AI allowance](/api-reference/errors#a-spent-ai-allowance). `GET /auth/plan` reports the calls used in `usage.aiCalls`. What counts as a call is described in [AI features](/guides/ai-features#how-many-ai-calls-can-a-workspace-make).

## When Redis is unreachable

Counters live in Redis, and a counter that cannot be read must never make the rest of the API wait for it. A command to Redis is given half a second. After that the request is decided by what the counter was protecting.

| Counter | While Redis cannot be reached |
| --- | --- |
| Plan request limits and the parallel request cap | The request is served and not counted |
| Rejected credential count per address | The credential is checked and not counted |
| Sign in, register, confirm, recovery and the other authentication endpoints | Answered `503` with `Retry-After`, because an attempt that cannot be counted could be a password guess |
| Refresh, run daily, score and keyword suggestions | Answered `503` with `Retry-After`, because the work they queue needs Redis too |

Everything that only reads PostgreSQL keeps working, so a signed in browser session keeps its dashboards and exports through a Redis restart. A client that gets the `503` should wait the seconds in `Retry-After`. The first attempt after Redis returns succeeds within a couple of seconds, with no restart of the API. The API log names the outage in one JSON warning every thirty seconds, for the request path and the queues together, and prints no stack trace for each reconnect attempt. Queued work waits and resumes on its own once Redis is back. An API that starts while Redis is already down is different: it waits for Redis before it serves any request and prints each reconnect attempt until then, so start Redis first.

A self hosted instance has no plan limits, so the first and last rows do not apply to it. The other two rows apply to every instance.

## Suspension

An operator can suspend a workspace after sustained abuse. A suspended workspace keeps reading and exporting its data from the dashboard and keeps full access to billing, so it can always pay and always leave with its data. Its API tokens are refused with `403` on every route except `GET /account/export`, so a script can still take the data out. Every write is refused with `403` too, and the daily run skips the workspace. The web app tells every member of the workspace on every page, with the reason the operator recorded, and `GET /auth/me` reports `suspendedAt` and `suspendedReason` for any client that wants to say the same.
