Five administrative surfaces ship with asobeast: the admin area of the web app at `/admin`, the queue dashboard at `/admin/queues`, the OpenAPI surface at `/docs`, the metrics scrape at `/metrics` and the support tooling at `/admin/support`. All of them answer `404` to anyone who is not the platform operator. Two more operator endpoints answer the same way: `/admin/capacity` and `/admin/proxy-pool`.

The last two matter to a hosted operator rather than a self hoster, and [Observability for a hosted instance](/operations/hosted-observability) describes what they serve.

## Who the platform operator is

The platform operator is the owner of the bootstrap workspace, the first account the instance ever created. It is a different principal from a workspace owner.

That distinction matters because registration decides who becomes an `owner`. By default every account after the first gets a workspace of its own and owns it, on a self hosted instance as much as on a hosted one, so `owner` alone cannot authorize an instance wide surface. A one person instance has a single account, which is both the owner of the bootstrap workspace and the operator. A customer who owns their own workspace is not an operator and receives `404` from every surface on this page, and neither is a member who joined the bootstrap workspace because the instance opted into `AUTH_REGISTRATION_WORKSPACE=shared`. See [Where a self registration lands](/security/authentication#where-a-self-registration-lands).

Owning your own workspace still authorizes everything inside it, including managing its team and scheduling its deletion. Only the cross tenant surfaces require the operator.

## Deleting the operator workspace

The operator's own workspace is the one exception to scheduling a deletion. While any account exists outside it, `POST /account/deletion` answers `409 Conflict`, because erasing the bootstrap workspace would leave an instance with accounts and no operator. Registration only hands out the role to the first account the instance ever creates, so a later sign up would never take it over.

The instance is allowed to reset itself. When the operator's account is the only one, deletion works as for any workspace, and the next registration becomes the operator, because an instance with no accounts bootstraps again. The web app explains the restriction in **Settings**, under **Workspace**.

The retention run checks again when the grace period ends. A deletion scheduled while the operator was alone is cancelled, not erased, if an account has registered since, and the log records `its scheduled deletion was cancelled instead of erased`. asobeast has no way to hand the operator role to another account, so to clear your own data delete its apps and keywords. If an instance has already lost its operator, see [Every admin surface answers 404 and no account is the operator](/operations/troubleshooting#every-admin-surface-answers-404-and-no-account-is-the-operator).

## Views only the operator sees

The web app keeps the views that describe the whole instance for the operator too. Capacity, the request budget and the API status are facts about the machine collecting for every workspace, not about one customer's account, so only the operator sees the **Capacity** section of the settings page, the request budget share on the dashboard status line and its 85 percent warning, the capacity step of app setup and the API status badge in the header. Every other account sets up an app in four steps and reads its own usage on the plan card. A one person self hosted instance looks the same as before, because its only account is the operator. The public `/health` endpoint is unchanged, so probes keep working without credentials. See [Health checks](/operations/health-checks).

These views hide the figures rather than restrict them. `GET /jobs/budget` still answers any signed in account and any personal token with the same estimate, so a script can read it. The MCP surface does not offer it as a tool.

## The admin area

The web app has an **Admin** area at `/admin` for the platform operator. It appears in the sidebar, the command palette and the account menu only for the operator, and any other account that opens the address sees the not found page.

| Tab | What it shows | Endpoint |
| --- | --- | --- |
| Overview | workspaces by plan, accounts and sign ups over 30 days, tracked apps by store, keyword markets, searched keywords, AI calls this month | `GET /admin/support/overview` |
| Capacity | daily demand against capacity, per store, the top consumers by name, and the proxy pool when one is configured | `GET /admin/capacity`, `GET /admin/proxy-pool`, `GET /admin/support/workspaces` |
| Workspaces | every workspace with its plan, members, apps and keyword markets | `GET /admin/support/workspaces` |
| Users | every account, newest first, with its workspace and whether its email is confirmed | `GET /admin/support/users` |
| Apps | every tracked app with its workspace, store, home market, competitors and keyword markets | `GET /admin/support/apps` |

Keyword markets count one phrase once per workspace, however many of its apps track it, which is the number the workspace's own plan card shows. The Overview and Workspaces tabs follow that rule, and the Overview total adds the workspaces together, so a phrase two workspaces track counts once in each. The Apps tab counts what each app tracks, so its rows can add up to more than the workspace figure.

Users and Apps accept `?workspaceId=` and return the newest 1,000 rows with the total. Reading either list is written to the support audit trail, the same trail the workspace list writes, because both return personal data. The overview returns counts only and is not written to the trail. The capacity report names its top consumers by workspace id only, because a self registered workspace is named after its owner's email; the Capacity tab takes the names from the workspace list, so reading them is written to the trail too. Every response from these endpoints carries `Cache-Control: no-store`.

The admin area is read only. It lists accounts and apps; it never opens a workspace, so an app name is not a link: the operator's own session cannot read another workspace's pages.

## When the operator's workspace has no plan {#when-the-operators-workspace-has-no-plan}

With billing on, the support tooling, the queue dashboard, the metrics scrape and the OpenAPI surface under the default `owner` setting need an entitled operator. An operator whose own workspace has no plan in force receives `404` from every one of them, exactly as a customer does, although `GET /auth/me` still reports `platformOperator: true` next to `entitled: false`. A plan is in force while a paid plan has not expired or a trial is running. The state is a natural one on a hosted instance: the bootstrap trial waits for the email confirmation, and every trial ends after `TRIAL_DAYS`.

The admin area reads `platformOperator`, `entitled` and `trialAwaitsConfirmation` from `GET /auth/me` and follows the same rule, so it says why instead of showing five tabs that cannot load.

| Operator state | What the admin area shows |
| --- | --- |
| A plan is in force | The five tabs |
| No plan, and the trial waits for the email to be confirmed | A notice to confirm the email, with no offer to pay |
| No plan, any other reason: the trial ended, the plan expired or none was ever set | A notice that the workspace needs a plan, with a link to the plans and to this page |

The **Admin** entry stays in the sidebar, the command palette and the account menu, so the explanation is always one click away. To open the area again, choose a plan on the upgrade page, or set `plan` on the bootstrap workspace to `indie` or `ultimate` in the database, as described in [Authentication and accounts](/security/authentication#entitlements-and-the-paid-plan-seam).

`GET /admin/capacity` and `GET /admin/proxy-pool` check only that the caller is the operator, so they keep answering `200` for an operator without a plan. The web app closes the whole area in that state so it never half loads.

An admin request can also be refused while the operator's workspace has a plan, for example when the workspace is suspended. The tab then says that the admin endpoints answer not found unless the workspace has a plan in force and is not suspended, rather than saying a record was deleted.

## Why 404 and not 403?

A `403` confirms that the thing you asked for exists. A `404` does not.

Anonymous callers therefore get the same answer whether the surface is present, disabled or was never built. There is no login prompt to attack, and a scanner learns nothing from the response.

If you expected a sign in page on `/admin/queues` and got a not found page, nothing is broken. Sign in as the operator in the same browser and reload.

## The queue dashboard

`/admin/queues` serves Bull Board, which shows every queue, its waiting, active, completed and failed jobs, and lets the operator retry a failed job.

| Setting | Default | Effect |
| --- | --- | --- |
| `BULL_BOARD_ENABLED` | `true` | `false` removes the dashboard entirely |

The operator gate is unconditional. There is no configuration that opens the queue dashboard to anonymous callers.

## The OpenAPI surface

`API_DOCS` controls who may read `/docs`, `/docs-json` and `/docs-yaml`.

| Value | Behaviour |
| --- | --- |
| `owner` | Default. Requires an operator session or an operator personal API token, and answers `404` otherwise |
| `public` | Serves the documentation and the OpenAPI document to anyone |
| `off` | Never registers the routes at all |

`public` is a deliberate choice, not an accident, and it is reasonable when the API surface is meant to be read by people you have not given accounts to.

## Both are reached through the web origin

You never reach either surface on the API port. The web app serves route handlers at the identical paths and proxies them through.

Identical paths matter: both surfaces are single page applications that build their asset URLs from the path they are mounted on, so serving `/admin/queues` at any other path breaks its own assets.

The gate itself runs before the application framework's guards, because both surfaces register their own routing outside them. It resolves the session cookie or the `asob_` token itself, and the queue dashboard re asserts the grant afterwards, so a deployment that forgot the wiring fails closed rather than open.

The web app hides the links to both surfaces from anyone who is not the platform operator, using a capability the API computes and returns with the signed in user. That is presentation only. Authorization is the gate above, and a customer who follows a link anyway still gets `404`.

## A read scoped token cannot change queue state

The queue dashboard is the one admin surface that writes. Pausing, resuming, retrying, promoting, cleaning and obliterating a queue all arrive as `PUT`, `POST` or `DELETE`, so the gate applies the token scope the rest of the API applies, and a read scoped token gets `404` on any of them.

| Credential | Read the dashboard | Change queue state |
| --- | --- | --- |
| Operator session | Served | Served |
| Operator token, write scope | Served | Served |
| Operator token, read scope | Served | `404` |

A reporting or MCP integration therefore only needs a read scoped token, and a leaked one cannot stop the daily run. See [Personal API tokens](/security/api-tokens).

## A suspended workspace loses the queue dashboard

The gate applies the same suspension rules the rest of the API applies, because running outside the guards would otherwise mean running outside the policy.

| Credential | `/admin/queues` | `/docs` |
| --- | --- | --- |
| Operator session, workspace suspended | `404`, because the dashboard is an operational surface rather than a read | Served, because reading stays open |
| Operator token, workspace suspended | `404` | `404` |

A suspended account keeps reading and exporting its data, and keeps billing, so the account can always pay and always leave. See [Rate limits and quotas](/api-reference/rate-limits).

The operator workspace is the one workspace that cannot be suspended. The support surface answers `409` and the command line refuses too, because a suspended operator workspace takes the support surface and the queue dashboard away from the operator, and with them the way to lift the suspension. An instance that an earlier release left with its operator workspace suspended restores it from [the command line](/operations/hosted-observability#suspending-and-restoring-from-the-command-line).

## Retired variables

`BULL_BOARD_USER` and `BULL_BOARD_PASSWORD` are ignored. The dashboard used to use basic authentication and now requires an operator session or a personal API token instead.

The API logs a warning at boot if either is still set. Remove them from your environment.
