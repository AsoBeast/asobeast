Billing is off unless `BILLING_ENABLED` is `true` and `STRIPE_SECRET_KEY` is set. A self hosted instance never reaches any of this. See [Configuration reference](/configuration/reference) for the variables.

## The catalog

Two products and four prices, created from a committed script rather than by hand, so a test account can be rebuilt exactly:

```bash
pnpm --filter api stripe:catalog
```

The script creates each price with the lookup key `asobeast_<plan>_<interval>`, `tax_behavior: exclusive` and each product with the software as a service tax code `txcd_10103001`, provisions the customer portal described under [Downgrade and cancellation](#downgrade-and-cancellation), and ends by printing the settings only the dashboard holds. It is idempotent: a second run finds everything it created and changes nothing. The [go live checklist](/operations/billing-go-live) repeats the dashboard settings.

The API resolves the four prices from their lookup keys when it boots, before every nightly reconciliation, and on the next checkout or catalog read whenever the catalog is still empty, at most once a minute. No price id has to be copied into the environment. The four `STRIPE_PRICE_*` variables remain as an override: set any of them and the catalog comes from the environment alone and never asks Stripe. A subscription on a price that has lost its lookup key, for example one archived after a price change, is still placed by the plan in the price's `asobeast_plan` metadata, which the catalog script sets on every price. A price that names no plan either way is refused loudly rather than falling back to a free plan, because a silent fallback means a paying customer gets nothing.

## Checkout

A checkout session always carries what a correct invoice needs:

- the billing address, required;
- a tax id field, so a business can enter its VAT number for a reverse charge;
- `customer_update` for the name and address, so both land on the Stripe customer and print on every later invoice;
- an explicit `flexible` billing mode, rather than whatever the pinned API version defaults to.

`STRIPE_TAX_ENABLED` adds automatic tax to every session. Leave it `false` until Stripe Tax is active with its registrations, because Checkout refuses to open while automatic tax has nothing to calculate with. The address and tax id are collected either way.

The success URL carries `{CHECKOUT_SESSION_ID}`, which Stripe replaces with the id of the completed session. The app posts it to `POST /billing/reconcile`, and the API adopts that session's subscription at once, provided the session names this workspace as its `client_reference_id`. A session that names another workspace, holds no subscription yet or is unknown to Stripe falls back to the customer's subscriptions, so the return never depends on the id.

## The webhook endpoint

Stripe posts every subscription event to one endpoint, and the URL is the web origin followed by the same `/api/backend/` prefix every other API call uses:

```text
https://your-host/api/backend/billing/webhook
```

Register that in the Stripe dashboard, put the signing secret it gives you in `STRIPE_WEBHOOK_SECRET`, and send one test delivery before you take a payment. Without the secret the endpoint refuses every delivery and checkout stays closed, so nobody pays for access that could never be provisioned.

The endpoint is the one billing route that is public, because Stripe has no session. It authenticates the delivery instead: each request carries a `stripe-signature` header computed over the exact bytes of the body, and a delivery whose signature does not verify is refused with 400. The web app forwards that header and the body untouched, so the API verifies what Stripe actually signed.

A refused delivery is logged. Look for `rejected a webhook delivery` in the API log, which names the reason, and check the endpoint's own delivery history in the Stripe dashboard. Stripe retries a failed delivery, so a secret you fix within the retry window costs nothing.

### What happens to an event this instance cannot place

Every verified delivery is stored once and processed from a queue, and each stored event records how it settled:

| Outcome | Meaning |
| --- | --- |
| `applied` | The subscription was written onto the workspace it belongs to |
| `ignored` | Nothing to do: an event type asobeast does not act on, an event that names no subscription, or one older than the state the workspace already holds |
| `orphaned` | The subscription names a workspace this instance does not have, or a workspace that belongs to a different Stripe customer |

An orphaned event settles on its first attempt. Waiting cannot make it placeable, so it is never retried and never pages. It keeps its payload for `RETENTION_BILLING_EVENTS_DAYS`, the API logs a warning naming the event, the subscription and the customer, and the nightly reconciliation reports the subscription. The count of events settled as orphaned in the last seven days is `asobeast_billing_events_orphaned`, and while it is above zero the `billing.orphan.events` alert fires at investigate. See [Billing incident](/operations/runbooks/billing-incident) for what usually causes one.

An event that fails for a reason that can pass, such as Stripe or the database being unreachable, still retries, and while it waits for a fix it is counted by `asobeast_billing_events_failed`, which pages.

An event whose subscription is on a price the catalog cannot place fails once and stops. The catalog refreshes from Stripe first, so a price created since the last refresh retries instead. When the price is still unknown, retrying cannot teach the catalog about it, so the job fails at its first attempt, the stored event keeps its failure and no processed time, and `asobeast_billing_events_failed` pages. Once the cause is fixed, usually by running the catalog script or giving the price its `asobeast_plan` metadata, replay the event from support with `POST /admin/support/workspaces/<id>/billing-events/<eventId>/replay`. The replay clears how the event settled and queues it again under a fresh job, and it is audited like every other support action. While the catalog has not resolved at all, the same failure keeps retrying, because it can pass once Stripe answers. Upgrading to the release that introduced these outcomes settles, as orphaned, every stored event that had failed for one of the two orphan reasons, so those rows stop counting as failed.

## One sandbox per environment

Stripe posts every event of a sandbox to every endpoint registered in that sandbox. A laptop and production that share one sandbox therefore share their events: a checkout on the laptop arrives at production as a subscription for a workspace production has never seen. Give every environment its own sandbox.

| Environment | Stripe account | Webhook |
| --- | --- | --- |
| Development on a laptop | A sandbox of its own, for example `asobeast-local` | Forwarded by the Stripe CLI, see below |
| A disposable QA stack | The development sandbox, while no laptop uses it at the same time | Forwarded by the Stripe CLI to the stack's web origin |
| CI | None. No automated test reaches Stripe | None |
| Production before launch | A sandbox no other stack uses | An endpoint registered in the dashboard |
| Production at launch | Live mode | A new live endpoint, with rotated keys |

A stack that does not bill leaves `BILLING_ENABLED` false and holds no Stripe keys at all. Production warns at boot while billing runs on a sandbox key, as a reminder to switch to live keys before a customer pays.

Create a sandbox in the dashboard from the account menu, then log the Stripe CLI in to it and forward its events to the local API:

```bash
stripe login --project-name asobeast-local
stripe listen --project-name asobeast-local --all-snapshot --forward-to localhost:4000/billing/webhook
```

`stripe listen` prints a signing secret of its own. That is the `STRIPE_WEBHOOK_SECRET` of the stack it forwards to, not the secret of any registered endpoint. Run `pnpm --filter api stripe:catalog` once against each new sandbox.

## States a workspace moves through

| State | Entitled | Buying again | What runs |
| --- | --- | --- | --- |
| Trial | Yes | Checkout | Everything, at Indie limits |
| Paying, while the first payment confirms | No | Refused until it settles | Reads and exports only |
| Active | Yes | Portal, to change plan | Everything, at the plan limits |
| Past due | Yes | Portal, to change plan | Everything, while Stripe retries the charge |
| Unpaid or paused | No | Portal, to start collecting | Reads and exports only |
| Canceled or expired | No | Checkout | Reads and exports only |
| Free, never subscribed | No | Checkout | Reads and exports only |

The plan in force is derived rather than trusted: a paid plan past its period end falls back to the trial if one is still running, and to free otherwise.

Every Stripe status lands in one of four outcomes. It **entitles** the workspace, it is **recoverable**, it is **pending**, or it is **gone**. Recoverable is the row that used to strand a customer: an unpaid or paused subscription pays for nothing, and a second one would be a double charge, so the only way forward is the portal. A workspace in that state is told its subscription stopped collecting and is offered a resume, never a checkout that would be refused.

Pending is an `incomplete` subscription: the first payment needs authentication or is still processing, and Stripe gives it about a day to settle. It entitles nothing yet, and a second checkout is refused with a message that names the pending payment, because both attempts could otherwise complete and charge the customer twice. The paywall and the plan card say the payment is being confirmed and offer nothing to click. The subscription becomes active when the payment lands, or expires and frees the customer to buy again.

A trial that ends with no payment method on file pauses or cancels the subscription according to the trial setting on the Stripe side. Pausing keeps the same subscription and asks for a card; cancelling frees the customer to buy again. Either is coherent, so pick one in the dashboard and leave it alone.

## Trial

Seven days, Indie limits, no card. With SMTP configured the trial starts when the customer confirms their email, not at registration. A workspace gets one trial ever, recorded by `trialStartedAt`, so a returning customer resumes on a paid plan rather than a second free week.

Milestone emails go out on days 0, 3, 5, 7 and 8 through the same SMTP transport and delivery log the product alerts use. The day 3 message is the one that matters: three days of positions is the first point at which the keyword monitor shows movement rather than a single reading.

## Dunning

A failed charge moves the subscription to `past_due`, which **stays entitled**. Revoking on the first decline turns an expired card into churn. asobeast emails the owner once, points them at the billing portal, and then follows Stripe's own retry schedule. Recovery is automatic: the next `invoice.paid` clears the warning and restores the plan with no manual step.

## Downgrade and cancellation

Both are self service through the Stripe customer portal. A cancellation takes effect at period end, so the customer keeps what they paid for. A downgrade, or a switch from annual to monthly, is scheduled at period end as well. An upgrade applies at once and invoices the difference. A plan change is a portal change, never a second checkout: a workspace that already names a live subscription is refused a checkout session with 409 and sent to the portal, so one workspace is never charged twice.

A workspace also gets at most one checkout session it can complete. Opening a session claims a short lease, so two requests in flight together cannot both create one, and the previous session is expired at Stripe before a new one opens, so a page left open in another tab cannot be paid afterwards. Stripe itself is asked for the customer's subscriptions before any session is created, which closes the window between a completed payment and the webhook that records it. A subscription found that way is reconciled onto the workspace before the checkout is refused, so the customer keeps what they already pay for, and a refusal that rests on stored state reconciles first as well rather than trusting a row a webhook may have missed. A live subscription on the customer whose metadata names a different workspace refuses the checkout without adopting it: one customer is never billed twice, and the mismatch is logged for support. Turn on **Limit customers to one subscription** in the Stripe dashboard as well: it is the only thing that stops two checkout tabs both completing.

A refusal carries the recovery in the error body, not only in its message, so the web app can open the portal for the customer rather than showing them a dead end.

- asobeast reads the scheduled phase from Stripe and records the plan the workspace will land on.
- Within a week of the effective date, if the workspace would be over the smaller plan's limits, the owner is emailed with the exact numbers.
- At the effective date the daily run covers the first items in a stable order and leaves the rest untouched. **Nothing is deleted.**

The catalog script provisions the portal rather than leaving it to the dashboard. It finds the default portal configuration and updates it, or creates one and says so. It allows cancellation at period end with a reason prompt, price changes across both products and all four prices with downgrades and switches to a shorter interval scheduled at period end, payment method updates, invoice history, and updates to the name, email, address, phone and tax id. It sets the terms and privacy links, `WEB_PUBLIC_URL` plus `/settings` as the default return, and turns the public portal login page off, because every portal visit starts from the API. Pausing is not offered: the portal of the pinned API version has no pause feature to configure, and a paused status is reserved for a trial that ended without a card.

## Reconciliation

Webhooks are reliable but not guaranteed, and stale local state means either a paying customer locked out or a churned one still served. A daily job compares every workspace against Stripe, treats Stripe as authoritative, corrects the difference and logs every correction at error level, because a reconciliation that quietly fixes drift hides a webhook bug. It also reports subscriptions Stripe knows about that belong to no workspace. The last nightly report is kept, and the number of those orphan subscriptions is exported as `asobeast_billing_orphan_subscriptions`. While it is above zero the `billing.orphan.subscriptions` alert fires at investigate and lists up to five of the ids. A reconciliation of one workspace says nothing about orphans and never replaces the report.

Reconciliation looks up a subscription two ways. The stored subscription id comes first, and when there is none, when Stripe has forgotten it, or when the one it names is already cancelled, the workspace customer is asked what it holds. A subscription there that names no other workspace in its metadata is adopted, which is what rescues a customer whose checkout completed and whose webhook never landed. Only a workspace that claims something Stripe cannot back is revoked, so a running trial is left to expire on its own rather than being reset every night.

The same repair runs the moment a customer comes back from checkout: the return carries a marker and the completed session id, which the app reads once, and it reconciles the workspace by that session there and then rather than waiting for a webhook that may never arrive. The marker is added to `STRIPE_PORTAL_RETURN_URL` as well when that is set, so the repair does not depend on the default return page. It is only cleared once the reconciliation succeeds, so a return that arrives while Stripe is unreachable is retried on the next load.

Only an authoritative answer revokes a plan. A subscription Stripe reports as missing is gone and the workspace drops to free, but a timeout, a rate limit, a rejected key, an outage or a price the local catalog cannot name leaves the workspace exactly as it is and is reported as unreconciled, because a provider that cannot answer is not the same as a customer who stopped paying.

An owner can reconcile their own workspace immediately with `POST /billing/reconcile`, so support can resolve a single stuck customer without waiting for the next run. That call answers 503 rather than a report when Stripe cannot be reached.
